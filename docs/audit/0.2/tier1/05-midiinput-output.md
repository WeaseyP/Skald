## Findings

### F-A05-1: Master Volume of exactly 0 exports as full volume, not mute
- **kind**: code-bug
- **node**: Output / project master
- **severity**: high
- **confidence**: high
- **evidence**: `skald-ui/src/components/Sequencer/SequencerDock.tsx:211` (`min="0"` on the master volume `<input type="range">`, matching the manual's documented 0–1 range); `skald-ui/src/app.tsx:82` (`useState(0.8)`, the same real value threaded through to Generate at `app.tsx:370`); `skald-ui/src/utils/projectSerializer.ts:110` (`master_volume: masterVolume` — sent through with **no** floor, unlike instrument volume which is floored at `projectSerializer.ts:199`); `skald-backend/core/codegen.odin:2455-2456` (`master_vol := project.master_volume; if master_vol <= 0.0 do master_vol = 1.0`).
- **detail**: The `<=0.0 → 1.0` fallback exists to treat an *absent* JSON field (an old save without `master_volume`) as unity gain — the same pattern the code correctly applies to instrument volume, where the UI serializer floors the value at `0.001` specifically so an intentional 0 is never confused with "absent" (`projectSerializer.ts:197-199`, comment: *"the backend reads an exact 0 as 'field absent' and substitutes unity"*). That floor was never applied to `master_volume`. A user who drags the transport dock's Master Volume slider to 0% — the obvious way to mute a project before exporting — ships a build that plays at full (`tanh(x*1.0)`) volume instead of silence. The live preview is unaffected because it bakes `master_volume` as `1.0` and drives the real slider through a separate JS `GainNode` (`useWasmAudioEngine.ts:92-95`), so this bug is invisible until the exported Odin actually runs, e.g. in the game.
- **suggested fix**: Apply the same "floor away from the absent-sentinel value" pattern used for instrument volume — either floor `masterVolume` at a tiny epsilon (e.g. `0.0001`) client-side in `projectSerializer.ts` before it reaches the backend, or change the backend's absent-field detection to a real optional/sentinel (e.g. `< 0.0`) instead of `<= 0.0`, since `0.0` is a legitimate mute value nowhere else in the codebase treated this way.

### F-A05-2: Manual's "Range" column for `device` lists display labels, not the stored parameter values
- **kind**: doc-bug
- **node**: MIDI Input
- **severity**: low
- **confidence**: high
- **evidence**: `midiInput.md:52` states the `device` range as `"All"`, `"Device A (Mock)"`, `"Device B (Mock)"`; actual `<option>` values in `ParameterPanel.tsx:365-367` are `"All"`, `"Device A"`, `"Device B"` — `"(Mock)"` only appears in the visible option text, not the value that lands in `data.device` / the serialized `parameters.device`.
- **detail**: A reader who expects `device === "Device A (Mock)"` (e.g. while writing an exposed-param integration, or hand-editing a saved `.skald.json`) will get a value that doesn't match anything they've read in the table. Harmless today because nothing reads `device` downstream (Code-vs-intent note 5), but the table conflates UI label with stored value.
- **suggested fix**: Split the table cell into "stored value" vs "displayed label", or just cite the values verbatim (`All` / `Device A` / `Device B`).

### F-A05-3: No diagnostic for zero or multiple `GraphOutput` nodes inside one instrument
- **kind**: missing-feature
- **node**: Output
- **severity**: medium
- **confidence**: medium
- **evidence**: `graph_validate.odin` has no check that at least one `GraphOutput` exists per instrument, and no check that flags more than one. `codegen.odin:2025-2047` (`generate_graph_output_adds`) simply sums whatever wires reach each `GraphOutput`'s `input` port into the same shared `output_left`/`output_right`, called once per `GraphOutput` node found during emission (`codegen.odin:1892-1893`, `:1993-1994`). Two `GraphOutput` nodes inside one instrument's subgraph therefore behave identically to one `GraphOutput` receiving both sets of wires — no separation, no error, no warning.
- **detail**: The zero-Output case is well documented (`output.md` Code-vs-intent note 3: "not an error — it is silence") but has no build-time diagnostic in the code despite `graph_validate.odin`'s stated design philosophy of "fail loudly on wires the generators would ignore" (`graph_validate.odin:9-19`). The more-than-one case isn't documented at all: a user who drops a second Output node expecting a second independent destination (e.g. to audition a sub-mix separately) instead gets it silently merged into the one stereo pair, with no indication anywhere in the UI that this happened.
- **suggested fix**: Add two low-cost warnings (not hard errors, since dry/wet parallel summing into one Output is legitimate) — one when an instrument's subgraph has zero `GraphOutput` nodes, one when it has more than one — printed by `validate_connections` or a sibling pass, so "why is my patch silent/why didn't my second Output do anything" stops being a support question.

### F-A05-5: The Pitch port's V/oct framing invites the exact double-transposition bug the manual has to warn about — kind: design
- **kind**: design
- **node**: MIDI Input
- **severity**: medium
- **confidence**: medium
- **evidence**: Oscillators already read `voice.current_freq` unconditionally (`codegen.odin:136`, filled at note-on by `codegen.odin:1447`: `freq := 440.0 * math.pow(2.0, (f32(note)-69.0)/12.0)`). MIDI Input's `pitch` output independently emits `(f32(voice.note)-69.0)/12.0` (`codegen.odin:776`) — the *same* exponent, framed as a V/oct control-voltage signal, which is the idiom every modular/CV chapter section in `midiInput.md` builds the reader's mental model on (`midiInput.md:11-13`: "1 volt per octave... Skald's Pitch output speaks this language"). Wiring it the way a CV-literate user would expect — straight to `input_freq` — silently doubles the transposition (`codegen.odin:151-163`), and the shipped example patch `sax3.json:231-236` does exactly this.
- **detail**: This isn't just a documentation gap (already tracked as a "blocker" in Code-vs-intent note 1) — it's a shape-of-the-abstraction problem. Skald made a deliberate, correct choice that oscillators track the note implicitly ("note-wins", `codegen.odin:128-135`), which is the right call for a game-audio tool where MIDI/piano-roll melodies must work with zero patching. But having *also* exposed a raw V/oct-shaped `Pitch` output on the same node actively re-invites the classic modular mistake this design choice was supposed to make impossible. A generic-performance-input redesign should either (a) not expose a literal V/oct mirror of the note at all — only an explicit, clearly-labeled *Transpose* signal defaulting to 0 that is unambiguously "add-on-top", or (b) keep the current signal but have `graph_validate.odin` special-case and warn on the one connection shape (`MidiInput.pitch` → any oscillator-family `input_freq` with no intervening node) that is *never* correct, since the manual itself can find no legitimate direct use for it.
- **manual impact**: `midiInput.md` "What it is" → Pitch paragraph (`:11-13`); "The controls" → "What you hear as you sweep each one" → Pitch (`:67-71`); "Why you patch it this way" → the two Pitch bullets (`:121`); "Try it" steps 4–5 (`:99-103`); Code-vs-intent note 1 (`:181-182`) would be resolved rather than merely documented.
- **migration**: `sax3.json` (and any other saved patch wiring `MidiInput.pitch` directly to an oscillator/FM/wavetable `input_freq`) currently plays doubled intervals by the manual's own admission — an automatic upgrade would need to detect that specific connection shape on load and either delete the wire (restoring correct pitch, matching what the manual's own "Try it" step 5 tells the user to do by hand) or insert a corrective ×0.5 Mapper inline. If the port is renamed (option a), every saved connection with `from_port == "pitch"` off a `MidiInput` node needs a rename pass to whatever the new port id is, since `graph_validate.odin`'s `valid_output_port` matches by exact string.

### F-A05-6: Gate is a plain multiplier wired next to an ADSR that is actually driven by a separate, hidden mechanism — kind: design
- **kind**: design
- **node**: MIDI Input, ADSR
- **severity**: medium
- **confidence**: medium
- **evidence**: `MidiInput.gate` is `1.0` until `voice.time_released > 0.0` (`codegen.odin:779-780`). The ADSR's own envelope stage machine is driven directly by `note_on`/`note_off` setting `voice.adsr_<id>_stage` (`codegen.odin:1467`, `:1537`) — `voice.time_released` itself is stamped at `note_off` (`codegen.odin:1530`) independently of any wire. The ADSR's `input` port is just a signal multiplicand (`codegen.odin:292`: `out = input * envelope * depth * vel_scale`), defaulting to `1.0` unwired.
- **detail**: There are two independent "note is held" mechanisms in the graph: the real one (`voice.adsr_*_stage` / `time_released`, driven by note events, invisible to the graph) and a graph-visible one (the `Gate` port) that looks exactly like what a modular user would plug into an envelope but isn't. Because both derive from the same `time_released` timestamp, they're always in phase, which makes the failure mode worse, not better — the wire "looks right" (Gate does go low exactly at release) while silently zeroing the entire envelope including the release tail the user just dialed in. This is exactly the "competing controls that don't talk to each other" pattern the brief calls out: whichever one you touch first (design the envelope, or wire the gate) determines whether the release tail exists, and nothing warns you either way.
- **suggested fix**: Either drop the exposed `Gate` port entirely (VCA `input_gain` gating can be achieved by other means, or a differently-named "Hold" utility node) so there is only one mechanism, or invert the architecture so the ADSR's stage machine is *actually* driven by an incoming Gate connection when one exists (falling back to the current implicit behavior when unwired) — making the graph-visible wire the source of truth instead of a decorative parallel signal.
- **manual impact**: `midiInput.md` "What it is" → Gate paragraph (`:15`); "The controls" → Gate sweep section (`:73-75`); "Try it" step 8 (`:109`); "Why you patch it this way" Gate bullets (`:122-123`); Code-vs-intent note 2 (`:184-185`) would be resolved rather than merely documented.
- **migration**: `sax3.json:237-242` wires `Gate → ADSR.input`, already flagged by the manual as a blocker. If the port is removed, an automatic upgrade would need to delete any `MidiInput.gate` → `*.input`/`ADSR.input` connection on load (the manual has already established this wire is never correct); `Gate → VCA.input_gain` wires, if any exist in other examples, would need to migrate to whatever the replacement gating mechanism is.

### F-A05-7: Fixed 3-port MIDI Input can't grow into pitch bend, mod wheel or aftertouch without a new node type — kind: design
- **kind**: design
- **node**: MIDI Input
- **severity**: medium
- **confidence**: medium
- **evidence**: `graph_validate.odin:68-69` hardcodes exactly three legal output ports (`pitch`/`gate`/`velocity`) for `MidiInput`; `get_output_var` (`param_utils.odin:64-71`) hardcodes the same three suffixes. The live MIDI listener only ever inspects status bytes `0x90`/`0x80` (`useWasmAudioEngine.ts:367-374`) — no `0xE0` (pitch bend), `0xB0` (CC/mod wheel), or `0xD0`/`0xA0` (channel/poly aftertouch) branch exists anywhere in `skald-backend/core/` or the preview listener. `voice.velocity` is written once at note-on and never updated (`codegen.odin:1444`), so there is no field to carry a continuous pressure/bend value even if one were parsed.
- **detail**: The manual's own "Terms introduced" section defines MPE, aftertouch and per-note pitch bend (`midiInput.md:175-176`) — concepts the chapter clearly expects a reader to want — but the architecture has no path to add even the *simpler*, non-MPE, single-channel versions of these (ordinary 14-bit pitch bend and CC1 mod wheel are near-universal in MIDI keyboards and used far more often in practice than MPE) without inventing a whole new node type, because the port list and the voice struct are both closed enumerations rather than data-driven. A more idiomatic-for-the-domain shape would be a generic CC/performance-input mechanism (pick a controller number as a parameter, get a normalized 0–1 or bipolar output) that composes with the existing per-voice state instead of requiring bespoke plumbing per MIDI message type.
- **suggested fix**: Prioritize standard, non-MPE pitch bend and mod wheel as new fixed outputs on this node (cheap, broadly useful, no channel-per-note complexity) before any MPE work, and consider a separate generic "MIDI CC" node keyed by controller number for everything else, rather than hardcoding more ports into `MidiInput` one at a time.
- **manual impact**: `midiInput.md` "What it is" → MPE paragraph (`:21`); "Terms introduced" → MPE / Aftertouch entries (`:175-176`); Code-vs-intent note 4 (`:190-191`) — the "no implementation" note would become "no architecture for it yet" with a concrete alternative.
- **migration**: Purely additive — no saved `.skald.json` project references a pitch-bend or CC port today, so no upgrade-on-load work is needed either way.

### F-A05-8: Master/instrument volume are baked compile-time constants — not what a game integrator expects from an "Output" — kind: design
- **kind**: design
- **node**: Output
- **severity**: high
- **confidence**: medium
- **evidence**: `codegen.odin:2012` returns `output_left * f32(<instrument.volume literal>)`; `codegen.odin:2477-2478` bakes `master_vol` as a literal into `math.tanh(mixed_left * <literal>)`. Neither has a generated setter (`output.md` Code-vs-intent note 6 already documents "no `project_set_volume` or equivalent is emitted"). The only way to get a runtime-movable level is the manual's own workaround: place a VCA immediately before Output and manually tick its exposure checkbox (`output.md:81`, `:122`).
- **detail**: For a tool whose stated purpose is generating DSP for a game engine to consume, "adjust the overall loudness of an asset, or duck the whole mix, at runtime" is about as core a requirement as a game-audio integrator has (music ducking under dialogue, distance attenuation, a settings-menu volume slider). Today that requires the integrator to know, out of band, that they must manually insert and expose a VCA — a workaround the manual has to spend a whole paragraph teaching, rather than a capability the Output/Instrument boundary provides by default. It also compounds F-A05-1: because "user gain" and "safety saturation" are fused into one `tanh(x * master_volume)` expression, there is no way to mute independently of the limiter curve, and the absent-value sentinel bug (0 → 1.0) becomes reachable in the first place *because* master volume has to double as both a level control and a magic "was this field set" flag.
- **suggested fix**: Make master volume and per-instrument volume always-exposed runtime parameters by default (e.g. auto-generate `project_set_master_volume` / `<Asset>_set_volume`), and separate "gain" from "safety limiting" into two independent stages so a gain of 0 can never be confused with an unset field.
- **manual impact**: `output.md` "The controls" table + "What you hear as you sweep them" (`:57-73`); "What 'expose' means, and why Output has nothing to expose" (`:77-81`); "Going further" → "Give yourself a master fader your game can move" (`:120-122`); Code-vs-intent note 6 (`:201`) would be resolved rather than merely documented.
- **migration**: Purely additive to the generated Odin API (new setters appear; existing `_process`/`_init` signatures are untouched), so no change to the saved project JSON schema and no upgrade-on-load logic needed for `.skald.json` files under `examples\`. Any *already-generated and hand-integrated* Odin source in a downstream game would need to be regenerated to pick up the new setters, but that is true of any codegen change and isn't a project-file migration concern.

### F-A05-9: Named instrument sub-graph output ports imply a multi-port patchbay the backend doesn't build — kind: design
- **kind**: design
- **node**: Output (InstrumentOutput / sub-graph ports)
- **severity**: medium
- **confidence**: medium
- **evidence**: `useNodeComposition.ts:113-116` keys ports by `(node, handle)` specifically so multiple boundary-crossing wires get distinct, uniquely-named `InstrumentInput`/`InstrumentOutput` nodes (comment: avoiding "silently cross-wiring every source into every target"), and the Instrument node advertises this as a named `outputs` list. But `InstrumentOutput` normalizes to the same `GraphOutput` backend type as the main Output node (`node-definitions.ts:220`, `json.odin:29`), and `generate_graph_output_adds` (`codegen.odin:2025-2047`) never reads any `name` field — every `GraphOutput` in a subgraph, named or not, adds into the same shared `output_left`/`output_right`.
- **detail**: The UI invests real effort (collision-safe unique naming, a dedicated "outputs" list on the Instrument node) in presenting something that reads exactly like a studio patchbay with distinguishable rows — the same metaphor `output.md` uses to introduce this feature (`:17`, "The other two: Input and Output ports inside an Instrument"). The backend delivers a single anonymous stereo sum instead. An instrument built to expose, say, a "dry" and a "wet" output separately will compile without error and export as one indistinguishable mix — the two named rows on the patchbay are actually the same jack.
- **suggested fix**: Either commit to real multi-port instrument output (codegen would need to emit and return N stereo pairs, or a struct, keyed by port name) so effect-style instruments can expose genuinely separate sends, or stop presenting per-output naming as meaningful in the UI (collapse it to a single implicit output, matching what the backend actually does) so the interface doesn't promise a capability that doesn't exist.
- **manual impact**: `output.md` "The other two: Input and Output ports inside an Instrument" (`:39-46`); "For sub-graph ports, name them after what they carry" (`:118`); Code-vs-intent note 4 (`:197`) would be resolved rather than merely documented.
- **migration**: Any saved instrument under `examples\` with more than one `InstrumentOutput` node in its subgraph currently exports as one summed stereo pair. If true multi-port output is implemented, an automatic upgrade-on-load would need to detect subgraphs with >1 `InstrumentOutput` and either (a) preserve the old summed behavior explicitly (tag the instrument as "legacy single-output" so its exported audio doesn't silently change), or (b) surface a one-time migration prompt, since separating the outputs changes what the generated code returns and any external game code consuming it.
