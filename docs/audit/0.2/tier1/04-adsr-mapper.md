## Summary

- **Confirmed TRUE** — the ADSR's `input` handle really is an audio-rate VCA input, not a gate: it defaults to the literal `1.0` when unconnected (`codegen.odin:224`), sums multiple connections (`:226-239`), and the final line is `input * envelope * depth * vel_scale` (`:292`). The per-sample Attack/Decay/Sustain/Release formulas, the velocity blend `(1-sens)+sens*velocity`, and the zero-length-segment guard (`math.max(x, 0.000001)` denominators, branch for a literal `0`) all match the manual's "Under the hood" math exactly, just at different line numbers (see F-A04-1).
- **Confirmed TRUE** — the "sustain-zero trap": `envelope <= 0.0001` during `.Sustain` forces `.Idle` on that same sample (`codegen.odin:282`), and the very next voice-lifecycle check in the *same* per-sample pass deactivates the voice if that was the instrument's only ADSR (`:1915-1930`, `has_adsr`/`voice_busy`/`voice.active = false`). By the time note-off arrives the voice is no longer `active`, so `note_off`'s voice search never finds it and Release genuinely never runs. Traced end-to-end, this is exactly as the manual describes.
- **Confirmed TRUE** — Mapper's lerp/clamp/degenerate-range-guard code (`generate_mapper_code`, now at `codegen.odin:737-758`) matches the manual's formula and inline comment ("Degenerate range maps everything to outMin") verbatim, and both shipped patches quoted throughout the chapter (`house-pluck-bass.skald.json`, `wobble-samplehold-bass.skald.json`) match the manual's cited numbers exactly, including the 310–2960 Hz combined-sweep arithmetic.
- **Confirmed TRUE** — depth is unipolar end-to-end: `param_ranges.odin:68-69` (0–1), `ADSRNode.tsx:13` (min 0/max 1), the Parameter Panel slider (`NodeParameterControls.tsx:135`, `slider('depth', 0, 1, 1)`), and the exposed setter's compiled-in clamp (`codegen.odin:1681-1682`, reading the same range table) all agree — there is no path to a negative depth anywhere in the stack.
- **New** — several backend line citations in both chapters' "Under the hood" sections have drifted far enough to point at unrelated code (Mixer channel-gain logic, `note_off` internals, RNG seeding, the getter dispatcher) rather than the code they claim to quote, even though the manual's prose and the code's actual behavior still agree (F-A04-1, F-A04-2).
- **New (design)** — the ADSR/VCA fusion is not merely a convenience, it is load-bearing: the dedicated VCA (`Gain`) node's own gain-modulation port is additive, not multiplicative, and its shipped default gain is 0.75, which together silently defeat the "bare envelope into a separate VCA" idiom that is the documented pattern for every other destination in the patch (F-A04-4).

### F-A04-4: ADSR/VCA fusion is structurally required, not just convenient — the standalone VCA node can't do a proper envelope sweep
- **kind**: design
- **node**: ADSR / VCA (Gain)
- **severity**: medium
- **confidence**: high
- **evidence**: `GainNode.tsx:3-13` — the dedicated "VCA" node has an `input_gain` modulation port. `codegen.odin` `generate_gain_code`: `gain_str := get_f32_param(graph, node, "gain", "input_gain", 1.0)` then `node_out = input * gain_str`. `get_f32_param` (`param_utils.odin:138-156`) sums modulation **additively** onto the base gain: `result = (base) + (mod1) + (mod2)...` — the same convention used for every other destination in the codebase (filter cutoff, pan, etc). The VCA node's own shipped default is `gain: 0.75` (`node-definitions.ts:154-157`).
- **detail**: Every other chapter (and this one, for filter-cutoff modulation) teaches the idiom "bare modulation source → destination's own modulation port, with the destination's own knob set near the bottom of the intended range." Applied to amplitude with the standalone VCA node, that idiom is actively broken: routing a bare 0-1 ADSR into the VCA's `input_gain` produces `gain = 0.75 + envelope`, i.e. output ranges from 0.75x (never silent) to 1.75x at the envelope's peak — the opposite of an amplitude envelope, and a trap for anyone arriving with modular-synth intuition (envelope generator, separately, into a VCA). The *only* place in the entire generated codebase that multiplies an audio signal by a control signal is the ADSR's own hardwired `input * envelope` line. So the fusion the manual frames as a convenience ("Skald's ADSR node does both jobs with the same code") is actually load-bearing: it is the sole mechanism by which Skald can produce a proper 0→full→0 amplitude shape at all. (A user *can* make the standalone VCA work by manually zeroing its own `gain` knob first — since additive-onto-zero equals the envelope value directly — but nothing in the UI, the node's default, or either manual chapter says so.)
- **suggested fix**: Either (a) document explicitly, in both the ADSR and a future VCA chapter, that amplitude-envelope modulation via the standalone VCA requires zeroing its own `gain` knob first, or (b) make `input_gain`'s modulation multiplicative (`gain_out = base * (1 + mod)` or similar) so "bare envelope into VCA" behaves the way every other "bare source into Mapper into destination" idiom in the manual already trains users to expect.
- **manual impact**: ADSR chapter, "The second big idea..." paragraph (line 15) and "What it looks like in Skald" paragraph describing the VCA fusion (line 28); Code-vs-intent note 1 (the "Gate" mislabeling discussion) would need a companion note about the standalone VCA's additive gain; "Why you patch it this way" canonical-chain paragraph (lines 99-103). A new VCA/Gain chapter (none currently exists in scope) would need this as its lead caveat.
- **migration**: If `input_gain` modulation semantics changed to multiplicative, no *existing* saved patch wires anything into a VCA's `input_gain` in the shipped examples (grep of `examples/` shows no `to_port: "input_gain"` / `targetHandle: "gain"` connections), so the change is likely safe to make without a graph-rewrite migration — but any hand-authored or user-saved project that *does* use `input_gain` today would change sound on load with no warning. An automatic upgrade would need to detect existing `input_gain` connections and either leave them under a legacy additive code path (versioned node behavior) or insert a compensating Mapper (`out 0..1` unchanged, since additive-into-zero and multiplicative-into-one coincide only when the base gain was already 0).

### F-A04-5: Mapper has no curve/exponential shaping option — a real gap given how central it is to usable modulation
- **kind**: design
- **node**: Mapper
- **severity**: medium
- **confidence**: medium
- **evidence**: `MapperNode.tsx:11-16` and `MapperParams` (`types.ts:151-156`) expose exactly four linear parameters (inMin/inMax/outMin/outMax); `generate_mapper_code` (`codegen.odin:737-758`) is a single `math.lerp` — no curve, exponent, or skew term anywhere in the pipeline. The chapter's own "Going further" and "Why you patch it this way" sections repeatedly demonstrate destinations that are linear-in-Hz (filter cutoff, `param_utils.odin:149-153`) versus exponential-in-octaves (oscillator/wavetable/FM pitch, `codegen.odin:163`, `:498`) as a fixed property of the *destination*, never the Mapper.
- **detail**: For pitch destinations the Mapper doesn't need internal curve support — the destination already exponentiates, so a plain linear Mapper output (in octaves) is correct. But for every linear-add destination (filter cutoff being the flagship example, `Cut`/`Res`, `Gain`, `Pan`), a Mapper can only ever produce a perceptually uneven sweep: equal steps of the 0-1 input produce equal Hz steps of the output, but equal Hz steps are not equal *musical* steps (the chapter's own opening paragraph makes exactly this point about pitch, and it's equally true of a wide cutoff sweep). Getting a musically-even filter sweep today requires either accepting the unevenness, stacking multiple Mappers, or exploiting an oscillator/FM node's own exponential math as an unrelated workaround — there is no first-class way to ask "give me a log-spaced sweep from 150 Hz to 1900 Hz" directly. A `curve` (or `exponential: bool`) parameter on the Mapper, defaulting to today's linear behavior, would close this gap without touching any destination code.
- **suggested fix**: Add an optional curve/exponent parameter to the Mapper (e.g. `curve: f32` where `1.0` = today's linear lerp and other values bias the `t` before interpolating), defaulting to linear so existing patches are unaffected.
- **manual impact**: Mapper chapter's "The controls" table (would gain a fifth row, lines 40-49), "What you hear as you sweep each one" (the Out Max paragraph, line 67, currently has to talk around the unevenness), "Under the hood" per-sample math block (lines 172-188), and "Going further" (several bullets, e.g. "Layer fast and slow," would simplify if a curve knob existed instead of requiring multiple chained Mappers).
- **migration**: None needed for existing patches — a new parameter with a linear-preserving default (`curve = 1.0` / `linear` mode) is additive and backward-compatible; `generate_mapper_code` would just need the new term folded into the `t` computation, gated so an absent/default value reproduces today's exact generated code byte-for-byte.

### F-A04-6: The Mapper chapter's own "no-Mapper" cautionary example uses a deprecated project schema
- **kind**: inconsistency
- **node**: Mapper
- **severity**: low
- **confidence**: high
- **evidence**: `examples/instruments/bass/lfo-filter-wobble-bass.skald.json` (cited in the chapter's step 3 and in Code-vs-intent note 5) is a flat top-level `nodes`/`edges` document with no `instrument` wrapper node, unlike its four sibling files in the same folder (`house-pluck-bass`, `wobble-samplehold-bass`, etc.), which all wrap their graph in an `instrument` node with a `subgraph`. `skald-backend/core/json.odin:309-326` explicitly handles this shape as a fallback: *"Legend loose graphs have no Instrument wrapper. Treat the whole graph as one SFX named Asset so the old examples still codegen"* — and hardcodes `voice_count = 1` for it.
- **detail**: Beyond the already-logged "this patch has no Mapper and barely wobbles" bug, the file is *also* structurally stale: it will load as a monophonic, unnamed "Asset" rather than a polyphonic "bass instrument" the way every other example in `examples/instruments/bass/` does, and the backend comment calling this path "legacy" strongly suggests the file predates the current Instrument-wrapper convention entirely rather than being a deliberately minimal teaching fixture. That makes it a doubly weak example to hang a teaching point on.
- **suggested fix**: Either re-save `lfo-filter-wobble-bass.skald.json` in the current Instrument-wrapped schema (matching its siblings) while fixing the missing Mapper, or drop it from the manual's citations in favor of a properly structured counter-example.
