## Findings

### F-A08-1: Mixer chapter's headline "blocker" bug (exposing a channel level discards the fader value) is fixed in current code
- **kind**: doc-bug
- **node**: Mixer
- **severity**: high
- **confidence**: high
- **evidence**: `skald-backend/core/codegen.odin:619-673` (`mixer_channel_level`, `mixer_level_channel`, `exposed_param_default`) — `exposed_param_default` special-cases `node.type == "Mixer"` and resolves the real authored `levels[channel-1].level` value instead of falling through to the range-table default; consumed at `codegen.odin:1248` (`def_val := exposed_param_default(node, p_name, rng.default)`) and written at `codegen.odin:1387-1389` (`p.%s = %.9f`, `res.default`). Proof: `skald-backend/tests/fixtures/mixer_exposed_default.json` authors `level1 = 0.25` and exposes it; `skald-backend/tests/golden/mixer_exposed_default.odin.golden:114` emits `p.level1 = 0.250000000` — the exact authored value, not the 1.0 the manual claims. `mixer.md`'s Code-vs-intent note #1 (lines 380-392) still describes this as a current "(blocker)" and cites `codegen.odin:1191-1198`, which in the current file is unrelated bus-domain struct-field code (Filter/LFO/Noise/SampleHold/Distortion state), not the exposure-default lookup at all — a strong sign the fix landed after the prose was written.
- **detail**: A user reading the manual today will be told that exposing "Input 1 Level" silently mutes/unity-pins that channel and should be avoided, or worked around by leaving channels unexposed. That is no longer true: the fader value the UI shows is exactly the value the exported instrument starts with. The manual actively discourages a feature that works correctly, which is worse than silence on a real bug — it teaches users to avoid something that is fine and to distrust a "your game gets a fader" workflow the same chapter otherwise recommends.
- **suggested fix**: Rewrite Code-vs-intent note #1 to describe the current (correct) behaviour, keep the historical note about the range-table fallback once being 0.0 (`param_ranges.odin:40-42`'s comment is still accurate as history), and re-cite the real resolution path (`codegen.odin:619-673`, `1246-1248`, `1387-1389`) plus the golden test as living proof.

### F-A08-3: A Panner at centre pan is quieter than the same source wired straight to Output — undocumented in both chapters
- **kind**: code-bug
- **node**: Panner, Output
- **severity**: high
- **confidence**: high
- **evidence**: `codegen.odin:2025-2047` (`generate_graph_output_adds`): for a Panner source it emits `output_left += node_<id>_out_left` / `output_right += node_<id>_out_right` (the equal-power pair, each 0.7071× input at pan 0, `codegen.odin:727-729`); for every other (mono) source it emits `output_left += v` and `output_right += v` with `v := get_output_var(src.id, src.port)` at full, unattenuated gain (`codegen.odin:2041-2045`). No -3 dB or any other pan law is applied to the direct path. `panner.md` states "it sounds the same loudness wherever you put it" (line 3) and, in the hands-on section, "it does not get louder or quieter" (line 97) — both true only when *sweeping the Panner's own slider*, not when compared to skipping the Panner entirely.
- **detail**: A user who wires an oscillator straight to Output gets full-scale in both channels. If they then insert a Panner set to 0 (the default) between the source and Output — e.g. to "future-proof" the patch for later automatic panning, or just because Panner is the idiomatic terminal node the manual recommends — the same source becomes audibly quieter (0.7071 vs 1.0 per channel, roughly -3 dB per side and up to -6 dB as heard through a mono fold-down: 1.414 summed loudness vs 2.0). Nothing in the UI or either chapter warns about this; the manual's own "why you patch it this way" section (panner.md lines 109-127) recommends terminating every tone chain in a Panner without mentioning that doing so changes loudness relative to not doing it.
- **suggested fix**: Either give the direct (non-Panner) mono-to-Output path the same 0.7071/0.7071 treatment so "no Panner" and "Panner at 0" are level-matched (code fix, most consistent with the equal-power design intent), or, if the current behaviour is intentional (direct wiring meant as true dual-mono, no pan law implied), add an explicit Code-vs-intent note in `panner.md` describing the loudness step a user will hear when adding/removing a terminal Panner.

### F-A08-4: "Stereo" in Skald is a single exceptional code path, not a general capability — design question raised by the project owner
- **kind**: design
- **node**: Panner, Mixer, Output (engine-wide)
- **severity**: medium
- **confidence**: high
- **evidence**: `00-foundations.md:3, 35` states every node computes exactly one `f32` per sample; `00-foundations.md:375-399` gives the instrument skeleton and shows `output_left`/`output_right` as accumulators fed by `node_<id>_out`, without ever mentioning that Panner is the sole node writing a genuinely different pair (`node_<id>_out_left/_out_right`, `codegen.odin:728-729`) or that this pair only survives one hop (`codegen.odin:2038-2040` special-cases exactly the Panner-to-GraphOutput edge; every other consumer reads the mono downmix at `codegen.odin:733`). Delay and Reverb hold **one shared buffer per instrument** (`codegen.odin:71-76` comment, corroborated by `00-foundations.md:191`), so they cannot process left and right independently even in principle. `types.odin:61-65`'s `Connection` struct carries no channel dimension at all — a wire is `from_node/from_port/to_node/to_port`, nothing else.
- **detail**: The engine is honestly describable as **mono-with-a-terminal-pan-stage**: every node computes one number, voices are summed as one number, bus effects (Delay/Reverb/Distortion/Filter/Mixer) all run on one number, and "stereo" is manufactured only at the very last node before Output by splitting that one number into `cos`/`sin`-weighted copies. This is a coherent, cheap design for game middleware — CPU cost never doubles except at the final pan step, and it matches how many older synths and a lot of procedural game audio actually work — but it is not stereo in the DAW sense: there is no way to build an independent-channel effect (stereo widening, ping-pong delay, decorrelated stereo reverb, mid-side processing) anywhere in the graph, and the one node that does touch two channels (Panner) has its output destroyed the instant it feeds anything except Output (already well documented in `panner.md`'s own Code-vs-intent note #2). The chapter that should own this framing (`00-foundations.md`) never states it as a design fact; it hides the exception inside a simplified pseudocode block instead.
- **suggested fix**: If the mono-with-terminal-pan model is being kept for 0.2, state it explicitly and once, in Foundations, as a scoping decision with its cost (no stereo effects; Panner must be the last node; direct-to-Output sources and Panner-centred sources currently differ in loudness — see F-A08-3) rather than leaving it to be inferred chapter-by-chapter. If real stereo is wanted, the cost is a rewrite of the DSP core, not an incremental change: every `generate_*_code` proc, the per-voice/per-bus state structs, `get_output_var`/`get_f32_param`/`sum_port_inputs` in `param_utils.odin`, and `graph_validate.odin`'s port tables would all need a channel dimension (or a doubled code-generation pass), Delay/Reverb buffers would double per instrument, and the UI would need a per-node mono/stereo affordance instead of a single number box.
- **manual impact**: `00-foundations.md:3, 35, 375-402` (the "one number per sample" claim and the instrument-skeleton pseudocode) would need a stated exception for Panner and an explanation of why "stereo" is legal only on the Panner→Output edge. `docs/manual-source/nodes/mixer.md`'s "The output is mono" passage (lines 80-84) and "Nest mixers" bullet (Going further, ~298-300) already describe the mono reality correctly and would only need to change if real per-node stereo were built. `docs/manual-source/nodes/panner.md`'s "What it looks like in Skald" section (lines 19-37, especially "The one rule that matters" at line 35) and "Why you patch it this way" (lines 109-127) currently present the Panner's stereo pair as a special affordance to route carefully around — accurate today, but framed as an incidental UI quirk rather than a stated architecture boundary; both would need reframing either way the design question is resolved.
- **migration**: If the model is kept (documentation-only fix): zero patch migration, no example under `examples/` changes. If real per-node stereo is introduced: none of the 66 example patches under `examples/` declare a schema/version field (checked directly — absent from both `slap-bass.skald.json` and `glassy-fm-pluck.skald.json`), so there is no existing hook to key an automatic upgrade off of. An upgrader would need to add one (e.g. a `graph_version` field defaulting missing values to "legacy mono"), and every node in every existing patch would need to be tagged to force the old single-channel codegen path — otherwise a stereo-aware rewrite of, say, Delay or Filter would silently change the exported audio of shipped instruments the moment the patch is re-exported, which is a correctness regression, not just a migration inconvenience.

### F-A08-5: Mixer's fixed 1-32 indexed-slot model vs. a dynamic or connection-keyed alternative — design question raised by the project owner
- **kind**: design
- **node**: Mixer
- **severity**: medium
- **confidence**: medium
- **evidence**: Mixer requires an explicit `inputCount` (1-32) and a `levels` array sized to match (`node-definitions.ts:138-147`, `MixerNode.tsx:19-41`); the exporter matches levels to input ports **by array position** (`codegen.odin:709`, `mixer_channel_level` reading `levels[channel-1]`) while both UI surfaces match **by `id`** (`MixerNode.tsx:22`, `NodeParameterControls.tsx:259`) — already logged as `mixer.md` Code-vs-intent note #6, a direct symptom of the fixed-slot design. Reducing `inputCount` below a wired port number aborts the whole export (`graph_validate.odin:115-128`, `mixer.md` line 77-78). By contrast, `Output` and every other multi-input port in the engine (e.g. two oscillators into one Filter `input`) accept **any number of wires with no count field at all** and simply sum them (`param_utils.odin:164-177` `sum_port_inputs`, `00-foundations.md:402`); the manual itself notes this is "the only thing" a Mixer buys over a raw wire-merge (`mixer.md` lines 260-264). `types.odin:61-65`'s `Connection` struct has no field for a per-edge level, so there is currently no way to attach a gain to a wire itself.
- **detail**: The Mixer is the only node in the engine whose input "slots" are indexed and pre-declared rather than simply following whatever gets wired. That buys per-channel level and per-channel exposure, but the price is a class of bugs the fixed model manufactures on its own: the position-vs-id mismatch (note #6), the inputCount-vs-backend-default disagreement (note #7, 4 in the UI vs 8 in the exporter and validator), and the "wire it, then shrink Inputs" export failure the manual calls out as a "practical consequence" (line 77-78) rather than a design smell. A dynamic model — the Mixer renders one row per **currently wired** input, the same way Output already behaves, with the level keyed to the connection (or to the source node id) instead of a channel index — would remove the index/id desync and the count-mismatch bugs by construction, at the cost of needing a place to store a per-connection parameter, which the graph schema does not currently have anywhere.
- **suggested fix**: For 0.2, consider whether the Mixer should move to the same wire-driven-with-no-declared-count model as Output/Filter/every other multi-input port, with level keyed by source (node id) rather than by a positional slot index — this is a smaller change than adding true per-edge parameters to the graph schema and would eliminate notes #6 and #7 outright. A per-edge-parameter model (level living on the `Connection` itself) is the more general fix and would also make per-source pan meaningful for the first time, but requires extending `types.odin`'s `Connection` struct and every place that reads connections, a larger change.
- **manual impact**: `mixer.md`'s "Its handles are generated from the channel count" section (lines 66-84, especially the "if you wire channel 5 and then reduce Inputs to 4" passage at line 77-78) and the "Inputs" subsection (lines 137-142) describe the fixed-slot behaviour as the norm; both would need rewriting if the slot model changes. Code-vs-intent notes #6 and #7 would be resolved rather than merely documented and could be removed.
- **migration**: 20 of 66 patches under `examples/` use a Mixer (`grep -rl '"type": "mixer"'`). Moving to a wire-driven model would require, per patch, resynthesizing a per-connection or per-source-id level from the existing `levels[]` array — mechanically straightforward **only if the migration keys off array position** (matching today's actual codegen behaviour) rather than `id` (matching today's UI display), since the two already disagree in some hand-edited or reordered files; keying off `id` instead would silently change which level applies to which wire for any patch already affected by note #6. Slots with a declared level but no wire (unused channels within `inputCount`) would simply be dropped, which is safe. As with F-A08-4, there is no schema version field today to gate this migration on, so an upgrader would need to add one.
