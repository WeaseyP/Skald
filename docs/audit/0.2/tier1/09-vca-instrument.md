### F-A09-2: ADSR and VCA both scale audio by a time-varying signal, with incompatible semantics — and the shipped corpus overwhelmingly prefers the node the manual treats as secondary
- **kind**: design
- **node**: ADSR, VCA (Gain)
- **severity**: high
- **confidence**: high
- **evidence**: ADSR's own generator (`codegen.odin:223-293`) computes `node_X_out = (input_str) * envelope * depth * vel_scale` — a pure multiply, `input_str` defaulting to the constant `"1.0"` when nothing is wired (`codegen.odin:224`), with no offset/baseline concept. VCA's generator (`codegen.odin:761-768`, `param_utils.odin:73-158`) computes `(sum of In) * (knob + Σ modulation on input_gain)` — additive-offset semantics, entirely different maths for what the manual calls "the same job." I grepped every `*.json` under `examples/` (including nested instrument subgraphs) for edges landing on an ADSR's `input`/`gain` ports: **90** connections feed an oscillator/filter/noise/etc. directly into an ADSR's `input` (using ADSR's built-in VCA behaviour, e.g. `examples/instruments/bass/*.skald.json` almost universally), versus **7** connections that route an ADSR's envelope output into a separate VCA's `input_gain` (concentrated in `examples/songs/full/four-bar-song.skald.json` and two sax patches). gain.md's entire "Try it" section teaches converting the sine-sub-bass patch *from* the 90-style pattern *to* the 7-style pattern, and only that migration introduces the "additive gain trap" documented at length in the same chapter (the 0.75-default-drone bug is entirely a VCA artifact; routing straight into ADSR's own `input`, as 90% of the shipped instruments do, never exhibits it).
- **detail**: This is the textbook "two nodes doing the same job differently, and nothing tells you which one to use" case the brief asks for. A user reading gain.md's hands-on walkthrough is taught that the "proper" idiom is oscillator → VCA ← ADSR-Gain, and is walked through a bug (the additive-offset drone) that exists **only** because of that recommended detour — while the actual shipped content mostly just wires audio straight through the ADSR and never hits the bug at all. Worse, if a user does both (ADSR shaping its own `input` *and* separately feeding a VCA), the two "gain" concepts have different clamps (VCA's exposed setter clamps to `[0,4]`, codegen.odin:1612-1625; ADSR's `depth` has no modulation port and no clamp at all on the graph path) and no shared mental model.
- **suggested fix**: Pick one owner for "scale audio by an envelope." Either (a) strip ADSR down to a pure envelope generator with only an `Env` output (no audio-shaping `input` at all), forcing all note-shaping through VCA and eliminating the two-different-multiply-conventions problem outright, or (b) keep ADSR's built-in multiply but explicitly document it as the *recommended* fast path for the common case (single envelope, no LFO/other modulation needed) and reserve VCA for cases needing summed/offset control (tremolo, external game-driven gain, multi-source mixing) — but either way, stop teaching the VCA detour as if it were the only correct pattern when 90% of the shipped library disagrees.
- **manual impact**: gain.md's entire "Try it (hands-on)" section (steps 1-10, built around converting `sine-sub-bass.skald.json` from ADSR-direct to ADSR→VCA) would need to be reframed or removed if option (a) were taken — it currently exists specifically to demonstrate migrating *away from* the pattern 90% of the corpus uses. The "Why you patch it this way" section's claim "The amp envelope always goes into the Gain port, never into the audio path" (gain.md, under "Why you patch it this way") is already contradicted by the shipped examples and would need to be corrected regardless of which option is chosen. instrument.md's "canonical chain" claim (Oscillator → Filter → ADSR → Distortion → Output, citing `sub-808-glide-bass.skald.json:83-88`) is itself an instance of the 90%-pattern and should probably be the one held up as canonical, not gain.md's VCA detour.
- **migration**: Option (a) breaks **most** of the example library outright — 90 connections across dozens of files rely on ADSR's audio `input` performing a multiply; removing that capability would silence or misroute all of them. An automatic upgrade-on-load would need to detect, for every ADSR node with an audio-rate source wired to its `input` port, that this is really "oscillator → VCA(gain=0) → [ADSR's old destination]" and mechanically insert a VCA node (gain knob 0), rewire the audio source into its `In`, rewire the ADSR's `Env` output into its `Gain`, and repoint the ADSR's old downstream connection to the new VCA's `Out` — for every one of the 90 sites, not just the one tutorial file. Option (b) requires no migration at all, only a documentation change.

### F-A09-3: ADSR's only input port is labelled "Gate" but never gates anything — it is the audio-multiply input
- **kind**: qol
- **node**: ADSR
- **severity**: medium
- **confidence**: high
- **evidence**: `ADSRNode.tsx:6` declares `inputs: [{ id: 'input', label: 'Gate' }]`. The codegen (`codegen.odin:223-239`) treats this exact port purely as an audio signal to be summed and multiplied by the envelope (`sources := find_inputs_for_port(graph, node.id, "input")`); it plays no role in starting/stopping the envelope. The actual "gate" — the thing that starts and stops the ADSR's stage machine — is internal voice state (`voice.age`, `voice.time_released`), driven only by `<Foo>_note_on`/`_note_off` (`codegen.odin:1394-1520`), completely independent of anything wired on this port.
- **detail**: A user who understands what a "gate" is in synthesis (the on/off signal that starts an envelope, per the manual's own Terms glossary in gain.md: "Gate — the on/off signal that says 'a note is being held right now'") will reasonably expect this port to accept or emit that signal. It does neither — it is Skald's equivalent of the VCA's `In` port, silently repurposed as an audio pass-through with an unrelated label. gain.md's own "Try it" section 3 has the user wire "the oscillator's Out to the VCA's In" and separately remove "the oscillator → ADSR input wire" without ever commenting on why an audio wire was going into something called "Gate" in the first place.
- **suggested fix**: Rename the port's UI label from "Gate" to "In" (matching VCA's own naming) to stop implying a trigger/gate function that doesn't exist.

### F-A09-6: An Instrument can be nested inside another Instrument in the editor; codegen has no case for it and hard-crashes with a generic error
- **kind**: missing-feature
- **node**: Instrument
- **severity**: high
- **confidence**: high
- **evidence**: `useNodeComposition.ts`'s `handleInstrumentNameSubmit` (lines 66-205) and the `canCreateInstrument`/`selectedNodesForGrouping` gating in `app.tsx:379` never filter out nodes of type `'instrument'` from the selection used to build a new Instrument's subgraph — an existing Instrument node can be selected alongside others and swallowed into a new one. `json.odin`'s `build_graph_from_raw` is explicitly documented as recursive ("recursively constructs the main graph and any nested instrument subgraphs", `json.odin:149`, recursion at `json.odin:217-220`) and `normalize_node_type` maps `"Instrument"`/`"instrument"` to `"Instrument"` (not skipped, unlike `"group"` at `json.odin:31`), so a saved project with a nested instrument loads without complaint. But the per-voice node-type dispatch switch in `generate_processor_code` (`codegen.odin:1863-1901`) has cases for every DSP node type and no case for `"Instrument"`; it falls into the `case:` default and calls `os.exit(1)` with `"Error: unknown node type \"Instrument\" (node id %s) in instrument %q — no code generator exists for it."` (`codegen.odin:1898-1901`).
- **detail**: Nothing in the UI prevents constructing this graph, and nothing warns at save/load time — the failure only surfaces when the user clicks Generate Code, at which point the whole build aborts with a message that talks about "unknown node type" rather than explaining that containers can't nest. This is exactly the kind of "features that do not compose" and "dead end" pattern the brief calls out. instrument.md never states whether nesting is supported one way or the other.
- **suggested fix**: Either implement nested-instrument codegen (each nested Instrument becoming its own independently-polyphonic sub-voice-block, which is a substantial feature) or, far more cheaply, reject an Instrument-type node from the "Create Instrument" selection at UI time with an explicit message ("Instruments cannot be nested"), and validate it again at load time with a clear error instead of the generic codegen fallback.
- **manual impact**: instrument.md's "What it can and cannot connect to" section (which currently only discusses Group vs Instrument, not Instrument vs Instrument) would need a new paragraph stating nesting is unsupported (or, if implemented, describing how nested polyphony composes — e.g. does a nested Instrument's own `voiceCount` multiply against the parent's?).
- **migration**: None of the shipped `examples/` appear to rely on nested instruments (a quick structural scan found only `InstrumentInput`/`InstrumentOutput` inside subgraphs, never an `instrument`-typed node inside another instrument's subgraph), so no automatic upgrade is needed today — this is a latent trap for future content rather than an existing-content break.

### F-A09-7: Duplicating an Instrument (copy/paste or "Export Step to Instrument") never renames it — two instruments end up sharing an identical name and track label
- **kind**: inconsistency
- **node**: Instrument
- **severity**: medium
- **confidence**: high
- **evidence**: General clipboard paste (`useGraphState.ts:151-195`) deep-clones `node.data` (fixing an earlier shared-subgraph-reference bug per its own comment, lines 172-174) but never touches `data.name` or `data.label` — the pasted Instrument keeps the exact same displayed name as the original. The dedicated "Export Step to Instrument" action (`app.tsx:299-346`, button at `ParameterPanel.tsx:135`) does the same: `JSON.parse(JSON.stringify(sourceNode))` followed by a new top-level `id`, with `name`/`label` untouched. `useInstrumentRegistry.ts:14-25` then auto-creates a *second* sequencer track keyed by the new node id but displaying the same label (`node.data?.label || node.data?.name`). Because `clean_instrument_name` (`codegen.odin:960-964`) derives the exported Odin symbol prefix from `inst.name`, two same-named instruments collide; `resolve_unique_names` (`codegen.odin:2251-2266`) silently appends `_2`/`_3` to disambiguate at build time.
- **detail**: A user who copies an Instrument (or uses "Export Step to Instrument") ends up with two visually-identical entries in both the node canvas and the sequencer track list — same name, same label, indistinguishable except by position — and only discovers they are in fact different assets by opening the generated `.odin` file and noticing one of them got an invisible `_2` suffix. If they were relying on a specific exported symbol name (e.g. `Keys_trigger`) for game-side integration, they cannot tell from the UI which of the two on-canvas instruments produced `Keys_trigger` versus `Keys_2_trigger`.
- **suggested fix**: On paste/export-step, append a distinguishing suffix to the cloned Instrument's `name`/`label` (e.g. "Keys copy" or "Keys (Step 3)" — the Export Step path already builds a similar suffix for the *internal node* label at `app.tsx:319`, just not for the instrument's own name).

### F-A09-8: Whether an Instrument auto-plays its sequence is inferred from incidental sequencer content, not an explicit setting
- **kind**: design
- **node**: Instrument
- **severity**: high
- **confidence**: high
- **evidence**: `detect_asset_type` (`codegen.odin:801-809`) classifies an instrument as `.Music_Layer` if `active_sequencer_tracks` returns any non-empty, un-muted track, and `.SFX` otherwise — a pure function of transient sequencer content at Generate-Code time, not of any field on the Instrument node itself. That classification then directly controls whether `_process_sequence` is auto-invoked inside `_process` (`codegen.odin:1787-1788`: `if asset_type == .Music_Layer { ...%s_process_sequence(p)... }`) and several other emission branches (`codegen.odin:2296`, `2305`, `2441`, `2551`).
- **detail**: instrument.md documents the *existence* of the SFX/Music-Layer distinction ("Whether it exports as a one-shot SFX or a looping music layer is decided by whether a sequencer track points at it") but not that this is a live, re-evaluated-on-every-export inference rather than something the user deliberately commits to. Deleting the last note from an instrument's auto-created track (e.g. while auditioning a sound) silently flips that instrument from Music Layer to SFX on the next Generate Code, changing which public procedures get emitted and whether the asset self-drives — a behavioural change with no confirmation, undo-visible signal, or even a UI element that shows the current classification.
- **suggested fix**: Make asset type an explicit field on the Instrument node (e.g. a toggle: "One-shot SFX" / "Music Layer (sequenced)"), defaulting from current track content only the first time, so the generated public API shape is a deliberate, stable choice rather than a side effect of whatever happens to be in the track view at export time.
- **manual impact**: instrument.md's "One Instrument = one game asset" paragraph (under "Why you patch it this way") states the classification as if it were a stable fact about the instrument; it would need rewriting to describe an explicit user-facing toggle instead of (or in addition to) the inference rule, and the "Terms introduced" glossary entry for "Asset" would need the same correction.
- **migration**: Every existing `examples/*.skald.json` project would need its Instrument nodes backfilled with an explicit asset-type field on load, computed once using the exact same `detect_asset_type` heuristic that runs today (checking for any active note in that instrument's associated track) so behaviour is unchanged for existing saves at the moment of upgrade — the risk is purely in future edits, not in the one-time migration itself.

### F-A09-9: No project-level view of per-instrument polyphony/CPU cost — nothing compares "siblings"
- **kind**: design
- **node**: Instrument
- **severity**: medium
- **confidence**: medium
- **evidence**: Each Instrument's `voiceCount` (1-32), `unison` (1-16, oscillator-only, multiplicative with voiceCount per instrument.md's own "112 oscillator evaluations" example), and per-ADSR `release` time (up to 10s, `param_ranges.odin:66-67`) are configured purely per-instrument, inside that instrument's own parameter panel. I searched `skald-ui/src/components` for any project-wide summary/overview surface (`Overview`, `Voice Budget`, `ProjectSummary`, etc.) and found none.
- **detail**: This is the exact scenario the brief flagged: one instrument in a project can plausibly run 32 voices with 16-way unison and 10-second releases (112 oscillator evaluations per sample, ringing long after its notes end) while a sibling instrument sits at monophonic with no release tail, and nothing in the UI ever puts those two facts side by side. A user assembling several instruments into one game project (instrument.md's own recommended workflow — "one Instrument per distinct sound your game triggers") has no way to audit aggregate voice count / CPU cost across the whole project without opening every Instrument's panel one at a time.
- **suggested fix**: Add a lightweight per-instrument summary row (name, voiceCount × unison-cost, longest release time) somewhere always visible — even a one-line badge on each Instrument node's collapsed view would close most of this gap.
- **manual impact**: instrument.md's "Pick voiceCount from the music, not from ambition" (under "Going further") and "Voice Count — what you hear as you change it" sections would gain a cross-reference to whatever summary surface is added; currently they only discuss tuning a single instrument's voice count in isolation.
- **migration**: None — this is additive UI, no existing save format or generated-code change required.

### F-A09-10: A glide-rate clamp added defensively is mathematically unreachable
- **kind**: qol
- **node**: Instrument (glide)
- **severity**: low
- **confidence**: medium
- **evidence**: `codegen.odin:1808-1809` emits `glide_k := 1.0 / math.max(voice.glide_time * sample_rate, 1.0)` immediately followed by `if glide_k > 1.0 do glide_k = 1.0`. Since the denominator is already floored at `1.0` by `math.max`, `glide_k` can never exceed `1.0` — the guard can never trigger.
- **detail**: Harmless, but it's dead defensive code that could mislead a future maintainer into thinking `glide_k` can exceed 1 through some path it can't. instrument.md's own "Under the hood" code excerpt for glide (quoting lines around this point) omits this line entirely, so the manual's snippet and the live file have already drifted here, independent of this being dead code.
- **suggested fix**: Remove the redundant clamp, or add a one-line comment explaining it's intentionally-redundant defense-in-depth if there's a call path I didn't find that sets `glide_time` differently.
