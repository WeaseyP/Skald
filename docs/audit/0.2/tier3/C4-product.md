# C4 — Skald as a product: a teardown

Scope: the experience of using Skald, from install to shipping audio in a game. Judged against its
own pitch — *design a synth visually, ship it as Odin source that runs in your game* — and against
the alternatives a game developer actually has (write the DSP by hand, license FMOD/Wwise, or bake
`.wav` files in a DAW).

I read all 21 Tier 1/2 files (199 findings) before starting. Everything below that is load-bearing
I re-verified myself against the repo; where I could not verify, I say so.

**What I could not verify:** I did not launch the Electron GUI. Everything about the running app is
reasoned from source, from the checked-in binaries, and from artefacts I generated by invoking the
real `codegen.exe` / `skald_codegen.exe` / `odin.exe` from the repo. Where a claim depends on
observing the running app, I flag it.

---

## Verdict

Skald is not 0.2-releasable, and the reason is not the 199 findings in Tiers 1 and 2 — it is one
thing nobody found, because everybody audited the source and nobody audited the product. **The
`skald_codegen.exe` that the Electron app spawns is checked into git and is 51 commits behind
`skald-backend/core/codegen.odin`.** Every backend fix of the last release cycle — reverb pre-delay
(P1), mixer exposed levels (P3), the voice-steal anti-click fix, and the `"<nodeId>::<param>"`
live-parameter alias — exists in source, is covered by golden tests, passes CI, and is *absent from
the running application*. I proved this by generating the same fixture with both binaries and
diffing. The most damaging consequence: the UI addresses every live knob as `nodeId::param`, the
shipped binary emits no such alias, `Asset_set_param` returns false, and `topologySignature` masks
the value so no rebuild fires either — **in the app as committed, dragging an exposed knob during
playback does nothing at all.** That is the core loop, dead, in the shipped artefact, while 174 UI
tests and a 26-fixture FFT acceptance suite report green.

Everything else follows from the same class of problem: this project is rigorous about the parts it
can test and unexamined about the parts it ships. The manual is genuinely excellent — 21 chapters,
~130 verified code claims, DSP formulas correct down to the Kellett pink filter — and it is
untracked in git, absent from `extraResource`, unlinked from the README, and unreachable from
inside the app. The README's only two links are both 404s inside its own repo. 26 of 101 shipped
example patches cannot be played, and the Load dialog opens directly on them. Load itself is a
one-click, unrecoverable destruction of the current session: no dirty flag, no confirmation, no
title-bar filename, no autosave, and the undo stack is deliberately cleared in the same action.
Undo is broken in seven distinct ways, three of which mean the most common editing gestures
(dropping a node from the palette, moving a node, importing a patch) leave no undo entry at all.

The handoff to a game is the least finished part of the tool, which is remarkable for a tool whose
entire reason to exist is that handoff. The generated file's own header tells integrators to bypass
`project_process` — and `project_process` is the only place master volume and the tanh limiter
live, so Skald's recommended integration path discards the mix the sound designer authored and the
clipping protection, and the shipped demo substitutes an unexplained `* 0.6`. There is no runtime
volume setter, no documented thread-safety contract for the setters a game must call from gameplay
code, no version or provenance stamp in the generated file, and instrument-to-asset-index
assignment is non-deterministic on the bare-graph path.

None of this is hard. Almost all of it is small. But it is the difference between a very good
prototype and a thing someone can trust with a day's work, and right now a competent user's first
hour ends with a broken link, an example that won't play, a knob that does nothing, and an undo
that doesn't. **The fix list below is roughly two focused weeks. Ship 0.2 after that, not before.**

## Corrections to prior tiers

### C1 — "The manual is stale pessimistically" is wrong for two of its four flagship cases

Tier 1's pattern #3 ("the manual warns users off features that have since been fixed") is the
single most repeated cross-cutting claim in the review, and for the backend half of it, **the
manual is right and the reviewers were wrong** — because the app does not run the fixed code.

I generated `skald-backend/tests/fixtures/reverb_predelay.json` and `mixer_exposed_default.json`
with both binaries:

| Claim | `skald-backend/codegen.exe` (built from source, 2026-07-30) | `skald-ui/skald_codegen.exe` (what the app runs, committed 2026-07-24) |
|---|---|---|
| Reverb pre-delay implemented | 6 × `reverb_*_pre_buffer` emitted | **0** |
| Mixer exposed level preserves fader | `p.level1 = 0.250000000` | **`p.level1 = 1.000000000`** |
| `PARAMS` row default | `{"level1", 0, 2, 0.25, "x"}` | **`{"level1", 0, 2, 1.0, "x"}`** |
| Voice-steal anti-click | `adsr_*_attack_start` + `if !stolen` guard | **absent — unconditional hard reset** |
| `nodeId::param` alias | `case "level1", "mix::level1":` | **`case "level1":` only** |

Therefore:

- **F-A07-1** (high, "Reverb Pre-Delay now works — the manual's 'does nothing' claim is stale"):
  **overturned as stated.** Pre-Delay does nothing in the shipped app. `reverb.md`'s Code-vs-intent
  notes 1 and 2 and its "Try it" step 8 are *accurate*. Downgrade to medium and reframe: the fix is
  written but not delivered.
- **F-A08-1** (high, "Mixer's headline blocker is fixed in current code"): **overturned as stated.**
  Exposing a channel level still pins it to unity in the shipped app. `mixer.md` Code-vs-intent
  note 1 is accurate. Same reframe.
- **F-A10-3** (`60-complexity-ladder.md` pre-delay note is stale): **overturned**, same reason.
- **F-B09a**'s FIXED.md status table ("All 6 packets are genuinely in code"): **half-correct.**
  P2/P6/P10/P12 are frontend TypeScript and *are* live in the app; P1 and P3 are backend Odin and
  are **not**. The table needs a "in the source" / "in the product" column.
- Tier 1's fixes-that-are-genuinely-live in the app: P2 range alignment, P6 Piano Roll A0, P10
  Distortion `shape`, P12 tooltip/example metadata. Those doc-bug findings (**F-A06-3, F-A06-4,
  F-A09-1, F-A10-5, F-A10-6, F-A10-7, F-A02-1**) all stand unchanged.

### C2 — F-B05-1's diagnosis is right but its cause and fix are wrong

F-B05-1 found all checked-in `generated_audio.odin` copies stale and recommended a regeneration
discipline. I confirmed the staleness (0 × `attack_start` in all seven copies; 3 in
`tests/golden/adsr_sine.odin.golden`). But this is a **symptom, not the disease**: they are stale
because they were produced by the stale `skald-ui/skald_codegen.exe`, which is the same binary the
app uses. Regenerating the examples without fixing the binary reintroduces the drift on the next
export. Supersede its recommendation with F-C4-1 below.

### C3 — F-B08-5 and F-B01-6 are moot in the shipped build

F-B08-5 (worklet 64-byte vs shim 128-byte name-buffer mismatch) describes a latent trap in a live
parameter path that, in the committed app, **never succeeds for any key length**, because the
binary emits no `::` alias at all. Both findings remain correct against source and both become live
the moment F-C4-1 is fixed — sequence them after it, not before.

### C4 — Affirmed

- **F-B02-4** correctly overturns **F-A07-4**'s reachability claim: `renderBpmSyncToggle` has zero
  call sites; I re-grepped and confirm. F-A07-4's underlying bug stands, its "a user can and will
  click it" premise does not.
- **F-B04-1** (non-deterministic instrument ordering) verified independently: `json.odin:303` and
  `:331` both iterate `graph.nodes` (a `map[string]Node`) unsorted, while `graph_utils.odin:9-14`

- **F-B06-4**'s corpus count is now out of date in the other direction: I count **101** JSON files
  under `examples/`, not 94.

## Findings

### F-C4-1: The binary the application runs is 51 commits behind its own source, and nothing in the repo, the tests, or CI detects it

- **kind**: risk
- **area**: build chain / release engineering / product integrity
- **severity**: critical
- **confidence**: high
- **effort**: S
- **when**: 0.2-blocker
- **supersedes**: reframes F-A07-1, F-A08-1, F-A10-3; supersedes F-B05-1's recommendation
- **evidence**:
  - `skald-ui/src/main.ts:72-73` — the app spawns `path.join(app.getAppPath(), 'skald_codegen.exe')`
    (or `process.resourcesPath` when packaged) for **both** `build-wasm-preview` (`main.ts:253`) and
    Generate Code.
  - `.gitignore:2,7` — `*.exe` ignored, then `!skald-ui/skald_codegen.exe` un-ignored. `git ls-files`
    returns exactly one `.exe`: this one.
  - `git log -1 -- skald-ui/skald_codegen.exe` → `af6500c`, 2026-07-24 21:22.
    `git rev-list af6500c..HEAD --count` → **51**.
  - `git log -1 -- skald-backend/core/codegen.odin` → `9ab241c`, 2026-07-30.
  - Direct A/B, both binaries on `tests/fixtures/mixer_exposed_default.json` and
    `reverb_predelay.json`: see the table in *Corrections* above. 42–46 lines of diff on a
    ~300-line fixture.
  - `skald-ui/package.json:8` — `"start": "electron-forge start"`. `"make": "electron-forge make"`.
    Neither chains `build:codegen`. Only `start:rebuild`, `setup:dev` (`scripts/setup-dev.ps1:85`)
    and `release:win` (`scripts/build-release.ps1:80`) rebuild it.
  - `.github/workflows/ci.yml` — the backend job builds `codegen.exe` fresh inside
    `run_acceptance.bat`; **nothing anywhere compares it to the committed
    `skald-ui/skald_codegen.exe`**, runs the examples corpus, or packages the app.
- **detail**: A build artefact is under version control, is the thing the product actually executes,
  and has no freshness check. A first-time cloner who runs `setup-dev.ps1` is fine. Everyone else
  is not: anyone who pulls and runs `npm start` (the README's own documented Run step), anyone who
  runs `npm run make`, any reviewer or tester who opens the repo, and — silently — the committed
  state of the repository itself. The README acknowledges the hazard in the weakest possible form
  ("`npm start` uses the existing code generator. If you change the Odin backend, run
  `start:rebuild`"), which puts the burden on the user to notice that *someone else's* commit
  invalidated their binary. `git status` reports a clean tree while the tree ships a binary that
  produces demonstrably different audio from the source next to it.

  The consequences that reach a customer's game: exported instruments click on every voice steal;
  exposed Mixer channel levels are pinned to unity regardless of the fader the designer set; Reverb
  Pre-Delay is decorative. The consequence that reaches the editor is F-C4-2.
- **recommendation**: Delete `skald-ui/skald_codegen.exe` from git, remove the `!` un-ignore, and
  make it a build output. Add a `predev`/`prestart` and `premake` npm hook that runs
  `build:codegen`; Odin is already vendored at `.tools/`, and I measured a full CLI rebuild as
  sub-second, so there is no reason not to build it every launch. Then add the *real* safety net: a
  **version handshake**. Emit a build stamp (git SHA of `skald-backend/`) from `main.odin`'s
  `-version` flag, have `main.ts` read it once at startup, compare against a constant baked into
  the renderer at build time, and refuse to start the preview with a clear banner on mismatch. Add
  a CI job that builds the codegen CLI and asserts the committed binary either matches or does not
  exist.
- **manual impact**: none directly, but this finding invalidates the "stale manual" framing in
  `reverb.md` (Code-vs-intent 1-2, "Try it" step 8), `mixer.md` (Code-vs-intent 1) and
  `60-complexity-ladder.md` (Code-vs-intent 1) — those passages should be left alone until the
  binary is fresh, then removed.
- **migration**: none — no saved patch is affected.

### F-C4-2: In the shipped build, every exposed-parameter knob is inert during playback, and no rebuild compensates

- **kind**: code-bug
- **area**: live preview / parameter path
- **severity**: critical
- **confidence**: high (source-verified end to end; not observed in a running GUI)
- **effort**: S (falls out of F-C4-1)
- **when**: 0.2-blocker
- **evidence**: The chain, verified link by link:
  1. `useWasmAudioEngine.ts:249-259` — the instant path posts
     `nameBytes: TextEncoder().encode(liveParamKey(sn.id, name))`, i.e. always `"<nodeId>::<param>"`.
  2. `projectSerializer.ts:222` — `liveParamKey = (nodeId, param) => \`${nodeId}::${param}\``, used
     unconditionally; there is no bare-name fallback anywhere.
  3. Generated shim from the **shipped** binary:
     `skald_set_param :: proc "c" (asset, name_len, value) { ... case 0: return Asset_set_param(&wasm_Asset, name, value) ? 1 : 0 }`.
  4. Generated `Asset_set_param` from the **shipped** binary:
     `switch name { case "level1": ... }` — **no `"mix::level1"` case**. Returns `false`.
  5. `skaldWasm.worklet.ts` ignores the return value; no error is posted back.
  6. `projectSerializer.ts:236-248` — `topologySignature` sets `n.parameters[name] = null` for every
     exposed param that `canApplyParamLive` accepts, *precisely so it does not trigger a rebuild*.
     Its own comment states the invariant: "Masking and live-applicability MUST agree: a param
     masked here but skipped by the instant path would change nothing until an unrelated rebuild."
- **detail**: The invariant is enforced on the TypeScript side and silently violated by the binary.
  The user drags a filter cutoff while the preview plays. The UI updates. The sound does not change.
  No banner, no console error, no rebuild — the engine has concluded the edit already applied. It
  will appear to work again as soon as any *unmasked* change (adding a node, changing a waveform)
  forces a rebuild, which makes it read as intermittent rather than broken and is the worst possible
  failure shape for a user's trust.

  This is the core loop. "Edit → hear" is the whole product. In the committed app, for the specific
  class of edit that is supposed to be instant and glitch-free, it does not work.
- **recommendation**: Fix F-C4-1. Then close the hole permanently so a binary/UI mismatch can never
  be silent again: have the worklet check `skald_set_param`'s return value and post an error message
  back on `0`, and surface it as a preview banner. That single change would have caught this class
  of bug the day it appeared. Add an acceptance fixture that drives `skald_set_param` with a
  `nodeId::param` key and asserts the audio changes.
- **manual impact**: none.
- **migration**: none.

### F-C4-3: The first hour — 26 of 101 shipped examples cannot be played, and the Load dialog opens on them

- **kind**: design
- **area**: examples corpus / onboarding
- **severity**: high
- **confidence**: high
- **effort**: M
- **when**: 0.2-blocker
- **supersedes**: consolidates F-B06-5, W2/B1 (CODEX brief), F-B09a §Q2 item 3
- **evidence**:
  - I parsed all 101 `examples/**/*.json`: **26** have no top-level `"type": "instrument"` node.
    `useWasmAudioEngine.ts:96-98` throws `"No instruments on the canvas. Wrap nodes in an Instrument
    before playing."` for every one of them, and `app.tsx:415-439` renders it as a red *Preview
    failed* banner.
  - The list includes the two files the manual's own spine chapters open with:
    `instruments/leads/saw-lead.skald.json` (`00-foundations.md:280`) and
    `instruments/bass/sine-sub-bass.skald.json` (`50-bass-teardown.md` Exercise 1). `00-foundations.md:288`
    adds a "wrap it in an Instrument" step; `50-bass-teardown.md` does not, for Exercise 1, Exercise 2
    Rungs 0 and X, and Exercise 3 steps 1-8 — already correctly identified in
    `EDITORIAL-REPORT.md:286-288`.
  - `src/main/dialogDefaults.ts:107-110` + `forge.config.ts:20` — Load opens on `examples/`, and the
    whole tree including `examples/archive/` is copied into every packaged build.
  - `examples/archive/PulsarBeam.json` still hard-fails: I ran it and got
    `Error: instrument "Asset": connection into Delay(3) uses unknown input port "input_delayTime"`,
    exit 1. `examples/archive/README.md` says these files were "moved out of the import-facing
    library" — they were moved one folder up from where the dialog opens.
  - `examples/songs/loops/to implement/` still contains a file named
    `this wont be the final boss battle but I do want to put this into geowars for the boss and then play geowars with just the boss..json`,
    and it ships.
- **detail**: The first thing a new user does is open an example. One in four of them produces an
  error banner instead of sound, and the error is about a concept ("wrap it in an Instrument") the
  user has not met yet. The dialog opens on a directory that also contains a broken file, a folder
  literally named "to implement", and an "archive" folder the project believes it removed. This is
  the single most controllable first-impression surface in the product and it is unmanaged.
- **recommendation**: Three things, in this order. (1) **Auto-wrap on load**: if a loaded graph has
  no Instrument node, wrap it in one named after the file, with a one-line toast explaining what
  happened. `json.odin:309-326` already does exactly this on the backend for the CLI — the editor
  should match. This converts 26 broken files into 26 working ones for the cost of about 40 lines
  and simultaneously fixes three unperformable manual exercises. (2) Exclude `archive/` and
  `to implement/` from `extraResource` (a second narrower entry, or a build-time filter), and delete
  `PulsarBeam.json`. (3) Point Load at a curated `examples/start-here/` of 6-8 files chosen to be
  the best first thing a person hears, and leave the full library one folder up.
- **manual impact**: `50-bass-teardown.md` Exercises 1, 2 and 3 lose their unperformable steps
  entirely rather than needing corrective inserts. `00-foundations.md:288-290`'s wrap step becomes
  a teaching aside rather than a load-bearing instruction. `output.md:89-93` deliberately teaches
  the refusal and would need rewriting.
- **migration**: If auto-wrap is applied on load and the file is then saved, the file changes shape
  (a new Instrument node with the old graph as its subgraph). That is a real, desirable upgrade, but
  it must be gated on the schema-version field F-B06-12 says does not exist yet — build that first.

### F-C4-5: Trust — Load destroys the session in one click, and nothing in the app knows the session exists

- **kind**: code-bug
- **area**: file I/O / session model
- **severity**: critical
- **confidence**: high
- **effort**: M
- **when**: 0.2-blocker
- **supersedes**: merges F-B06-2 and F-B07-4 and extends both
- **evidence**:
  - `useFileIO.ts:114-136` — `handleLoad` replaces `nodes`/`edges` and then calls `setHistory([])`
    / `setFuture([])`. No prompt, no guard, no condition.
  - `app.tsx:375` — `onLoad={handleLoad}` wired straight to the sidebar button.
  - No dirty tracking exists: `grep -rn "isDirty|unsaved|beforeunload|document.title|setTitle"` over
    `skald-ui/src` returns only two unrelated code comments.
  - No autosave, no crash recovery: the only `localStorage` use in the codebase is
    `logger.ts:20`'s debug flag. `ErrorBoundary.tsx` catches render throws but the graph lives in
    React state, so a reload loses it.
  - The window has no title reflecting the open file; there is no recent-files list; `packageName`
    (`app.tsx:86`) does not round-trip through save/load (F-B06-11, confirmed).
- **detail**: Skald has no concept of "the project I am working on". It has a canvas, and Load
  overwrites it. There is no filename anywhere in the chrome, no asterisk, no "you have unsaved
  changes", no recovery file. A user an hour into a patch who mis-clicks Load — or who clicks it
  deliberately to peek at a reference patch, which is exactly what the manual repeatedly instructs
  — loses everything, and the undo stack that could have saved them is cleared by the same action.
  This is not a rough edge; it is the reason a professional will not put a day's work into this
  tool.

  Clearing history on Load is the correct decision (`app.tsx:147-148`'s comment is right). The
  defect is that it is the *only* safety mechanism the app has, and Load is the one action that
  removes it.
- **recommendation**: A single small workstream. (1) Track `dirty` — set on any mutation that pushes
  undo history, clear on successful Save. (2) Gate Load and Import behind
  `dialog.showMessageBox` when dirty. (3) Put the filename and a `•` dirty marker in the window
  title via `BrowserWindow.setTitle`. (4) Autosave the full `{nodes, edges, sequencerTracks,
  session}` blob to `app.getPath('userData')/recovery.json` on a 30-second debounce, and offer to
  restore it on next launch if it is newer than the last successful save. (5) Make Save atomic —
  `fs.writeFileSync(tmp)` then `fs.renameSync` (F-B06-3), so a failed overwrite cannot destroy the
  previous good file. Items 1-3 are half a day; 4-5 are another day.
- **manual impact**: `00-foundations.md:284`'s "Load replaces your canvas entirely … so save
  anything you care about first" becomes a description of a confirmation dialog rather than a
  warning the reader has to remember. Chapter 1 (F-C4-4) documents autosave/recovery.
- **migration**: none.

### F-C4-6: Undo is unreliable in seven distinct ways, and it is the app's only safety net

- **kind**: code-bug
- **area**: undo/redo
- **severity**: high
- **confidence**: high
- **effort**: M
- **when**: 0.2-blocker
- **supersedes**: consolidates F-B01-2, F-B01-3, F-B01-9, F-B07-1, F-B07-2, F-B07-3, F-B07-9,
  F-B09b-5; adds one new gap
- **evidence**: All re-verified in the current tree.
  1. **Two stacks, one keystroke.** `useGraphState.ts:39-40` and `useSequencerState.ts:9-39` are
     independent LIFO stacks; `app.tsx:209-219` pops both on every Ctrl+Z regardless of what the
     last action touched.
  2. **Node drags snapshot too late.** `useGraphState.ts:81-83` snapshots only on
     `position && !dragging`, by which time the closure's `nodes` already holds the second-to-last
     drag tick. Undo after a drag moves the node a few pixels.
  3. **Palette drop is untracked.** `useNodeComposition.ts:44-64` (`onDrop`) calls `setNodes`
     with no `saveStateForUndo()` — unlike every sibling in the same file (`:200`, `:217`, `:269`).
     This is the most frequent action in the editor.
  4. **Import Patch is untracked.** `useFileIO.ts:195-197` — same omission.
  5. **"Export Step to Instrument" is untracked** — *new, not in prior tiers*. `app.tsx:342` calls
     the raw `setNodes` exported by `useGraphState.ts:238`, bypassing history entirely. The action
     adds a whole cloned Instrument to the canvas and cannot be undone.
  6. **Transport controls have no undo.** `app.tsx:76,78,82` — `bpm`, `patternSteps`,
     `masterVolume` are plain `useState`, in neither stack.
  7. **Coalescing is wall-clock, not gesture-scoped.** `useGraphState.ts:57-64` — a 500 ms window
     with no per-control identity, so a long slow drag splits into several entries and two edits on
     different nodes within 500 ms merge into one.
  Plus `useSequencerState.ts:169-172` — `loadTracks` calls `saveHistory()` on file load instead of
  clearing, so sequencer-undo can revert to the *previous file's* tracks.
- **detail**: Given F-C4-5, undo is the only thing standing between a user and losing work. Three of
  the seven gaps mean the most common gestures in the editor produce no undo entry at all, so a
  user's mental model of "how many times do I press Ctrl+Z to get back" is never right. Prior tiers
  filed these as eight separate findings across three agents; they are one workstream and should be
  scoped as one.
- **recommendation**: Replace both stacks with one ordered history of
  `{nodes, edges, tracks, session}` snapshots behind a single `pushHistory(label)` API, and route
  every mutation through it — including the four currently-untracked call sites and the three
  transport fields. Snapshot on the *first* `dragging: true` tick, not the last. Coalesce by gesture
  identity (`CustomSlider`/`NumberInput` already know when they are focused) rather than by clock.
  Then add visible Undo/Redo buttons with enabled state reflecting real stack depth — currently the
  feature is discoverable only through the `?` legend. This is one to two days and it retires eight
  prior findings.
- **manual impact**: Chapter 1 documents undo scope honestly. `50-bass-teardown.md:326`'s "Undo"
  instruction becomes reliable.
- **migration**: none.

### F-C4-7: The core loop is survivable but not good, and one third of the latency is free to remove

- **kind**: qol
- **area**: preview build chain
- **severity**: medium
- **confidence**: high (timings measured on this machine)
- **effort**: S
- **when**: 0.2-desirable
- **supersedes**: extends F-B08-4 with measurements on real shipped content
- **evidence**: I ran the real toolchain (`skald-backend/codegen.exe` +
  `.tools/odin-dev-2025-02/.../odin.exe`) with the exact flags from `main.ts:253-261`:

  | Project | codegen | `odin -o:speed` | `odin -o:none` |
  |---|---|---|---|
  | `tests/fixtures/dual_osc.json` (1 instrument) | ~10 ms | **208 ms** | 104 ms |
  | `examples/snes-kit/demoforyoutube.json` (9 instruments, 4692 lines emitted) | 51 ms | **702 ms** | 172 ms |
  | `examples/snes-kit/songs/chase-loop.skald.json` (9 instruments) | 51 ms | **713 ms** | 174 ms |

  `main.ts:259` passes `-o:speed` — export-grade optimisation — for a preview module whose only
  real-time requirement is finishing one 128-sample render quantum. `REBUILD_DEBOUNCE_MS = 250`
  (`useWasmAudioEngine.ts:32`) is justified by a comment reading "measured build is ~200ms".
  There is **no `isBuilding` state anywhere** — `previewStale` only appears on *failure*, so a
  successful slow rebuild is indistinguishable from nothing happening.
- **detail**: On a real shipped song, a non-instant edit costs 250 ms debounce + ~750 ms build ≈ one
  full second with no feedback of any kind before the sound changes. Switching to `-o:none` for the
  preview path takes that to ~425 ms, a 2.2× improvement on the whole round trip, for a one-word
  change. Combined with the hot-swap killing sustained notes (F-B08-2, confirmed: `instantiate()`
  builds a fresh `WebAssembly.Instance` and `skald_start_all` only restarts Music Layer assets), the
  loop is: edit, a second of silence, and any note you were holding stops. That is workable for
  parameter tweaking (once F-C4-2 is fixed and that path is instant again) and unpleasant for
  structural editing.
- **recommendation**: (1) Change `-o:speed` → `-o:none` in `main.ts:259` for the preview path only;
  keep `-o:speed` for Generate Code. Verify with the acceptance suite that no fixture regresses.
  (2) Surface `isBuilding` from the engine and render a small "rebuilding…" pip near the transport —
  this is the difference between "slow" and "broken". (3) Track held notes in a
  `Map<asset, Set<note>>` and replay them after `instantiate()` succeeds, the same way
  `preserveTransport` already replays sequencer position.
- **manual impact**: none.
- **migration**: none.

### F-C4-8: The handoff to a game is the least finished part of the tool

- **kind**: design
- **area**: generated API / integration
- **severity**: critical
- **confidence**: high
- **effort**: M
- **when**: 0.2-blocker
- **supersedes**: consolidates F-A05-1, F-A05-8, F-B05-2, F-B05-3, F-B05-8
- **evidence**:
  - **The recommended path drops the mix and the limiter.** The generated header, verified in
    `examples/integration_demo/generated_audio/generated_audio.odin:18-19`, reads: *"project_init/
    process/destroy is a convenience wrapper for the test harness only — game code should consume
    per-asset procs directly."* `codegen.odin:2477-2478` puts `math.tanh(mixed * master_vol)` — both
    the authored master volume **and** the only clipping protection in the whole system — inside
    `project_process`. The shipped demo (`examples/integration_demo/main.odin:211-212`) therefore
    writes `l := (sfx_l + layer_l) * 0.6`, an unexplained literal with no relationship to the `0.8`
    the designer set in `_demo_project.json:4`.
  - **There is no runtime volume control.** `codegen.odin:2455-2456` bakes `master_vol` as a literal;
    no `set_master_volume` / `project_set_volume` symbol exists (`grep -rn set_bpm|set_master_volume
    skald-backend/core` → nothing). Ducking music under dialogue, distance attenuation, and a
    settings-menu slider all require the integrator to know, out of band, to insert and expose a VCA.
  - **A master volume of exactly 0 exports as full volume.** `codegen.odin:2456` —
    `if master_vol <= 0.0 do master_vol = 1.0`, and `projectSerializer.ts:110` sends `masterVolume`
    with no floor, unlike instrument volume at `:197-199` which is floored at 0.001 *for exactly
    this reason, with a comment saying so*.
  - **No thread-safety contract.** Every `<Foo>_set_<param>` is a plain unguarded field write; every
    `_process` reads the same field. No `sync`, `atomic` or `Mutex` anywhere in
    `skald-backend/core/`. Nothing in the header, the README, the demo, or the manual states which
    thread setters may be called from. The built manual contains **zero** occurrences of "thread".
  - **No documentation.** 21 manual chapters cover the graph editor; **zero** cover the artefact a
    game engineer receives. `examples/integration/` is an empty directory next to the populated
    `examples/integration_demo/`.
- **detail**: The boundary between the editor and the game is the entire reason Skald exists, and it
  is the part with no chapter, no thread contract, no runtime mix control, and a recommended
  integration pattern that silently discards two things the editor authored. A game team that
  follows Skald's own README verbatim ships audio that is louder than intended, unlimited against
  clipping across N simultaneous assets, and races on every parameter write from gameplay code.
  Meanwhile the parts that *are* well-built — allocation-free `_process`, sound note lifecycle, the
  typed-vs-string setter split — are invisible because nothing documents them.
- **recommendation**: Four things, all small, all 0.2.
  1. Emit `<Asset>_set_volume` and a project-level `skald_set_master_volume` writing a live `p.`
     field, and split gain from limiting: `mixed * vol` then a separate `skald_soft_limit(l, r)`
     proc the per-asset path can call after summing its own assets. This fixes F-A05-1, F-A05-8 and
     F-B05-2 together and makes the demo's `0.6` replaceable with something meaningful.
  2. Floor `masterVolume` client-side at `0.0001` in `projectSerializer.ts` (one line) *and* change
     the backend sentinel from `<= 0.0` to `< 0.0` so a real 0 can never be mistaken for an absent
     field.
  3. **Pick a thread contract and write it in the generated header.** The cheapest correct answer
     matching the demo's actual usage is "all `_set_*` calls must happen on the thread that calls
     `_process`" — one sentence, emitted by `codegen.odin:2313-2321`, plus a line in the README.
     Do not ship 0.2 without saying *something*.
  4. Write `EDITORIAL-REPORT.md`'s Chapter 25 ("Exporting Odin and wiring it into a game"). Extend
     the generated header to list each asset's exposed params and both ways to set them — the data
     is already computed at header-generation time (`codegen.odin:1691-1703`).
- **manual impact**: adds Chapter 25; `output.md`'s "What 'expose' means, and why Output has nothing
  to expose" and its "Give yourself a master fader your game can move" workaround both become
  obsolete; `00-foundations.md:421`'s "master volume is applied before the limiter … that is
  deliberate" needs restating once the two stages separate.
- **migration**: additive to the generated API; no `.skald.json` changes.

### F-C4-9: You cannot tell whether the `.odin` file in your game is current, and regenerating it can reshuffle your asset indices

- **kind**: code-bug
- **area**: codegen determinism / artefact provenance
- **severity**: high
- **confidence**: high
- **effort**: S
- **when**: 0.2-blocker
- **supersedes**: merges F-B04-1 and F-B05-7
- **evidence**:
  - `json.odin:303` and `:331` — `build_project_from_graph` iterates `graph.nodes`
    (`map[string]Node`, `types.odin:94`) unsorted to assign `project.instruments[idx]`, while
    `graph_utils.odin:9-14` carries an explicit comment: *"Odin map iteration order is unspecified
    and varies run-to-run … or the generated source is non-deterministic"*, and
    `codegen.odin:1046-1050` repeats it. `build_project_from_graph` is the one caller that ignores
    it. B04 reproduced three different asset orderings from three runs of the unmodified
    `four-bar-song.skald.json`; the asset index is what `skald_trigger(asset: i32, …)` switches on.
  - `codegen.odin:2283-2321` — the generated header carries package name and asset lists but no
    Skald version, no source hash, no timestamp. `main.odin:90-99` writes the target with a blind
    `os.write_entire_file`. A search for `schema_version|GENERATOR_VERSION` in the backend returns
    nothing.
  - `codegen.odin:956-965` + `:2251-2266` — the exported symbol prefix is the instrument's display
    name, sanitized. Renaming "Sfx" to "SFX" renames every public proc with no alias. Separately,
    un-exposing a parameter on node B changes the *field name* on untouched node A (`:1251-1258`,
    collision prefixing is recomputed from the current node set every run).
- **detail**: Three separate ways the artefact a game links against is unstable under regeneration:
  its asset indices can permute for no reason, its symbol names can change because of an unrelated
  edit, and it carries nothing that lets anyone answer "is this file current?" except regenerating
  and diffing — which, per F-C4-1 and F-B05-1, is exactly the step nobody performs.
- **recommendation**: (1) Replace both loops in `build_project_from_graph` with
  `nodes_sorted_by_id(graph)` — the helper already exists and every other pass uses it. One-line
  fix per loop, and it makes byte-for-byte golden testing of those fixtures possible. (2) Add a
  provenance line to the generated header: Skald version, codegen build stamp (the same one
  F-C4-1 needs), and a hash of the input JSON; and change the header's opening from descriptive
  prose to `// AUTO-GENERATED — do not edit; the next codegen run overwrites this file.` (3) Make
  field-name collision resolution stable per node (always suffix a node that has ever collided),
  so editing node B cannot rename node A's setter. Defer the rename-alias question (F-B05-4) to
  0.3 — it needs a stable per-instrument export name, which is a schema change.
- **manual impact**: Chapter 25 documents the provenance stamp and the regeneration contract.
- **migration**: (1) and (3) change generated symbol layout for some projects — a one-time
  find-and-replace for anyone already integrated, and it should be called out in the changelog.

### F-C4-14: Competitive position — what wins, what loses, and the pitch that is actually true

- **kind**: design
- **area**: product positioning
- **severity**: medium
- **confidence**: medium
- **effort**: S
- **when**: 0.2-desirable
- **evidence**: synthesis of the above plus the node palette (`Sidebar.tsx:264-280`, 18 types),
  the generated API surface (`examples/integration_demo/generated_audio/generated_audio.odin`), and
  `codegen.odin`'s allocation-free `_process` (no `new`/`make`/`append` in any generated process
  path, confirmed by B05 and spot-checked here).
- **detail**:

  **What would make someone choose Skald today, honestly:**
  1. **It generates source, not a runtime.** No middleware licence, no `.bank` files, no
     integration SDK, no DLL. You get one `.odin` file with allocation-free `_process` procs you can
     read, step through in a debugger, and modify. For a solo or small team shipping an Odin game,
     that is a genuinely differentiated proposition that FMOD and Wwise structurally cannot offer.
  2. **Procedural audio that is actually procedural.** A `.wav` from a DAW is 400 KB and one sound.
     A Skald instrument is a few KB of code that responds to note, velocity, and exposed parameters
     at runtime. For sounds that need to vary — engines, weapons, footsteps, adaptive music layers —
     this is the right shape.
  3. **The manual.** Once it is shipped, it is the best explanation of "what does this knob do to
     the samples" I have seen attached to a tool of this size. It teaches synthesis, not just
     Skald. That is a real reason to pick it over a DAW for someone who does not already know
     synthesis.
  4. **Preview *is* the export** — architecturally. The old hand-maintained Web Audio mirror is
     gone; the editor compiles and runs the same Odin the game gets. Once F-C4-1 and F-B08-1 are
     fixed, that claim becomes true, and it is a strong one.

  **What would make someone put it down in the first hour, in the order they will hit it:**
  1. A README whose two links 404 (F-C4-4).
  2. Loading an example and getting a red error banner instead of sound — one in four chance
     (F-C4-3).
  3. Dragging a knob during playback and hearing nothing change (F-C4-2).
  4. Losing an hour of work to a mis-clicked Load, or to an undo that did not undo (F-C4-5,
     F-C4-6).
  5. Getting to the end, exporting, and discovering there is no way to change the volume at runtime
     and no statement about which thread they may call setters from (F-C4-8).

  **The pitch is currently too broad.** "Build audio instruments, sound effects, and songs with a
  node graph" invites comparison with a DAW and with Wwise, and Skald loses both comparisons on
  breadth: mono-with-a-terminal-pan-stage, no compressor, no EQ, no chorus, no stereo effects, no
  band-limiting, no per-edge modulation depth, no runtime mix. The honest, winnable pitch is
  narrower: **"Procedural sound effects and adaptive music for Odin games, as source you own."**
  Lead with the code output and the zero-runtime story. The songwriting features are real but they
  are not what makes Skald better than the alternative.
- **recommendation**: Rewrite the README's opening paragraph and the release notes around the
  code-generation story. Ship `EDITORIAL-REPORT.md`'s Chapter 24 ("What Skald deliberately does not
  do") — a tool that states its boundaries confidently reads as designed; one that leaves the user
  to discover them reads as unfinished. Do not add a compressor/EQ/chorus (F-B10-4) for 0.2; state
  their absence instead.
- **manual impact**: adds Chapter 24; `00-foundations.md`'s framing gains an explicit scoping
  section (the mono-with-terminal-pan decision per F-B10-3).
- **migration**: none.

## Is Skald 0.2-releasable?

**No.** Not because of the 199 findings, most of which are correct and none of which are individually
disqualifying. It is not releasable because the artefact the user runs is not the artefact the tests
test, and as a direct consequence the central interaction of the product — turn a knob, hear the
change — does not work in the committed build.

### The shortest honest path to 0.2

Roughly **two focused weeks**. Everything below is a blocker; nothing below is architectural.

**Week 1 — make the product be the code (≈5 days)**

1. **F-C4-1** — remove `skald_codegen.exe` from git; build it on `prestart`/`premake`; add a version
   handshake between the renderer and the binary. *(1 day)* — this alone flips F-C4-2, F-B05-1,
   and the P1/P3 fixes from "written" to "delivered".
2. **F-C4-2** — have the worklet check `skald_set_param`'s return and surface a banner on false;
   add an acceptance fixture driving a `nodeId::param` key. *(half day)*
3. **F-C4-12** — three CI jobs: examples corpus (codegen + `odin check`), binary freshness,
   `npm run make` + integration-demo smoke. *(1 day)*
4. **F-C4-9** — sort `build_project_from_graph`'s two loops; add a provenance stamp and an
   AUTO-GENERATED banner to the header; stabilise collision-suffix naming. *(1 day)*
5. **F-C4-8 items 1-3** — runtime master/instrument volume setters, split gain from the limiter,
   floor `masterVolume`, write the thread contract into the generated header and the README.
