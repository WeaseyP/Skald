## Summary

- The manual's headline claim — "**The preview is the export**... What you hear is what ships" (`00-foundations.md:221`) — does **not** hold for the one control every session touches: Master Volume. The live preview permanently bakes `master_volume = 1.0` into the compiled wasm's limiter and instead applies the dock's Master Volume slider as a *post-limiter* JS `GainNode`, while the export bakes the real value *pre-limiter*. These are different functions (`vol·tanh(x)` vs `tanh(vol·x)`), and the manual itself documents the pre-limiter behaviour as "deliberate" (`00-foundations.md:421`) — a property the live editor cannot demonstrate. This is the single highest-value finding in this audit (F-B08-1).
- I empirically measured the edit→rebuild→hear loop rather than just reading it: a trivial 1-instrument patch rebuilds its wasm module in ~170ms, but a patch with 24 instruments at voice/unison settings well inside the sliders' allowed range (16 voices, 7-way unison — max is 32/16) takes **~1.4s per rebuild**, 8× the code's own "~200ms" assumption behind the 250ms debounce (F-B08-4). Building the exact same output at `-o:none`/`-o:minimal` instead of the `-o:speed` the preview currently uses takes ~250ms — `-o:speed`'s extra optimisation time buys nothing for a preview that only needs to clear one ~2.9ms render-quantum budget, and there is no "rebuilding…" indicator anywhere in the UI to tell a user their edit registered during that gap.
- Hot-swapping the wasm module on a topology edit while playing constructs a brand-new `WebAssembly.Instance` from scratch. `skald_start_all()` only restarts sequenced (Music Layer) assets — it does not know about, and cannot restore, any currently-sustained MIDI-held note or audition trigger. Editing an unrelated node while holding a chord silently kills that chord until you release and re-press (F-B08-2). The same swap also performs a **synchronous** `WebAssembly.Module`/`Instance` compile directly inside the audio-thread message handler (F-B08-3) — real allocation and real compile work on the render thread, on every hot-swap.
- A live-param addressing contract is broken and untested-for-real: the worklet hard-rejects `set-param` names longer than 64 bytes with a comment claiming that's "the generated shim's skald_name_buf size" — but the actual generated buffer is `[128]u8` (`codegen.odin:2530`), and `projectSerializer.ts` already assumes 128 when deciding whether an edit is live-appliable. A param key in the 65–127 byte range is masked out of the topology signature (so no rebuild fires) *and* silently dropped by the worklet (so nothing plays either) — a genuinely inert control, currently low-probability given today's short auto-generated node IDs, but a real latent trap, and the unit test for this path (`WasmWorkletGuard.test.ts`) bakes in the wrong 64-byte number too, so CI will not catch a future ID-scheme change that makes it common (F-B08-5).
- The good news: the things Tier-1-adjacent testing already worried about are solid. Build failures during playback correctly leave the previous module running and surface a visible, actionable `previewStale`/`previewError` banner; a fast double-Play is latched to one build; a Stop that lands mid-build tears down cleanly; and a burst of edits during an in-flight build correctly collapses to one queued rebuild of the *latest* graph, not a stale one (`WasmEngineContract.test.tsx`). No Odin installed produces a clear, surfaced error rather than silent failure.
- Smaller items: `process()` allocates two new `Float32Array` views every render callback instead of reusing them (F-B08-6); nothing anywhere measures or surfaces real-time CPU headroom / xruns, so a patch heavy enough to miss its render deadline fails with only audible crackle and no diagnostic (F-B08-7, extends `F-A09-9`); the Odin-missing probe isn't cached on failure and uses blocking `spawnSync` calls that would stall the *entire* Electron main process (all IPC, not just audio) if a candidate ever hangs rather than fast-failing (F-B08-8); and the oscilloscope sizes its time-domain buffer using `frequencyBinCount` instead of `fftSize`, silently halving the waveform window it draws (F-B08-9).

## Findings

### F-B08-1: Master Volume behaves differently in the live preview than in the exported game — the manual's own "deliberate" design claim cannot be verified in the editor
- **kind**: code-bug
- **area**: WASM preview engine / master bus
- **severity**: high
- **confidence**: high
- **evidence**: `useWasmAudioEngine.ts:92-95` — `buildProjectData(nodes, edges, sequencerTracks, bpm, 1.0, patternSteps, nearestInScale)`: the preview build **always** bakes `master_volume = 1.0`, with the comment "the dock's volume slider drives the JS master GainNode live instead, so volume moves don't force a recompile." `SequencerDock.tsx:101-117` then applies the real `masterVolume` state via `masterGainNode.gain.setValueAtTime/setTargetAtTime`, and `useWasmAudioEngine.ts:191-196` wires that gain node **after** the AudioWorkletNode (`node.connect(masterGain); masterGain.connect(analyser); analyser.connect(context.destination)`). Meanwhile `codegen.odin:2455-2456,2475-2478` (export `project_process`) and `codegen.odin:2658-2665,2683-2684` (preview's own `generate_wasm_shim_code`, whose comment literally says "identical policy to project_process ... so the preview IS the export") both compute `tanh(mixed * master_vol)` where `master_vol` comes straight from `project.master_volume` — i.e. from whatever was actually serialized, which for preview is the hardcoded `1.0`, not the dock's slider value. The manual documents the pre-limiter placement as intentional: "master volume is applied before the limiter, so turning it down reduces saturation as well as level. That is deliberate" (`00-foundations.md:421`), citing this exact code.
- **detail**: `vol·tanh(x)` (what preview actually plays) and `tanh(vol·x)` (what export actually plays, and what the manual describes) are different functions except at `vol = 1`. In the shipped game, pulling Master Volume down reduces how hard the limiter squashes the mix — the manual's whole point in the "gain staging" walkthrough. In the live editor, pulling the same dock slider down just linearly attenuates whatever saturation the mix already produced at unity gain; the character of a loud, squashed mix never changes, only its loudness. A user who dials in a "quieter but clearer" master level by ear in the editor will hear a *louder but still squashed* result in the exported build (since export re-applies the real, lower master_vol pre-limiter and reduces saturation as advertised) — the two disagree in the specific way the brief calls out as the highest-severity divergence class: same graph, same slider value, different sound. Both the reason for the shortcut (avoiding a recompile on every volume drag) and the reason it's wrong (it silently defeats the deliberately-chosen signal order) are visible in the code's own comments.
- **suggested fix**: Give the master limiter the same "instant param" treatment already built for exposed node parameters: expose `master_volume` as a live `skald_set_param`-style target in the wasm shim (a single scalar, trivial to add to the generated `Project_State`/shim) so the dock slider updates it in place without a recompile, instead of routing it around the compiled DSP entirely. That removes the JS `GainNode` workaround and its divergence in one move.

### F-B08-2: Hot-swapping the wasm module while playing silently kills any currently-sustained note (MIDI hold, audition) with no resume
- **kind**: code-bug
- **area**: WASM preview engine / audio worklet
- **severity**: high
- **confidence**: medium
- **evidence**: `skaldWasm.worklet.ts:70-92` (`instantiate`) always builds a brand-new `WebAssembly.Instance` and re-initializes every asset's processor state (`ex.skald_init(sampleRate)`), then calls `ex.skald_start_all()` and, only if `preserveTransport`, re-seeks each asset's **sequencer step position** from the single `stepAsset`'s prior step/wait (`skaldWasm.worklet.ts:71-76,82-85`). `codegen.odin:2547-2555` shows `skald_start_all` only restarts `Music_Layer` (auto-sequenced) assets — it has no concept of "notes currently held via MIDI or the audition trigger" to restore. `useWasmAudioEngine.ts`'s MIDI listener (`359-406`) and audition handler (`340-353`) only ever send `note-on`/`trigger` in response to a live user action; nothing re-sends a `note-on` for a still-held key after a `swap` message (`useWasmAudioEngine.ts:279-318`, the `scheduleRebuild` path).
- **detail**: Hold a chord on a MIDI keyboard (or trigger a long audition), then tweak any parameter that isn't on the instant-apply exposed-param path (e.g. change an oscillator's waveform, add a node, change a filter's type) — the debounced rebuild swaps in a module whose processors start silent, and the held notes simply stop sounding until you release and re-press. To a user this looks exactly like "editing my filter cut my bass note," with no error, banner, or explanation, because from the engine's point of view nothing failed — the rebuild succeeded, previewStale stays clear, and the graph on screen is correct; only the live voice state was discarded. The secondary transport detail compounds this on multi-track patterns: the reseek in `instantiate()` applies **one** asset's `(step, wait)` pair to every asset's `skald_seek`, so if any sequenced asset had drifted from the "step asset" used for the UI playhead (e.g. started later, muted/unmuted mid-pattern), a hot-swap silently resyncs it to the wrong asset's position (lower confidence — Skald's single global `pattern_steps` makes this a narrow edge case in practice, but the code has no per-asset seek).
- **suggested fix**: Track currently-sounding notes per asset in the engine (a simple `Map<asset, Set<note>>` updated on note-on/off/trigger) and replay them against the freshly-swapped instance immediately after `instantiate()` succeeds, the same way `preserveTransport` already replays sequencer position. At minimum, surface this as a known limitation ("live edits restart currently-held notes") so it reads as expected behaviour rather than a bug.

### F-B08-3: Hot-swap compiles the new WebAssembly module synchronously on the audio-rendering thread
- **kind**: perf
- **area**: audio worklet / real-time safety
- **severity**: medium
- **confidence**: medium
- **evidence**: `skaldWasm.worklet.ts:70-92` — `instantiate()` runs `new WebAssembly.Module(bytes)` and `new WebAssembly.Instance(module, this.imports())` directly, and is invoked synchronously from `handleMessage`'s `'swap'` case (`skaldWasm.worklet.ts:103-105`), which is the `AudioWorkletProcessor`'s `port.onmessage` handler — code that Web Audio explicitly runs on the same rendering thread as `process()`, interleaved between render quantums rather than on a separate thread. The comment at `skaldWasm.worklet.ts:64-69` acknowledges the compile happens "on the audio thread" and defends it only on the grounds that "preview modules are tiny" — a claim contradicted by F-B08-4's own measurement (176KB+ for a moderately-sized patch).
- **detail**: If a `WebAssembly.Module` compile-plus-instantiate ever takes longer than the render-quantum budget (128 samples, ~2.9ms at 44.1kHz) on a given hot-swap, the next `process()` call is delayed and the output buffer underruns — an audible click or dropout exactly at the moment of a live edit, for exactly the size of patch (large graphs) where this is most likely to bite. I could not measure in-browser wasm compile time directly in this environment, hence medium rather than high confidence, but the code's own reasoning ("preview modules are tiny") is already shown to be an unsafe assumption by the empirical build-time scaling in F-B08-4.
- **suggested fix**: Compile the new module off the audio thread (e.g. `WebAssembly.compile`/`instantiate` on the main thread or in a separate worker, transferring only the compiled `WebAssembly.Module` — noting this reopens the structured-clone issue the code's own history already fought (`useWasmAudioEngine.ts:85-90`), so the fix needs to either use `WebAssembly.compileStreaming` results proven cloneable, or accept the audio-thread compile but measure and cap it, backing off to keep the previous module if compile time approaches the render-quantum budget.

### F-B08-4: Rebuild latency scales far past the code's own "~200ms" assumption as patch size grows, and `-o:speed` buys nothing for preview
- **kind**: perf
- **area**: build chain (`main.ts` buildWasmPreview)
- **severity**: medium
- **confidence**: high
- **evidence**: `useWasmAudioEngine.ts:30-32` sizes `REBUILD_DEBOUNCE_MS = 250` on the comment "measured build is ~200ms." `main.ts:255-261` passes `-o:speed` to `odin build ... -target:freestanding_wasm32 ... -o:speed` for **every** preview rebuild, identical to the export-quality optimisation level. I reproduced the actual toolchain (the repo's own `skald_codegen.exe` + the Odin compiler at `C:\Odin\odin.exe`) against `skald-backend/tests/fixtures/dual_osc.json` (1 instrument) and a generated 24-instrument variant of the same fixture with `voice_count: 16, unison: 7` — well inside the sliders' allowed ranges (max 32 voices / 16 unison, `param_ranges.odin`). Results: the 1-instrument build compiles to wasm in ~170ms; the 24-instrument build takes **~1.4s at `-o:speed`**, versus **~250ms at `-o:none`/`-o:minimal`** for the identical source — i.e. `-o:speed` alone accounts for ~5.6× of that gap, for a preview module whose only real-time requirement is finishing one ~2.9ms render quantum in time, not running at export-grade speed.
- **detail**: Any edit that isn't on the instant exposed-param path (adding a node, changing a filter type, changing voice/unison counts, anything the topology signature treats as a real change) forces this full codegen+compile round-trip. For any patch of realistic size, a user waits over a second per non-trivial edit — well past the "live" feel the 250ms debounce was tuned for — and, worse, there is no in-UI indicator that a rebuild is in flight at all: only `previewStale` (shown on *failure*) exists; a slow but eventually-successful rebuild is invisible, so a user has no way to tell "my edit is being applied" from "nothing happened" during that gap.
- **suggested fix**: Use a faster optimisation level (`-o:none` or `-o:minimal`) for the live-preview build specifically, reserving `-o:speed` for the explicit Generate/export path where runtime performance in the shipped game actually matters; this alone should recover most of the ~5.6× gap. Separately, expose an `isBuilding` state from the engine and show a lightweight "rebuilding…" indicator so edits during a longer rebuild read as in-progress rather than silently ignored.

### F-B08-5: Live-param name-buffer size is inconsistent between the worklet (64 bytes) and the actual generated buffer (128 bytes) — and the test suite bakes in the wrong number
- **kind**: code-bug
- **area**: WASM preview engine / live parameter path
- **severity**: medium
- **confidence**: high
- **evidence**: `codegen.odin:2530` emits `skald_name_buf: [128]u8` — the real, generated buffer size. `projectSerializer.ts:224-228` correctly derives its live-applicability check from this: `const MAX_PARAM_KEY_BYTES = 128;` with the comment "the generated wasm shim's param-name mailbox is 128 bytes." But `skaldWasm.worklet.ts:106-111` hard-codes the opposite number: `if (!this.ex || !m.nameBytes || m.nameBytes.length === 0 || m.nameBytes.length > 64) break;`, with a comment claiming "64 = the generated shim's skald_name_buf size" — which is simply false; there is only one such buffer in the codebase and it is 128 bytes. `topologySignature` (`projectSerializer.ts:236-248`) masks out any exposed-param value where `canApplyParamLive` (the 128-byte check) says the edit will apply live. `WasmWorkletGuard.test.ts:1-8,58-76` tests and asserts the worklet's 64-byte cutoff directly, so this wrong number is locked in by a passing test rather than caught by one.
- **detail**: For a `"<nodeId>::<param>"` key between 65 and 127 bytes (encodable and accepted by the real wasm buffer, and already treated as "live" by `topologySignature`'s masking), the actual sequence is: the value is masked out of the topology signature (no rebuild scheduled, because the engine believes the edit applies live) → `sendChangedExposedParams` posts a `set-param` message → the worklet's `> 64` check silently `break`s with **no error posted back**. The result is a control that visibly changes in the UI and produces literally no change in either the currently-playing preview or any future rebuild (since the signature keeps masking it) — an inert control with no warning, exactly the "control that lies about what it does" class the brief marks high-severity. Today's auto-generated node IDs (`Date.now().toString(36) + Math.random().toString(36).substr(2,5)`, ~13 chars) keep most real keys well under 64 bytes, which is why this hasn't been observed, but the 64/128 mismatch is unambiguous and only one of the two numbers can be correct.
- **suggested fix**: Change the worklet's cutoff from `64` to `128` (or better, read `skald_name_buf`'s actual length from an exported constant instead of hard-coding either number in two places), and update `WasmWorkletGuard.test.ts` to assert against the real buffer size so a future regression fails the test that's supposed to guard it.

### F-B08-6: `process()` allocates two fresh typed-array views every render callback instead of reusing them
- **kind**: perf
- **area**: audio worklet
- **severity**: low
- **confidence**: high
- **evidence**: `skaldWasm.worklet.ts:146-153` — every call to `process()` (once per 128-sample render quantum, hundreds of times per second) does `out[0].set(new Float32Array(this.ex.memory.buffer, this.leftPtr, n))` and the same for the right channel, constructing two brand-new `Float32Array` view objects each time rather than reusing cached views.
- **detail**: These are lightweight view objects, not buffer copies, so the cost is small, but it is nonetheless a heap allocation inside the real-time audio callback — exactly the category the brief asks to check for. `leftPtr`/`rightPtr` only change on `instantiate()` (initial construction or a hot-swap), so the views can be safely cached and only reconstructed at those points.
- **suggested fix**: Cache `this.leftView`/`this.rightView` alongside `leftPtr`/`rightPtr` in `instantiate()`, and have `process()` reuse them (recreating only if the underlying `ArrayBuffer` has been detached/regrown, which freestanding wasm32's static memory here should not do).

### F-B08-7: No real-time CPU headroom, xrun, or voice-budget signal anywhere — a patch can silently exceed the render-quantum budget with only audible crackle as feedback
- **kind**: risk
- **area**: audio worklet / project-wide
- **severity**: medium
- **confidence**: medium
- **evidence**: `skaldWasm.worklet.ts:146-166`'s `process()` has no timing instrumentation of any kind — no measurement of how long `skald_process(n)` took relative to the quantum's real-time budget, no counter surfaced to the port, nothing. I found no CPU meter, xrun counter, or voice-budget UI anywhere under `skald-ui/src/components` (consistent with Tier 1's `F-A09-9`, which found no project-level polyphony/CPU summary at all). Per-instrument `voice_count` (1-32) and `unison` (1-16, oscillator-only, multiplicative) are configured in isolation per instrument with no aggregate check.
- **detail**: This extends `F-A09-9` from the design-visibility angle to the real-time-safety angle: even if a summary view existed, nothing today would tell a user their *actual* patch is too heavy for one CPU core to render in time until it audibly glitches — in the preview identically to the exported game, since (per the manual's own promise) both run the same generated code. There is no adaptive behaviour (voice culling, quality reduction) and no diagnostic distinguishing "your patch is too heavy" from any other cause of crackle (a genuinely different failure mode from the debounced-rebuild glitches in F-B08-2/3).
- **suggested fix**: Have the worklet measure wall-clock time spent in `skald_process()` per quantum (cheap — one `performance.now()`-equivalent pair) and post a lightweight running "CPU load %" / xrun-count message the UI can render next to the transport controls; this is useful independent of, and cheaper than, a full static voice-budget estimate.

### F-B08-8: Failed Odin lookups are never cached and use blocking `spawnSync`, which can stall the entire Electron main process, not just the audio path
- **kind**: risk
- **area**: build chain (`main.ts`)
- **severity**: low
- **confidence**: medium
- **evidence**: `main.ts:175-191` — `findOdin()` caches `cachedOdinPath` **only** on success ("caching a miss would keep saying 'not found' after the user installs Odin mid-session," per its own comment); every failed Play or rebuild re-runs the full candidate probe. Each candidate is probed with `spawnSync(candidate, ['version'], { timeout: 10_000 })`, and `spawnSync` blocks the calling thread — here, the single Node.js event loop that is the entire Electron main process, which also services every other `ipcMain.handle` in the app.
- **detail**: When Odin genuinely isn't installed, `spawnSync` on a nonexistent executable fails immediately (ENOENT) rather than waiting out the timeout, so in the common case this is harmless. But if any candidate *resolves* to something that hangs (a stuck antivirus scan holding the file, a same-named unrelated binary that never exits, a network-mounted PATH entry that stalls), each of up to three candidates can block the main process for its full 10s timeout — up to 30s where the whole app (menus, dialogs, any other pending IPC) is unresponsive, repeated on every single Play attempt since the miss is never cached.
- **suggested fix**: Cache a negative result too, with a short TTL (e.g. 5-10s) or an explicit "recheck" trigger (e.g. window refocus) instead of caching misses forever — this keeps the "install Odin mid-session" case working while removing the always-re-probe-on-every-click behaviour, and consider `spawnSync`'s replacement with an async `spawn` + timeout so a hang degrades one IPC call instead of the whole process.

### F-B08-9: Oscilloscope buffer is sized from `frequencyBinCount`, not `fftSize` — the drawn waveform window is half what it should be
- **kind**: code-bug
- **area**: Visualization (AudioVisualizer)
- **severity**: low
- **confidence**: medium
- **evidence**: `AudioVisualizer.tsx:34-36` — `const bufferLength = analyser.frequencyBinCount; const dataArrayTime = new Uint8Array(bufferLength); const dataArrayFreq = new Uint8Array(bufferLength);`, then `analyser.getByteTimeDomainData(dataArrayTime)` at line 40. `frequencyBinCount` is `fftSize / 2` (1024 for the `fftSize = 2048` set in `useWasmAudioEngine.ts:193`); the Web Audio API's documented convention for `getByteTimeDomainData` sizes the destination array from `fftSize`, not `frequencyBinCount` (the frequency-domain methods are the ones sized from `frequencyBinCount`, since a real FFT's usable output is half its window).
- **detail**: This doesn't throw or crash — the API silently uses as much of the array as fits — but it means the oscilloscope only ever plots half of the analyser's actual time-domain window, effectively showing a twice-as-zoomed-in, truncated waveform compared to what a correctly-sized buffer would draw. Purely cosmetic (no audio is affected, and no test covers this component), but easy to fix and worth doing before any manual chapter cites the visualiser's output.
- **suggested fix**: Size `dataArrayTime` from `analyser.fftSize` (a separate `Uint8Array(analyser.fftSize)`), keeping `dataArrayFreq` sized from `frequencyBinCount` as it already correctly is.
