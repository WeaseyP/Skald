## Summary

- Tier 1 found the same bug independently on LFO (F-A03-1/2/7), Sample & Hold (F-A03-2/8) and
  Delay (F-A07-4/5): `bpmSync` selects, **at codegen time, from raw JSON**, which of two
  mutually-exclusive Odin expressions gets emitted for the node's rate — but the generic,
  name-keyed exposure pass (`codegen.odin:1216-1283`) has no idea `bpmSync` exists, so it happily
  emits a struct field, a typed setter, a `_PARAMS` row and a P-lock target for the free-run
  parameter regardless. This audit confirms that is the single root cause, traces it one level
  further than Tier 1 did (into the P-lock/sequencer-automation path, and into the live preview's
  own instant-apply mechanism, not just the exported public API), and finds one dormant piece of
  backend code (`param_ranges.odin`'s unreachable `"bpm"` case) that suggests project-tempo
  runtime exposure was once anticipated and never finished.
- BPM itself (the project-level tempo) is architecturally sound: exactly one owner
  (`app.tsx`'s `bpm` state), one write path (`clampBpm`), one serializer
  (`buildProjectData`/`projectSerializer.ts`) feeding both preview and export, and — verified
  directly — the sequencer's step clock, note-duration formula, and every `bpm_sync_seconds_expr`
  consumer (LFO/S&H/Delay) agree on the *same* seconds-per-beat arithmetic, so a "1/8" division
  means the same duration everywhere it appears (F-B02-8). The bug is entirely in the per-node
  sync/free-run duality, not in tempo propagation.
- `docs/proposals/bpm-ux.md` is accurate and its "Implemented now" fixes are real, but it is
  scoped to *communicating* BPM correctly (NaN guards, shared option lists, one clamp, a
  time-annotation) and never once touches the dead-parameter bug — it treats the
  `bpmSync`+`syncRate` "relationship" mechanism itself as a given, not as something to audit. A
  reader could reasonably conclude BPM-sync is done for 0.2; it is the single biggest open item
  in this scope (F-B02-6/F-B02-7).
- One Tier 1 disagreement resolved: F-A07-4 (Delay/Reverb, agent A07) states a user "can and will"
  click a link icon to expose Delay's BPM Sync; F-A03-4 (LFO/S&H, agent A03) found that click
  path (`renderBpmSyncToggle`) is dead code. Re-checked directly: `renderBpmSyncToggle(` has
  **zero call sites** anywhere in `ParameterPanel.tsx`, for any node type. F-A03-4 is right;
  F-A07-4's premise about *how* a user reaches the bug is wrong, though the underlying dead-param
  danger it describes is still real for anyone who reaches it another way (F-B02-4).
- Recommended fix (F-B02-6): stop baking the sync/free-run *choice* at build time. Make `bpmSync`
  a real runtime-checked field (bool-as-f32, with a proper `{0,1,0}` range instead of the ±1e6
  fallback) and always emit both expressions gated by a runtime `if`, so the exposed setter for
  `frequency`/`rate`/`delayTime` is never structurally dead, P-locks on it are never structurally
  dead, and — combined with a UI-side live-recompute of the stored free-run value whenever synced
  — the free-run number can never go stale relative to its own sync division either. One fix,
  shared across LFO/S&H/Delay.

## Findings

### F-B02-1: The exposure-resolution pass is structurally blind to `bpmSync` — this is the one root cause behind three separate Tier-1 findings
- **kind**: code-bug
- **area**: BPM sync / exposure system (LFO, Sample & Hold, Delay)
- **severity**: high
- **confidence**: high
- **evidence**: `skald-backend/core/codegen.odin:1216-1283` (`Phase 3: Exposed-parameter resolution` — walks `effective_exposed_params` for every node, calls `lookup_param_range(p_name, node.type)` and `exposed_param_default`, and builds a struct field + setter + `_PARAMS` row purely keyed on parameter *name* and node *type*; nothing in this pass reads `node.parameters["bpmSync"]`). Contrast with `bpm_sync_seconds_expr` (`codegen.odin:35-58`) and its three call sites (`generate_lfo_code:372-374`, `generate_sample_hold_code:398-400`, and the Delay generator's equivalent) which *do* read `bpmSync` from the same raw JSON, but only to pick which string gets substituted into the per-sample expression — a decision made once, at codegen time, entirely independent of Phase 3's exposure emission.
- **detail**: This is the mechanism underneath F-A03-1, F-A03-2 and F-A07-4 (all already filed as high-severity code-bugs on the individual nodes). It is filed here as its own finding because the fix belongs at this layer, not at three call sites: any future BPM-synchronizable node (an Arpeggiator, a synced Gate, a tremolo) will reproduce the identical bug the moment it's added, because nothing about the architecture prevents it — the exposure pass simply has no concept of "this parameter is sometimes structurally unused."
- **suggested fix**: see F-B02-6 for the full recommended architecture. Minimally: `effective_exposed_params` (or a new pass just before it) should drop the free-run parameter name from a node's effective exposure list whenever `bpmSync` resolves `true` at codegen time, and should error loudly (matching the existing P-lock "no matching node" error style at `codegen.odin` `collect_plock_targets`) if a P-lock targets it anyway — turning today's three silent no-ops into either "doesn't exist" (compile-time, loud) or "always works" (F-B02-6), never "exists and lies."

### F-B02-2: BPM sync's silent-no-op reach extends into the sequencer's own P-lock automation, not just the exported public API
- **kind**: code-bug
- **area**: BPM sync × Sequencer P-locks
- **severity**: medium
- **confidence**: high
- **evidence**: `effective_exposed_params` (`codegen.odin:971-999`) unions the UI's `exposedParameters` array with every P-lock target collected by `collect_plock_targets`, with no distinction between the two sources — a P-lock is just another way to land in the same `resolutions` map Phase 3 builds (F-B02-1). `resolve_plock_targets`/`collect_plock_targets` resolve a step override's key to `{node_id, param}` purely by name match against the node's real fields; there is no check anywhere in that path for whether the target is currently sync-overridden.
- **detail**: Tier 1's F-A03-1/2 and F-A07-4 describe the bug from the angle of a game calling a generated public setter. The same dead branch is reachable from inside Skald itself: a per-step parameter-lock (P-lock) on `frequency`/`rate`/`delayTime` targeting a node with `bpmSync: true` compiles cleanly, produces a real `set_param` call in the generated step-advance code (`codegen.odin:2190`), and does precisely nothing audible, with no error, no warning, and no visual difference in the Piano Roll/Step Properties editor between a P-lock that works and one that is dead on arrival. A user building an evolving synced wobble via per-step automation — a normal, encouraged workflow per the Sequencer chapter — can spend real time programming a P-lock lane that never affects the sound.
- **suggested fix**: same root fix as F-B02-1/F-B02-6 closes this automatically (the runtime-branch approach makes `set_param` calls always live, whether they originate from a game, a P-lock, or a knob drag). If that lands later than a quick mitigation is needed, `collect_plock_targets` could at minimum warn (not hard-error, since `bpmSync` can be toggled later) when a P-lock key resolves to a parameter that is sync-shadowed at the moment of export.

### F-B02-3: The dead `bpmSync`-exposure danger is also live inside Skald's own preview, not only in exported games — currently gated only by a dead UI affordance
- **kind**: risk
- **area**: BPM sync × live preview (`useWasmAudioEngine.ts`)
- **severity**: low
- **confidence**: medium
- **evidence**: `projectSerializer.ts:236-248` (`topologySignature`) masks to `null` (i.e., treats as a live-appliable value, not a rebuild trigger) any parameter name that is both `in n.parameters` **and** listed in that node's `exposedParameters` — with no exclusion for boolean-typed fields like `bpmSync`. `useWasmAudioEngine.ts:232-266` (`sendChangedExposedParams`) then posts a `set-param` message straight to the running wasm module for exactly those masked names, again with no type awareness. Today this chain is inert only because `bpmSync` cannot currently be added to `exposedParameters` through the UI (F-A03-4, confirmed still true for Delay too — see F-B02-4): the one click path that would reach it, `renderBpmSyncToggle`, is never called.
- **detail**: If F-A03-4's dead toggle were wired up (a reasonable, low-effort fix on its own) without also fixing F-B02-1, exposing `bpmSync` and then flipping its checkbox *while the preview is playing* would silently take the instant-apply path instead of forcing the rebuild that (today) is the only thing that would actually move a synced node between its two baked-in expressions. The checkbox would visibly flip; the audio would not change; no rebuild, no warning, nothing distinguishes this from a successful live edit. This is worth fixing at the same time as F-A03-4, not after it — wiring up the dead toggle in isolation would turn a currently-unreachable bug into a reachable one.
- **suggested fix**: fix F-B02-1/F-B02-6 before (or in the same change as) F-A03-4's toggle-wiring fix, so there is no window where exposing `bpmSync` is possible but still structurally dead in the running preview.

### F-B02-4: Tier 1 disagreement resolved — Delay's "expose BPM Sync" click path does not exist (F-A07-4's reachability claim is wrong; F-A03-4 is right, and generalizes to Delay)
- **kind**: doc-bug
- **area**: Tier-1 cross-check (LFO/S&H vs Delay/Reverb chapters)
- **severity**: low
- **confidence**: high
- **evidence**: F-A07-4 asserts: *"`ParameterPanel.tsx:242-270` (`renderBpmSyncToggle` wires a link/expose icon next to the BPM Sync checkbox exactly like any other parameter... so a user can and will expose it)"*. Direct re-check: `grep -n "renderBpmSyncToggle(" skald-ui/src/components/ParameterPanel.tsx` (searching for a *call*, not the `const renderBpmSyncToggle = (...) => {` definition at line 243) returns **no matches** — the function is defined and never invoked, for any node type. `NodeParameterControls.tsx:158-192` confirms all three node types (`lfo`, `delay`, `sampleHold`) render `bpmSync` as a bare `<input type="checkbox">` with no `renderControlWrapper`/expose-icon wrapper at all, so there is no exposure affordance to click for any of them, not just LFO/S&H.
- **detail**: F-A07-4's underlying bug claim (an exposed `bpmSync` would produce a dead, wrongly-ranged runtime parameter) is correct and still stands — it is exactly F-A03-3's mechanism, generalized. What is wrong is the reachability story: no current UI path lets a user click their way into exposing `bpmSync` on *any* node. The only ways to reach it today are hand-editing the save JSON or (per F-B02-2) a P-lock targeting it directly. This matters for prioritization: the bug is real but currently latent, not something an ordinary user will stumble into by clicking the obvious icon next to every other row, the way F-A07-4 implies.
- **suggested fix**: none needed beyond noting it — this is a correction to the Tier 1 record, not a new code issue. If/when F-A03-4's dead toggle is wired up for real, this finding (and F-B02-3) become live again and should gate that change on F-B02-1/6 landing first.

### F-B02-5: `param_ranges.odin` already has a `"bpm"` range entry that no code path can ever reach — a fossil of an unfinished runtime-tempo feature
- **kind**: missing-feature
- **area**: Project tempo / generated public API
- **severity**: medium
- **confidence**: high
- **evidence**: `skald-backend/core/param_ranges.odin` — the generic name-keyed fallback table has `case "bpm": return {20.0, 999.0, 120.0, "bpm"}` sitting alongside real, reachable entries like `voiceCount`/`unison`/`detune`/`glide`. But `lookup_param_range` is only ever called from the exposed-parameter resolution pass (F-B02-1), which walks **node** parameters; project-level `bpm` is never a node parameter (it lives on `Project`, not `Node`, per `projectSerializer.ts:17` / `docs/proposals/bpm-ux.md` section 1.1), so this case can never execute. Confirmed no `set_bpm`/`_set_bpm` symbol exists anywhere in `skald-backend/core` (`grep -rn "set_bpm" skald-backend/core` — no hits) and `codegen.odin:1321` (`p.bpm = %.9f`, baked once from the session value at `_init` time) is the only writer of the runtime field.
- **detail**: `p.bpm` genuinely is a live runtime struct field — every consumer (`bpm_sync_seconds_expr`, the sequencer's `samples_per_step_f`, note-duration math) reads it fresh each call rather than treating it as a codegen-time literal, which is architecturally exactly what you'd want for a future "change tempo at runtime" feature. But there is no public setter, no `_PARAMS` row, and no UI path to ever expose it — a shipped game cannot sync its music tempo to gameplay (a common, reasonable ask: tension ramps, adaptive music, rhythm-game tempo changes) without hand-patching the generated struct outside the documented API. The `param_ranges.odin` entry reads like someone started this feature and stopped; `docs/proposals/bpm-ux.md`'s deferred-items table lists "Runtime tempo changes without rebuild" and says "`p.bpm` already exists on the processor for it" — so this gap is already known, just not scheduled.
- **suggested fix**: treat this as a real, scoped 0.2 candidate, not just a fossil to delete: add `bpm` as a project-level exposable value (its own checkbox somewhere in the sequencer toolbar, or always-on), emit a `<Namespace>_set_bpm`/`skald_set_bpm` entry point that writes `p.bpm` directly (no clamp table lookup needed beyond the one that already exists), and gate it behind nothing more than "does this project want tempo runtime-adjustable" — much smaller than the per-node fix in F-B02-6, and independently valuable.

### F-B02-6: [design] Recommended architecture for 0.2 — collapse the sync/free-run duality into one authoritative value with a runtime-checked mode flag, shared by LFO, Sample & Hold and Delay
- **kind**: design
- **area**: BPM sync (engine-wide: LFO, Sample & Hold, Delay, and any future synced node)
- **severity**: high
- **confidence**: high
- **evidence**: Builds directly on Tier 1's F-A03-7 and F-A03-8 (which independently proposed the same shape for LFO and S&H) and extends it to Delay and to the P-lock/preview paths found in F-B02-1/2/3. Root cause evidence: `codegen.odin:35-58` (`bpm_sync_seconds_expr`, compile-time string selection), `:371-374`/`:397-400` (unconditional overwrite in the two generators Tier 1 cited), `:1216-1283` (exposure pass with no `bpmSync` awareness, F-B02-1), `param_ranges.odin` (no `bpmSync`/`syncRate` case, F-A03-3/F-A07-4), `types.ts:36-39` (`BpmSynchronizable` — `bpmSync?: boolean; syncRate?: string` as two independent, always-present optional fields with no linkage to the base rate field).
- **detail**: **The recommended architecture:**
  1. **One authoritative stored number per node** (`frequency` / `rate` / `delayTime`), always. It is never "dead" — it is either the live value (free-run mode) or the value the UI keeps continuously synced to whatever the sync formula currently resolves to (sync mode). The UI, not the backend, is responsible for this recompute: whenever `bpmSync` is on and either `syncRate` or the project `bpm` changes, the editor writes the resolved Hz/seconds straight into the node's stored `frequency`/`rate`/`delayTime` field (using the existing `syncRateToSeconds` from `bpm.ts`, already a verified mirror of the backend formula). This is what makes F-A03-5's drift (`wob-lfo.frequency: 2` vs the true `2.333`) structurally impossible going forward, not just a one-time data fix.
  2. **`bpmSync` becomes a real runtime-checked field**, not a compile-time-only branch selector. Give it a genuine `{0.0, 1.0, 0.0, ""}` entry in `lookup_param_range` (closing F-A03-3/F-A07-4's ±1e6-range bug directly) and let it flow through the exposure pass like any other f32-representable parameter.
  3. **Codegen always emits both expressions**, gated by a runtime `if` on the (possibly-exposed, possibly-P-locked) `bpmSync` field, e.g. for the LFO: compute `sync_freq` and read `p.frequency` unconditionally, then `freq := p.<id>_bpmSync != 0 ? sync_freq : p.frequency` before building the phase increment. Cost is one extra branch and one extra local per node per sample — negligible next to the trig already in these generators.
  4. **`syncRate` stays compile-time-only** (a string can't cross the f32-only `set_param` contract without a lookup table, and there's no strong case for a game wanting to re-pick the *division* at runtime the way it might want to flip sync on/off or grab the raw rate) — only `bpmSync` and the base rate need to become live.
  5. With (2)+(3) in place, `set_frequency`/`set_param("frequency", …)` on a synced node **actually changes the sound** the instant it's called, exactly like every hardware/DAW LFO's "grab the knob, you leave sync" idiom (matching F-A03-7's proposed idiom, extended: either document that calling the free-run setter is now live-and-additive-on-top-of-sync — probably confusing — or have the generated setter also flip the node's own `bpmSync` field to 0, giving the unambiguous, expected behavior).
  This single change closes F-A03-1, F-A03-2, F-A03-3, F-A03-5, F-A03-7, F-A03-8, F-A07-4, F-A07-5, and F-B02-1/2/3 above, all from one mechanism, applied identically to three generator functions.
- **manual impact**: `nodes/lfo.md` — the entire "Frequency and syncRate — the same control, two clocks" section and Code-vs-intent note 2 (both resolved rather than documented as a trap); "Try it" step 6 ("Break the sync") needs rewriting since unticking sync now always reveals the last-heard value, never a stale one. `nodes/sampleHold.md` — the "BPM Sync" section and Code-vs-intent note 3, same treatment. `nodes/delay.md` — "The controls" `bpmSync`/`syncRate`/`delayTime` row, the "syncRate + bpmSync" subsection, the "What expose does" "one trap" paragraph, and Code-vs-intent note #5 in full (per F-A07-5's own manual-impact list, which this finding fulfils rather than duplicates). `docs/proposals/bpm-ux.md` section 3.4's deferred-items table should gain this as an explicit line item — it is currently invisible in that document (see F-B02-7).
- **migration**: **Schema-compatible, behavior-changing.** No JSON key is renamed or removed — `bpmSync` stays a bool, `syncRate` stays a string, `frequency`/`rate`/`delayTime` stay plain floats. Required migration work: (a) backend — extend three generator functions (`generate_lfo_code`, `generate_sample_hold_code`, the Delay generator) to emit the runtime-branch form instead of the string-substitution form, add the `bpmSync` range-table case, and update the exposure pass so `bpmSync` is treated as an ordinary exposable f32 once it has a real range (roughly 100–150 line diff, contained to `codegen.odin` + one line in `param_ranges.odin`); needs new golden fixtures exercising runtime `set_param("bpmSync", 0/1)` and `set_param("frequency", …)` on a synced node for all three node types (none exist today — confirmed by `grep -rln bpmSync skald-backend/tests skald-backend/acceptance`, only an unrelated fixture file matches). (b) frontend — add the live-recompute-on-change effect described in (1) above (small, localized to wherever `syncRate`/`bpm` edits are handled for these three node types); wire or delete `renderBpmSyncToggle` (F-A03-4) *together with* this change, not before it (per F-B02-3). (c) data — a load-time normalization pass should recompute any `bpmSync: true` node's stored free-run field against its `session.bpm` once, exactly as F-A03-7/F-A03-8 already specify, so existing saved patches (the one confirmed-drifted example, `wobble-samplehold-bass.skald.json`'s sibling `wob-lfo`, plus any undetected others) start from a coherent baseline before the new "always-live" semantics take over. Patches with no project `bpm` (bare/unwrapped graphs) have nothing to recompute against and should be left as-authored with a load-time note. (d) public API — exported games that call the free-run setter on a synced asset today get a guaranteed no-op; after this change they get a real effect. Nothing could have legitimately depended on the old no-op, but it is a public-API behavior change worth one changelog line for 0.2.

### F-B02-7: The existing BPM proposal (`docs/proposals/bpm-ux.md`) is correct but scoped one layer too shallow — it never surfaces the codegen-level bug at all
- **kind**: doc-bug
- **area**: BPM sync — planning document
- **severity**: high
- **confidence**: high
- **evidence**: `docs/proposals/bpm-ux.md` section 1.1 states the `bpmSync`+`syncRate` mechanism as settled fact ("three node types... store a *relationship* to the project tempo instead") with no scrutiny of whether that relationship is implemented soundly; section 2 ("Inconsistencies found") lists seven items, all about *communicating* BPM (NaN guards, duplicate option lists, backend accepting `bpm<=0`, no visible sync-time link, UI/backend range mismatch, dead `start_time`, saves-without-session) — none about a synced node's free-run parameter surviving as a dead public setter. Section 3.4 ("Deferred / explicitly not implemented") lists six items, the closest being "Runtime tempo changes without rebuild (`skald_set_param` for bpm)" — which is about the *project-level* BPM value (F-B02-5's gap), not the per-node sync/free-run duality Tier 1 found on three separate nodes.

It is a genuinely good, narrowly-scoped piece of work that solved a real and different problem (BPM *input hygiene*) well. The risk is exactly that quality: a reader who trusts this document as "the BPM audit" for 0.2 planning would reasonably conclude tempo work is largely done, when the highest-severity tempo bug in the codebase (three nodes, high-severity per Tier 1, confirmed and generalized here) is completely absent from it.

### F-B02-8: Confirmed correct — sync-rate divisions mean the same duration everywhere they appear (sequencer grid, LFO, Sample & Hold, Delay)
- **kind**: design
- **area**: BPM sync — cross-node consistency (verified, not a bug)
- **severity**: low
- **confidence**: high
- **evidence**: `skald-backend/core/codegen.odin:2114` (`samples_per_step_f := p.sample_rate * 60.0 / (p.bpm * 4.0)`, i.e. one sequencer step = a sixteenth note = 0.25 beat) and `:2202` (note duration `* (60.0 / p.bpm / 4.0)`, the same constant) match `bpm_sync_seconds_expr`'s (`:35-58`) division arithmetic exactly at `"1/16"` (`denom=16`, `beats = 4/16 = 0.25`). `skald-ui/src/definitions/bpm.ts:45-58` (`syncRateToSeconds`) is a byte-for-byte arithmetic mirror of the backend formula (confirmed by its own doc comment and by `BpmConsistency.test.tsx`'s parametrized checks against `120`/`60`/`90`/`240` BPM). `projectSerializer.ts:167`'s `start_time` (compatibility-only field, per the proposal) uses the identical `60.0/bpm/4.0` constant, and `StepGrid.tsx`'s playhead-animation duration does too (per `bpm-ux.md` section 1.3).
- **detail**: This is worth stating explicitly because so much of this scope is about *silent* divergence between nominally-identical concepts (the brief's own worked example is "a BPM here and a BPM there... which one reaches the audio?"). Here, four independent code paths (sequencer stepping, note-duration, the UI's display-only `start_time`, and the three BPM-synced nodes' rate formula) were checked against each other directly and all agree: "1/8" is 0.25s at 120 BPM everywhere it is used, with no unit or off-by-one-beat confusion between them. No fix needed; recorded so a later pass doesn't re-spend time re-verifying it.
- **suggested fix**: none.

### F-B02-9: UI (20–300) vs backend (20–999) BPM range mismatch is still open, and is the same architectural gap F-A10-17 already flagged
- **kind**: inconsistency
- **area**: Project tempo range
- **severity**: low
- **confidence**: high
- **evidence**: `skald-ui/src/definitions/bpm.ts:18-19` (`BPM_MIN = 20`, `BPM_MAX = 300`) vs `skald-backend/core/param_ranges.odin`'s generic `case "bpm": return {20.0, 999.0, 120.0, "bpm"}`. `docs/proposals/bpm-ux.md` section 2 item 5 already documents this exact gap and defers it ("Harmless today — the UI is the only producer — but the two bounds should eventually be one constant in the JSON contract").
- **detail**: Currently harmless for the reason the proposal states (nothing lets a project exceed 300 BPM today, so the backend's wider ceiling is never exercised) — but it is the same failure mode F-A10-17 generalizes as an architecture-level design finding: a UI bound and a backend bound for the same concept, maintained as two separate literals with no shared source. If F-B02-5's runtime-BPM-setter feature ships, a game could legitimately call `set_bpm(500)` — a value no UI path could ever have produced, clamped by a range the UI author never saw — which is exactly the class of drift F-A10-17 warns generalizes badly. Filed here as confirmation this specific instance is still live, not a new independent bug.
- **suggested fix**: if/when F-B02-5 (runtime BPM) ships, unify the two bounds first (pick 300 or a documented wider value and update both `bpm.ts` and `param_ranges.odin` from one place) rather than exposing a backend range the UI has never validated against.
