## Summary

- **New, empirically proven**: `build_project_from_graph` (`skald-backend/core/json.odin:296-367`) assigns `project.instruments[idx]` by iterating the raw `graph.nodes` **map** with no sort, unlike every other emission pass in this codebase (which is scrupulous about this exact hazard — see `graph_utils.odin:9-14`'s own comment and `codegen.odin:1046-1050`'s reiteration of it). I built the actual `skald_codegen.exe` from the current source and reproduced this live: running it 5 times on one static 6-instrument fixture produced at least 3 distinct struct/body orderings, and running it 3 times on the **shipped** `examples/songs/full/four-bar-song.skald.json` produced three different "Music Layer assets:" orderings (`Pad HiHat Kick Lead Bass` / `Pad Bass HiHat Lead Kick` / `Kick Pad Bass HiHat Lead`) from byte-identical input. See F-B04-1.
- **Generalizes Tier1 F-A09-6** (nested Instruments crash codegen): I mapped the full disagreement across all three layers — parser, validator, and dispatch — and found the gap is wider than "add a dispatch case." The front-end's own serializer (`projectSerializer.ts`'s `formatSubgraph`/`formatNodesForCodegen`) never recurses into a second level of subgraph, so a nested Instrument always reaches the backend with `subgraph == nil` regardless of what the user built inside it — the backend's recursive subgraph parser (`json.odin:203-222`) is dead code for the real product. I reproduced the exact crash and captured its literal text. See F-B04-2.
- **New, empirically proven**: the Panner's stereo output (`output_left`/`output_right`, real ports in the backend's `valid_output_port` and `get_output_var`) cannot survive any consumer except a direct wire into GraphOutput. `PannerNode.tsx` exposes exactly one output handle; `output_left`/`output_right` do not appear anywhere else in `skald-ui/src`. I confirmed by codegen that Panner → Filter → Output reads the constant-power mono downmix, silently discarding whatever pan was dialed in the instant anything processes the signal. See F-B04-3.
- **New, empirically proven**: codegen performs zero dead-node elimination. An Oscillator with no path to GraphOutput still gets its full per-voice, per-unison phase/waveform code emitted and executed every sample forever, contributing nothing — verified by compiling a fixture with a deliberately orphaned 16-unison oscillator. See F-B04-4.
- **New, empirically proven**: `sanitize_identifier` (`param_utils.odin:43-62`) has no Unicode transliteration. Non-Latin or emoji instrument/label names collapse to strings of pure underscores that are visually indistinguishable from each other — verified: "キック" and "🎵🎵" both sanitize to 8 underscores. See F-B04-5.
- I built the real `skald_codegen.exe` and Odin-checked (`odin check -no-entry-point`) a battery of generated files — a 6-instrument duplicate-name fixture, the shipped `four-bar-song.skald.json`, and a "kitchen sink" graph exercising every node type (MidiInput, FmOperator, Wavetable, pink Noise, BPM-synced SampleHold, Mixer, ADSR with modulated attack/decay, asymmetric Distortion, Mapper, Panner, Gain, Filter, Delay, Reverb) — **all compiled cleanly with zero errors**. Outside the specific structural gaps above, the emitted Odin is solid: no one-package-per-directory violations, no type errors, no unused-import problems (Odin doesn't flag those, confirmed empirically). This matters for calibrating the other findings: they are architectural/structural gaps, not basic code-generation quality problems.

## Findings

### F-B04-1: `build_project_from_graph` orders instruments by unsorted map iteration — proven non-deterministic across runs of identical input
- **kind**: code-bug
- **area**: codegen / json parsing (instrument ordering)
- **severity**: high
- **confidence**: high
- **evidence**: `skald-backend/core/json.odin:296-367` (`build_project_from_graph`) — `idx := 0; for _, node in graph.nodes { if node.type == "Instrument" ... ; project.instruments[idx] = Project_Instrument{...}; idx += 1 }`. `graph.nodes` is `map[string]Node` (`types.odin:94`). Compare to every other emission pass in the same package, which the authors explicitly protect against exactly this: `graph_utils.odin:9-14` ("Odin map iteration order is unspecified and varies run-to-run... must iterate this sorted-by-id view instead of `graph.nodes` directly, or the generated source is non-deterministic"), and `codegen.odin:1046-1050` repeating the same warning immediately before building `all_nodes := nodes_sorted_by_id(graph)`. `build_project_from_graph` is the one caller that skips this.
  I built `skald_codegen.exe` from the current source (`odin build main.odin -file`) and ran it 5× on a static 6-Instrument bare-graph fixture (all named "Dup" to force `resolve_unique_names`' suffixing, `codegen.odin:2251-2266`): the header's `// SFX assets:` line always listed `Dup Dup_2 Dup_3 Dup_4 Dup_5 Dup_6` (cosmetically stable, since that loop just counts up), but `diff` against run 1 showed runs 3, 4, and 5 each assigned a **different underlying oscillator id** (`osc_a` vs `osc_f` vs `osc_d`, etc.) to the struct/body that ended up named plain `Dup`. Separately, I ran the CLI 3× on the **shipped, unmodified** `examples/songs/full/four-bar-song.skald.json` (which has no `"project"` wrapper — 5 top-level `"instrument"`-typed nodes, exactly the shape that routes through this function) and got three different orderings of the `// Music Layer assets:` line: `Pad HiHat Kick Lead Bass`, `Pad Bass HiHat Lead Kick`, `Kick Pad Bass HiHat Lead`.
- **detail**: This function is reached whenever the codegen CLI is fed a "bare graph" JSON (no `project` key, `Instrument`-typed nodes at the top level) instead of the `{project: {instruments: [...]}}` shape — exactly the shape several shipped example files use (`four-bar-song.skald.json`, `possible-background-music.skald.json`), and exactly the shape a CI script, golden-test harness, or anyone testing the CLI directly (as its own `-in:`/`-out:` flags invite) would use. The live GUI's "Generate Code" button is not affected (`projectSerializer.ts`'s `buildProjectData` always emits the `project` wrapper via a deterministic `.map()`, so it goes through `build_project_from_raw` instead, which is unaffected). But for anyone or anything using the bare-graph path, regenerating from byte-identical input can silently reassign which instrument gets which name-suffix and which slot in `Project_State`/the wasm-shim's index-addressed dispatch (`skald_trigger(asset: i32, ...)`, `codegen.odin:2564-2573`, switches on `i` = `project.instruments` index). Any two runs of the exact same file can disagree about which instrument is asset 0. This also makes byte-for-byte golden-snapshot testing of these specific fixtures inherently flaky — directly undermining the determinism discipline the rest of this file goes out of its way to document and enforce.
- **suggested fix**: Replace the two `for _, node in graph.nodes` loops in `build_project_from_graph` (`json.odin:303-307` and `:331-361`) with iteration over `nodes_sorted_by_id(graph)` (already used everywhere else), or better, sort by each Instrument's node id (or a stable pre-sanitization order) before assigning `idx`.

### F-B04-2: Nested Instruments — the full disagreement is deeper than "missing dispatch case"; the frontend never serializes what would be needed to fill it in
- **kind**: code-bug
- **area**: codegen dispatch / json parsing / frontend serialization (extends Tier1 F-A09-6)
- **severity**: high
- **confidence**: high
- **evidence**: I reproduced Tier1's crash directly: feeding a project-wrapped JSON with an `Instrument`-typed node nested inside another instrument's `audio_graph.nodes` to the built CLI produces `Error: unknown node type "Instrument" (node id inner) in instrument "Outer" — no code generator exists for it. Refusing to generate a silently-broken patch.` and a clean `exit(1)` (`codegen.odin:1894-1901`, the per-voice dispatch switch's default case). Tracing the layers above that:
  1. **Parser** (`json.odin:203-222`, `build_graph_from_raw`): fully recursive — an `Instrument`-typed node's own `subgraph` (from a dedicated `subgraph` field, or `params["subgraph"]`) is parsed into `node.subgraph` by calling `build_graph_from_raw` on itself. This machinery clearly anticipates nesting.
  2. **Validator** (`graph_validate.odin:37-61`, `valid_input_ports`): has no `case "Instrument"` at all, so it returns `(nil, false)` — `known=false`. The caller (`validate_connections`, line 131-132) explicitly does `if !known do continue // unknown node type — emission dispatch reports it`. This is a deliberate design choice to defer to codegen, but it means the one place in this codebase that is otherwise obsessive about "fail loudly, early, and specifically" (dangling connections, typoed ports, cycles, bus-domain violations — all hard errors with a purpose-built message before any code is emitted) punts this exact case to the least specific error path.
  3. **Frontend serializer** (`skald-ui/src/utils/projectSerializer.ts:39-87`): `formatSubgraph` calls `formatNodesForCodegen` on a subgraph's node list; that function generically maps every node (including any child of type `'instrument'`) and unconditionally does `delete parameters.subgraph` (line 51) — it never re-invokes `formatSubgraph` for a child that is itself an Instrument. Only the OUTER `buildProjectData` loop (line 121-145) calls `formatSubgraph(data.subgraph)`, and only for the top-level instrument nodes filtered by `getInstrumentNodes` (line 91-92, `n.type === 'instrument'` on the top-level `nodes` array only). So a second-level nested Instrument's `subgraph` is stripped and never replaced — by the time JSON reaches the backend, a nested Instrument node always has no subgraph data at all, regardless of what the user built inside it.
- **detail**: Tier1 (F-A09-6) correctly identified the crash and suggested either implementing nested codegen or rejecting nesting at UI/load time as "far cheaper." This finding sharpens the cost estimate: the parser's recursive support (#1) is currently unreachable/untested dead code given the real serialization path (#3), so "implement nested codegen" is not a self-contained backend change — it would also require rewriting `formatSubgraph`/`formatNodesForCodegen` to recurse, and deciding semantics Tier1 already flagged as unspecified (does a nested Instrument's own `voiceCount` multiply against the parent's polyphony? which `bpm`/plocks/sequencer context applies?). The "reject at validation time" option is comparatively far cheaper and has an obvious, natural home: add `case "Instrument": return nil, false` distinctly from the generic unknown-type fallback in `valid_input_ports`, or better, a dedicated pre-flight check (mirroring `compute_bus_domain`'s style of purpose-built `os.exit(1)` messages) that walks every subgraph for a nested `Instrument`-typed node and fails with an explicit "Instruments cannot be nested" message before any code generation work begins — consistent with this file's own established idiom of catching structural violations as early and specifically as possible.
- **suggested fix**: Add an explicit pre-flight validation pass (called once per subgraph, recursively) that rejects any `Instrument`-typed node found inside another instrument's graph with a clear, dedicated error message, rather than relying on the generic per-voice dispatch fallback. If nesting is ever implemented instead, the frontend serializer must be rewritten to recurse (currently it silently discards the exact data a fix would need).

### F-B04-3: Panner's stereo output cannot survive any consumer except a direct wire into GraphOutput — the ports the backend supports are unreachable from the editor
- **kind**: design
- **area**: codegen / Panner / editor-backend port contract
- **severity**: high
- **confidence**: high
- **evidence**: Backend support is real: `graph_validate.odin:70-72` (`valid_output_port` recognizes `"output_left"`/`"output_right"` for `Panner`), `param_utils.odin:64-70` (`get_output_var` returns dedicated `node_%s_out_left`/`_out_right` variables for those port names), `codegen.odin:720-735` (`generate_panner_code` computes true stereo AND a constant-power mono downmix `node_%s_out = (L+R)*0.7071068` "for mono-input consumers... a Panner feeding a Filter or Gain used to produce TOTAL SILENCE"). But `skald-ui/src/components/Nodes/PannerNode.tsx:10` declares exactly one output handle: `outputs: [{ id: 'output', label: 'Out' }]` — there is no second handle to drag a wire from. I grepped the entire `skald-ui/src` tree for `output_left`/`output_right`: zero matches anywhere outside the backend. I then built and ran the codegen on a `Oscillator → Panner(pan=1.0) → Filter → GraphOutput` fixture: the emitted Filter code reads `high_filt1 := f32(((node_pan1_out)) - ...)` — `node_pan1_out` is the mono downmix, confirmed by `generate_panner_code`'s own emission. Only `generate_graph_output_adds` (`codegen.odin:2025-2047`) special-cases `src_node.type == "Panner" && (src.port == "" || src.port == "output")` to route the real stereo pair — and only because the *destination* happens to be a GraphOutput, not because the wire says anything about L/R.
- **detail**: The whole point of a Panner is to place a sound in the stereo field. That placement is only preserved through the one specific wiring pattern (Panner directly into an instrument's Output) that the codegen has special-cased by destination type. Route the panned signal through literally anything else first — a Filter, Gain, Delay, Mixer, another Panner — and the stereo image silently collapses to the constant-power mono downmix at the exact point of panning, with no warning, no visual cue, and no way for the user to do otherwise (there is no handle to wire around it). A user who pans a sound hard left, then adds "one more Filter" for tone shaping, gets a patch that behaves as if the pan control did nothing — the same "lying control" shape as the Oscillator Fixed Pitch example this whole audit uses as its working definition of a design smell, except here the control quietly works only in one specific topology instead of being hidden.
- **suggested fix**: Either (a) add `output_left`/`output_right` handles to `PannerNode.tsx` so users can explicitly route each channel (and keep the existing mono-downmix `'output'` handle for the common case), or (b) if true per-channel routing is out of scope for now, propagate the stereo pair implicitly through every consumer the way `generate_graph_output_adds` already does for GraphOutput specifically — i.e., teach `sum_port_inputs`/`get_f32_param` to special-case a Panner source the same way, so panning is preserved through at least one more hop (e.g., a Filter or Delay placed after a Panner) instead of collapsing at the very next node.
- **manual impact**: Any panner.md-equivalent section describing "Out" as carrying the pan; would need a new note describing exactly when the pan information survives (only into GraphOutput) versus when it's downmixed.
- **migration**: None required for option (b) (backend-only); option (a) is additive to the node's handle list and does not change the meaning of the existing `'output'`/mono handle, so no saved `.skald.json` needs to change.

### F-B04-4: No dead-node elimination — orphaned/disconnected nodes are fully emitted and executed every sample forever
- **kind**: missing-feature
- **area**: codegen / performance
- **severity**: medium
- **confidence**: high
- **evidence**: The per-voice dispatch loop (`codegen.odin:1861-1903`) and the bus-domain dispatch loop (`:1952-2006`) both walk `sorted_nodes`/every node in the graph unconditionally — neither checks whether a node's output is ever consumed (directly or transitively) by a `GraphOutput`. I built and compiled a fixture with `voiceCount=8`, `unison=16` containing one Oscillator wired to Output and a second, identical Oscillator wired to nothing: the generated file still declares `osc_osc_dead_phase: [16]f32` and emits the full unison loop (`codegen.odin:183-220`'s template) for `osc_dead` verbatim, including the per-sample phase increment, waveform branch, and unison average — 128 sine evaluations per sample that feed no variable anything downstream ever reads.
- **detail**: This is a completely ordinary editing pattern — a user drags in an oscillator to audition it, decides against it, and either forgets to delete it or leaves it half-wired while trying something else — and it silently becomes permanent CPU cost in every exported build, at whatever the node's configured voice/unison cost is, with no warning anywhere in the UI or codegen output that it's dead weight. Combined with the fact that Skald already has no per-project voice-budget/CPU overview (Tier1 F-A09-9), a user has no way to even notice this is happening short of reading the generated Odin by hand.
- **suggested fix**: Before emission, compute the set of nodes with a live path (forward reachability) to any `GraphOutput`/`InstrumentOutput` in the graph, and either skip fully-dead nodes during emission (cheapest) or at minimum emit a build-time warning listing them (`fmt.eprintf`, non-fatal) so the user can clean up before shipping.

### F-B04-5: `sanitize_identifier` has no Unicode fallback — non-Latin and emoji names collapse to indistinguishable strings of underscores
- **kind**: code-bug
- **area**: codegen / identifier generation
- **severity**: medium
- **confidence**: high
- **evidence**: `param_utils.odin:43-62` (`sanitize_identifier`) maps every byte that isn't ASCII `[A-Za-z0-9_]` to `'_'`, one underscore per byte (not per codepoint) — so a multi-byte UTF-8 character becomes several underscores. I built and ran the codegen on instruments named `"キック"` (Japanese, 9 UTF-8 bytes) and `"🎵🎵"` (2 emoji, 8 UTF-8 bytes): the emitted struct names were `_________Processor` and `__________Processor` respectively — both purely underscores, distinguishable from each other (and from any other non-Latin name of similar byte-length) only by counting characters. `clean_instrument_name` (`codegen.odin:960-965`) only special-cases the *empty*-name case (`len(inst.name) == 0`) with a fallback to `Instrument_<id>`; it has no equivalent check for "name is non-empty but sanitizes to zero alphanumeric content." The same `sanitize_identifier` call is reused for the collision-prefix path on exposed-param field names (`codegen.odin:1256`, `sanitize_identifier(get_string_param(node, "label", node.id))`), so a filter labeled in Japanese or with an emoji produces an equally unreadable exposed-parameter field name.
- **detail**: The generated code still compiles (verified) and `resolve_unique_names`'/the field-name collision resolver's numeric suffixing (`_2`, `_3`, ...) still guarantees no two identifiers collide, so this is not a build-breaking bug. But for any non-English-language studio, or any project that uses emoji labels for quick visual identification in the editor (a normal thing to do with SFX libraries), the generated public API — proc names, `Skald_Param_Info.name` strings, struct names — degenerates into meaningless runs of underscores that give a game programmer integrating the asset zero information to go on, and that are easy to visually confuse with each other.
- **suggested fix**: When the sanitized result contains no alphanumeric characters at all (only underscores), fall back to the node/instrument id the same way the empty-name case already does, rather than emitting the underscore string. A full transliteration table is out of scope, but "detect the degenerate case and use the id instead" is a small, targeted fix reusing the existing empty-name fallback pattern.

### F-B04-6: No user-wireable feedback loops — the only feedback in the entire node set is the one hardcoded comb inside Delay/Reverb
- **kind**: design
- **area**: codegen / graph topology
- **severity**: low
- **confidence**: medium
- **evidence**: `topological_sort` (`graph_utils.odin:25-69`) plus its caller (`codegen.odin:1043-1062`) treat any cycle as an unconditional hard error (`os.exit(1)`, "instrument %q contains a feedback loop... Break the cycle (remove the feedback wire) and regenerate"). There is no mechanism anywhere in the codebase (no implicit unit-delay insertion, no "feedback" wire type, no special-cased back-edge) to let a user wire an actual feedback path through the graph — the *only* feedback in the entire node vocabulary is the single literal-coefficient comb built into `generate_delay_code`/`generate_reverb_code` (`codegen.odin:514-579`).
- **detail**: Feedback loops (through a filter, through an FM operator, Karplus-Strong-style comb-and-filter loops) are a normal, well-understood, cheap DSP technique — cheap specifically because the standard fix is trivial: break the cycle for scheduling purposes with an implicit one-sample delay on a designated "feedback" input, exactly the way most modular/node-based audio tools (and Pure Data/Max, VCV Rack, etc.) handle it. Skald's current architecture forecloses this category of patch entirely and unconditionally, rather than allowing it with the standard one-sample-latency caveat. This is a real capability gap for a "modular synth in a box" tool, not just a missing preset.
- **suggested fix**: Consider allowing a designated "feedback" connection (perhaps a distinct edge/port convention, or any edge that closes a cycle) to be scheduled with an implicit one-sample delay — read the *previous* sample's value from the feedback source instead of demanding topological order — so a user-built feedback loop degrades to "one sample late" instead of "build refused."
- **manual impact**: Would need a new "Feedback loops" section wherever the topology/graph-model chapter lives, since this is currently undocumented as an absolute restriction (the manual currently only documents that *bus-domain* nodes can't feed voice-domain nodes, not that no cycle of any kind is permitted anywhere).
- **migration**: Purely additive (a new legal graph shape); no existing saved `.skald.json` contains a cycle today (they'd already fail to generate), so nothing needs to change for existing content.

### F-B04-7: The one-package-per-directory safety net lives only in the Electron layer, not in the codegen binary itself
- **kind**: risk
- **area**: codegen / build tooling
- **severity**: low
- **confidence**: high
- **evidence**: `skald-ui/src/main/codegenGuards.ts` (`assertCodegenTargetSafe`, called from `main.ts:88-90`) is the only place that refuses to write a generated file into a directory that already contains a `.odin` file declaring a different `package` — exactly the hazard the brief asks about. `skald-backend/main.odin` (the actual `skald_codegen.exe` CLI, documented via its own `-name:`/`-in:`/`-out:`/`-wasm-shim:`/`-package:` flags) has no equivalent check anywhere in `core/codegen.odin` or `main.odin` — it will happily `os.write_entire_file` over or alongside anything at the given path.
- **detail**: The CLI is a general-purpose, independently documented tool (used directly by `build_codegen.bat`, the acceptance harness, and — per its own flag surface — clearly intended to be invokable outside the Electron app). Any caller other than the Electron main process (a CI pipeline, a batch "export all examples" script, a future headless build step, or a developer running the exe by hand per its documented flags) gets zero protection against silently producing a directory with two conflicting `package` declarations, which will fail to build the moment Odin is invoked on that directory — exactly the failure mode the Electron-side guard's own comment says "really happened" once already.
- **suggested fix**: Port `assertCodegenTargetSafe`'s two checks (don't overwrite a foreign-package file at the exact path; don't drop a foreign-package file into a directory owning a different package) into `main.odin` itself, so the protection travels with the binary rather than living only in one caller.
