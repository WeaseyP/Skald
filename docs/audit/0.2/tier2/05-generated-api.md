## Summary

- Read Tier 1's `05-midiinput-output.md` first, per instructions — its F-A05-8 (master/instrument volume baked as compile-time literals, no runtime setter, VCA-before-Output workaround required) and F-A05-1 (master volume of exactly 0 exports as full volume) are the anchor findings for this pass. Both are confirmed again directly in the generated artifact and are **not** re-filed here.
- Traced the actual generated surface end to end: `skald-backend/core/codegen.odin` (the generator), `examples/integration_demo/generated_audio/generated_audio.odin` + `main.odin` + `README.md` (Skald's own reference integration), `skald-ui/generated_audio.odin` and four other checked-in `generated_audio.odin` copies (`skald-backend/`, `skald-backend/tests/`, `skald-backend/acceptance/generated_audio/`, `skald-backend/tester/generated_audio/`, `skald-backend/tester/fixture_player/generated_audio/`), and `skald-backend/tests/golden/*.odin.golden` (the internal regression snapshots).
- **The single biggest finding**: every generated `.odin` file checked into the repo — the integration demo, the UI's own copy, both tester copies, the acceptance copy — is stale relative to what `codegen.odin` currently emits. All six are missing a voice-stealing anti-click fix that current `codegen.odin` demonstrably has and that the *internal* golden snapshots (`skald-backend/tests/golden/*.golden`) already reflect. The regression-test safety net exists and works; nothing regenerates the human-facing examples, so the artifact integrators would actually read is behind the generator that produced it.
- Skald's own recommended integration pattern (bypass `project_*`, call per-asset `_process` directly — the README says so explicitly) silently discards **both** the authored master volume and the tanh soft-limiter, because both live only in `project_process`. The shipped demo's `main.odin` substitutes an untraceable, hand-picked `* 0.6` instead. This compounds Tier 1's F-A05-8/F-A05-1 rather than sitting next to them: even if master volume grew a runtime setter tomorrow, the recommended integration path still wouldn't see it.
- The API surface itself is otherwise well-designed for the constraints of the domain: idiomatic Odin (proc-takes-pointer-first-arg, matching `core:strings.Builder`-style APIs), genuinely allocation-free per-frame (`new`/`make`/`append` only appear in the test-harness `project_init` wrapper, never in any `_process`), and the note-scheduling/duration semantics are sound. The gaps are in the things around the DSP core: thread-safety contract, input validation, versioning/rename safety, and documentation of the surface that exists.
- No dedicated manual chapter, and no file under `examples/docs/`, documents the generated Odin API itself — 21 manual chapters cover every node exhaustively; zero cover the artifact a game actually consumes. `examples/integration/` (a path this brief pointed at) is a fully empty directory next to the populated `examples/integration_demo/`.

## Findings

### F-B05-1: Every checked-in example/demo generated_audio.odin is stale — missing a voice-steal anti-click fix the current generator already has
- **kind**: inconsistency
- **area**: codegen / generated API — voice stealing
- **severity**: high
- **confidence**: high
- **evidence**: `skald-backend/core/codegen.odin:1461-1501` — current generator captures the stolen voice's live envelope level (`adsr_%s_prev_level`/`attack_start`) and, per the comment at `:1471-1476`, deliberately keeps a stolen voice's oscillator phase/filter state intact ("the old hard reset (phase and filter to zero mid-waveform) was an audible click on every steal"), guarding the hard reset with `if !stolen` (`:1497-1499`). None of the checked-in generated files contain this: `grep -c attack_start` returns **0** in `examples/integration_demo/generated_audio/generated_audio.odin`, `skald-ui/generated_audio.odin`, `skald-backend/generated_audio.odin`, `skald-backend/tests/generated_audio.odin`, `skald-backend/acceptance/generated_audio/generated_audio.odin`, and `skald-backend/tester/{,fixture_player/}generated_audio/generated_audio.odin` — all six unconditionally zero `v.osc_1_phase`, `v.filter_2_low/band`, and `v.adsr_3_release_level` on every `note_on` (`examples/integration_demo/generated_audio/generated_audio.odin:154-158`), stolen or not. By contrast `skald-backend/tests/golden/adsr_sine.odin.golden` (and its siblings) already contain `attack_start` (3 occurrences), because `run_golden.bat` (`skald-backend/run_golden.bat:1-97`) regenerates and diffs those specific snapshots against fresh `codegen.exe` output as part of the internal test loop.
- **detail**: The regression-test safety net (`tests/golden/`) is working exactly as designed and is up to date. Nothing else is. A user who opens `examples/integration_demo/` — the file this repo positions as "what consuming a Skald-generated `.odin` package from a real game looks like" (`examples/integration_demo/main.odin:2-3`) — is reading and building against a generator that is behind current `codegen.odin`, with an audible, previously-fixed-and-reverted-looking click bug reintroduced by staleness. Anyone diffing "what changed since I last regenerated" has no signal that this happened short of noticing the click or grepping for `attack_start` themselves; there's no build step, CI check, or doc note tying example freshness to generator changes.
- **suggested fix**: Add the example/demo/UI-bundled `generated_audio.odin` files to the same regeneration discipline as `tests/golden/` — either a pre-commit/CI check that regenerates them from their source `.json` and fails the build on diff, or a single `regen_examples.bat` run as part of the release checklist so "does the shipped example match the shipped generator" is a checked invariant, not a hope.

### F-B05-2: Skald's own recommended integration pattern silently discards both master volume and the safety limiter — extends F-A05-1 / F-A05-8
- **kind**: inconsistency
- **area**: Output / project mix, game integration pattern
- **severity**: high
- **confidence**: high
- **evidence**: `examples/integration_demo/_demo_project.json:4` sets `"master_volume": 0.8`; the generated `project_process` bakes it in as `math.tanh(mixed_left * 0.800000012)` (`examples/integration_demo/generated_audio/generated_audio.odin:629-630`) — but `examples/integration_demo/README.md:7-8` states outright: *"The convenience `project_*` wrapper is not used; that's a test-harness affordance only"*, and `main.odin:2-5` frames the whole file as "the same way game code would" drive it. The demo's actual mix (`main.odin:211-212`) is `l := (sfx_l + layer_l) * 0.6` / `r := (sfx_r + layer_r) * 0.6` — a bare literal with no reference to `master_volume`, no tanh, and no comment explaining where `0.6` came from.
- **detail**: Tier 1's F-A05-8 already established master/instrument volume have no runtime setter. This finding is the other half: even the one place master volume *does* reach generated code (`project_process`'s bake-in) is never exercised by the integration path Skald itself recommends, because that path is told explicitly not to use `project_process`. A game team following the README loses the editor-authored mix level and the anti-clip limiter simultaneously, and has to invent — with zero guidance in the generated file, the README, or the manual — its own final-stage gain and any clipping protection across N simultaneously-playing assets. The `0.6` in the shipped example is exactly the kind of unexplained magic constant an integrator would copy-paste into a real game without understanding it's disconnected from anything authored in the editor.
- **suggested fix**: Once master volume gets a runtime setter (per F-A05-8's fix), also expose the tanh soft-limiter (or an equivalent per-mix-call limiter proc, e.g. `skald_soft_limit(l, r) -> (f32, f32)`) as a small standalone utility the per-asset integration path can call after summing its own assets — so "don't clip when I mix N processors myself" doesn't require adopting the whole `project_*` wrapper just to get the one safety behavior it provides.

### F-B05-3: Thread safety of setters against the audio thread is undocumented and mechanism-free
- **kind**: risk
- **area**: generated API — runtime parameter setters
- **severity**: high
- **confidence**: high
- **evidence**: `Sfx_set_cutoff` (and every generated `<Foo>_set_<param>`) is a plain, unguarded field write — `examples/integration_demo/generated_audio/generated_audio.odin:217-222` (`p.cutoff = v`); `Sfx_process` reads the same field directly at `:292` (`cutoff_c_2: f32 = math.clamp(f32(p.cutoff), ...)`). A search of `skald-backend/core/` for `thread`, `atomic`, `Mutex`, or any synchronization primitive returns zero matches anywhere in the generator's emitted code. The demo's own producer thread happens to call both `check_timeline` (which calls `Sfx_set_cutoff`) and `Sfx_process` from the *same* thread (`examples/integration_demo/main.odin:205-210`), which is precisely why the race never surfaces there — but nothing states that constraint anywhere.
- **detail**: A typical game does not process audio on its main/gameplay thread; the far more common shape is a dedicated real-time audio callback pulling `_process` while gameplay code (input, AI, distance calculations for a 3D pan/cutoff sweep) calls the typed setters from a different thread. That is a textbook unsynchronized concurrent read/write on a plain `f32` — formally a data race, and in practice a source of occasional torn/glitched parameter reads under contention, especially once a param is anything wider than a single scalar in the future. Nothing in the generated file's header comment, the `README.md`, or any manual chapter says "setters must be called from the same thread as `_process`" or offers an alternative (double-buffered param shadow, a lock-free single-writer queue, atomics). An integrator has no way to know this is a constraint until they hit it.
- **suggested fix**: Pick one of two contracts and document + enforce it: (a) state plainly that all `<Foo>_set_*`/`<Foo>_set_param` calls must happen on the same thread that calls `<Foo>_process` (cheapest, matches the demo's actual usage), or (b) make the generated setters genuinely thread-safe (e.g. write into a small lock-free pending-value slot per param that `_process` applies at the top of the next frame). Whichever is chosen, put one sentence about it in the generated file's own header comment (see F-B05-6) since that is the only artifact most integrators will actually read.

### F-B05-4: Editing an unrelated node, or renaming an instrument, silently changes the generated proc/field names a game already compiles against
- **kind**: design
- **area**: codegen — naming stability across regeneration
- **severity**: high
- **confidence**: high
- **evidence**: The per-asset API prefix is the instrument's display name, sanitized (`clean_instrument_name`, `skald-backend/core/codegen.odin:956-965`, feeding `resolve_unique_names`, `:2251-2266`) — renaming "Sfx" to "SFX" or "Player_SFX" in the editor changes every exported symbol (`Sfx_init` → `SFX_init`, `Sfx_set_cutoff` → `SFX_set_cutoff`, …) with no deprecation alias. Separately, an exposed param's typed-setter field name is only label-prefixed when it *collides* with another exposed param of the same name (`counts[p_name] > 1` at `codegen.odin:1251-1258`); removing or unexposing the *other* colliding node drops the count back to 1, so the *surviving, untouched* node's field silently reverts from e.g. `Filter_cutoff` back to bare `cutoff` (`:1246-1267`) even though nothing about that node itself was edited.
- **detail**: Both are real "regenerate after an edit" scenarios with no protection. A cosmetic instrument rename (something a sound designer would do without thinking, e.g. "Sfx" → "Sfx_v2" while iterating) breaks the build of any game code written against the old prefix — a compile error, at least, so it fails loudly, but with zero indication *why* short of diffing the generated file. The second case is worse: editing node B (deleting it, or un-exposing one of its params) changes the public name of node A's setter, which a developer reviewing "what did I just change" would have no reason to suspect, since node A's own configuration is untouched. There is no stable per-node/per-asset identifier a game could hold onto across a rename (the raw node id exists internally — `node_raw_id`, `types.odin:84-86` — and already backs the `"<raw_id>::<param>"` string alias, but that alias isn't surfaced for the *asset* prefix itself, only for individual exposed params, and isn't mentioned as a stability guarantee anywhere).
- **suggested fix**: Either (a) let the user pin a stable "export name" per instrument, separate from its display label, that survives renames, or (b) generate a compatibility shim on rename — keep the old prefix as a thin wrapper calling the new one for one release cycle, with a deprecation comment. For the field-name-reversion case specifically: make field-name collision resolution stable per node (e.g. always suffix with the node's raw id when *any* param on that node has ever collided in this project's history) rather than recomputed fresh from the current node set every regeneration, so an edit to node B can never change node A's generated symbol.
- **manual impact**: No existing chapter documents this because no chapter covers the generated API's naming/versioning contract at all (see F-B05-9) — this would be new content, not a rewrite.
- **migration**: Purely a codegen/output-naming change; no `.skald.json` schema field changes, so no upgrade-on-load logic for saved projects. Any game already built against current auto-generated names would need one manual find-and-replace per renamed asset the first time this ships, same as today, but never again afterward if a stable export name is adopted.

### F-B05-5: Invalid note/velocity input has no clamp or validation, inconsistent with every exposed knob param
- **kind**: missing-feature
- **area**: generated API — note_on / trigger
- **severity**: medium
- **confidence**: high
- **evidence**: `<Foo>_note_on(p, note: u8, velocity: f32, duration: f32)` (`codegen.odin:1394`) stores both verbatim — `v.note = note` / `v.velocity = velocity` (`codegen.odin:1443-1444`, confirmed in generated output at `examples/integration_demo/generated_audio/generated_audio.odin:141-142`) — with no range check anywhere in the generator. `velocity` then multiplies directly into `vel_scale = (1.0 - vs) + vs*velocity` (demo file `:332`), and `note` feeds `440.0 * math.pow(2.0, (f32(note)-69.0)/12.0)` (`:145`) with `note` typed `u8` (legal range 0–255, not MIDI's 0–127). Contrast this with every exposed knob setter, which the generator does clamp: `Sfx_set_cutoff` clamps to `[20, 20000]` (demo file `:217-222`).
- **detail**: A very ordinary integration bug — passing a raw MIDI 0–127 velocity without normalizing to 0–1, or accidentally dividing by 100 instead of 127 leaving a value >1 — silently produces an envelope scaled above unity or, with a negative/garbage velocity, an inverted-polarity signal, with no error, no clamp, no assertion. A note number above 127 (also an easy off-by-something in game code building note tables) produces a frequency that's simply wrong — no crash, just audibly incorrect or aliased pitch. Every other numeric input in the same file is guarded; these two, the most fundamental inputs to the whole API, are not.
- **suggested fix**: Clamp `velocity` to `[0,1]` and `note` to `[0,127]` at the top of the generated `_note_on`/`_trigger`, the same way exposed params are clamped — cheap, and turns "silently wrong audio" into "clamped to the nearest valid value," which is the behavior every other setter in the file already has.

### F-B05-6: The generated file's own header comment omits the typed setters, string-keyed set_param/get_param, and PARAMS table — the exact mechanism for exposing gameplay-tunable parameters is invisible unless you scroll past it
- **kind**: doc-bug
- **area**: generated API — self-documentation
- **severity**: medium
- **confidence**: high
- **evidence**: The header comment generator (`codegen.odin:2313-2321`) emits only: *"Game integration: import this package and use the per-asset APIs. SFX: `<Foo>_init`, `<Foo>_trigger`, `<Foo>_process`, `<Foo>_is_playing`. Music Layer: `<Bar>_init`, `<Bar>_start`, `<Bar>_stop`, `<Bar>_process`, `<Bar>_set_loop`"* plus a note about `_trigger`/`_note_on`/`_note_off`. It never mentions `<Foo>_set_<param>` (generated at `codegen.odin:1675`), `<Foo>_set_param`/`<Foo>_get_param` (string-keyed dispatch, `:1737-1772`), the `<Foo>_PARAMS` table (`:1691-1703`), or the `"<node_id>::<param>"` alias (`:1730` / `types.odin:84-86`). Confirmed in the actual generated output: `examples/integration_demo/generated_audio/generated_audio.odin:1-21` (the real header) vs. `Sfx_set_cutoff` at `:217-222` and `Sfx_PARAMS`/`Sfx_set_param`/`Sfx_get_param` at `:224-243` — all present in the file, none mentioned in its own summary.
- **detail**: The `README.md` for the integration demo explicitly praises this header as the reason "consumers know what's there without opening the source" (`examples/integration_demo/README.md:101-105`). But the single feature the manual's own "Going further" section pitches as the reason exposure exists — *"Use exposure as a game-design tool… The generated `<Asset>_PARAMS` table then documents the contract for whoever writes the gameplay code"* (`docs/manual-source/00-foundations.md:367`) — is exactly the part missing from that same table's self-description. An integrator who trusts the header (as the tool encourages them to) would not discover the runtime-parameter feature exists at all without reading past it into the body of the file.
- **suggested fix**: Extend the header template to list, per asset, its exposed params and both ways to set them (typed setter name + the fact that `_set_param`/`_get_param` and `PARAMS` exist), generated straight from the same `stable_resolutions` list already used to emit them (`codegen.odin:1691-1703`) — it's already computed at header-generation time, just not written into the comment.

### F-B05-7: No version/provenance stamp in generated output, and codegen silently overwrites the target file unconditionally
- **kind**: missing-feature
- **area**: codegen CLI / generated artifact provenance
- **severity**: medium
- **confidence**: high
- **evidence**: `skald-backend/main.odin:90-99` writes `target_file` via `os.write_entire_file` with no check for an existing file, no diff, no "this looks hand-edited, are you sure" — it's a blind overwrite. The header comment generator (`codegen.odin:2283-2321`) embeds package name, instrument counts, and per-name lists, but never a Skald version, a source-JSON hash/timestamp, or any other value that would let a reader determine "was this file produced from the `.skald.json` sitting next to it, or from an older/different one." A search of the whole backend for `version`/`schema_version`/`GENERATOR_VERSION`-style constants returns nothing.
- **detail**: This is the flip side of F-B05-1: because nothing in the generated artifact records what produced it, staleness (or a hand-edit made to work around a bug, then silently discarded on next regen) is undetectable by inspection — the only way to know a file is out of date is to regenerate it and diff, which is exactly the step that evidently isn't happening for the example files. It also means a game team integrating a `.odin` file into their own build has no way to answer "is this current" without re-running `codegen.exe` themselves and comparing.
- **suggested fix**: Add a one-line stamp near the top of the generated header — e.g. a hash of the input JSON plus a codegen build/version identifier — and add a `// AUTO-GENERATED — changes will be overwritten by the next codegen run` banner (the current header reads as descriptive documentation, not a warning) so a hand-edit-then-regenerate loss is at least a conscious, visible risk rather than a silent one.

### F-B05-8: No manual chapter or dedicated reference documents the generated Odin API itself
- **kind**: missing-feature
- **area**: documentation
- **severity**: medium
- **confidence**: high
- **evidence**: `docs/manual-source/` has 21 chapters — `00-foundations.md`, `50-bass-teardown.md`, `60-complexity-ladder.md`, and 18 files under `nodes/` (`adsr.md` through `wavetable.md`) — every one about the graph editor and node behavior. None documents the emitted `.odin` API contract, its lifecycle (`_init`/`_trigger`/`_process`/`_is_playing`), its threading expectations, or its versioning behavior. `examples/docs/` contains only `PRIVATE_WEB_APP_SETUP.md`, `RELEASING.md`, and a release-notes file — nothing API-facing either. The only documentation of the generated surface anywhere in the repo is scattered inline comments in `codegen.odin` (accurate but written for Skald's own contributors, not integrators) and the one `examples/integration_demo/README.md`.
- **detail**: For a tool whose stated purpose is producing DSP source code a game consumes, the *node graph* — the authoring surface only Skald's own users touch — is documented exhaustively, while the *artifact a game engineer actually receives and has to integrate* has no chapter at all. A game programmer handed a `.odin` file and told "here's the audio, wire it up" has to reverse-engineer the API from one example project's README and the generated comments, discovering by trial (or by reading source, which the tool's whole premise says they shouldn't need to) things like the alias mechanism (F-B05-6), the thread-safety gap (F-B05-3), or the rename-fragility (F-B05-4).
- **suggested fix**: Add one manual chapter (or a section of `00-foundations.md`) specifically for "Integrating the generated package": lifecycle calls, typed vs. string-keyed setters and when to use each, the `"<node_id>::<param>"` alias and who it's actually for (editor tooling, not games — currently undocumented that this is the intent), threading constraints once F-B05-3 is resolved, and what does/doesn't survive a regeneration.

### F-B05-9: examples/integration is a fully empty directory
- **kind**: qol
- **area**: examples
- **severity**: low
- **confidence**: high
- **evidence**: `find examples/integration -type f` returns zero results; the directory itself exists but is empty, while its near-identically-named sibling `examples/integration_demo/` contains the full working demo (`main.odin`, `README.md`, `_demo_project.json`, `build_and_run.bat`, `generated_audio/`).
- **detail**: Small, but exactly the kind of thing that reads as a broken or half-finished repo to a new integrator browsing `examples/` for "how do I hook this up" — a directory named `integration` that contains nothing, right next to the one that does. It's either dead scaffolding left over from a rename/restructure, or a placeholder someone intended to fill and didn't; either way it costs a confused few minutes to whoever finds it first.
- **suggested fix**: Delete the empty `examples/integration/` directory, or if it was meant to hold something distinct from the demo (e.g. a minimal/no-audio-device "just the API calls" snippet), populate it and cross-link it from `integration_demo/README.md`.

### F-B05-10: No NaN/Inf or out-of-range guard on the actual shipping per-asset output path
- **kind**: risk
- **area**: generated API — output safety
- **severity**: medium
- **confidence**: medium
- **evidence**: The only NaN/Inf/range check anywhere in the integration demo is inside `run_silent_test`, which only runs under `-mode:silent-test` (`examples/integration_demo/main.odin:296-313`, explicitly framed as "Useful for CI / smoke without an audio device," `:293-295`). The real playback paths — `audio_callback` (`:173-187`) and `producer_thread` (`:191-229`) — write `Sfx_process`/`Layer_process` output straight into the ring buffer and out to the device with no check at all. Nothing in `codegen.odin`'s emitted `_process` clamps or sanitizes its return value either (only `project_process` gets a `tanh`, and per F-B05-2 the recommended per-asset integration path skips `project_process` entirely).
- **detail**: Certain patch configurations (e.g. an SVF filter driven to instability at extreme cutoff/resonance combinations, or the sample-rate-division-by-zero case if `_init` is skipped or called with `sr=0`) can produce `NaN`/`Inf`/wildly-out-of-range samples. In the CI smoke test this is caught and reported; in an actual shipped game, following the actual recommended per-asset integration pattern, the same condition would reach the audio device directly — at best an audible artifact, at worst (depending on platform/driver behavior with non-finite floats) a hardware pop or a crash in the platform's audio stack.
- **suggested fix**: Move the NaN/Inf/range check from being a demo-only CI convenience into the generated library itself — either sanitize (`is_nan/is_inf → 0.0`) at the end of every generated `_process`, or expose it as an opt-in `_process_safe` variant, so the safety net exists in code every consumer links against rather than only in the one file nobody ships.

## Verdict — could you ship a game with this today?

Mostly, for a narrow, non-adaptive use case: fire-and-forget SFX and a looping music layer with one or two exposed knobs, on a single thread, is exactly what `examples/integration_demo` demonstrates, and it works. The core DSP loop is real-time safe (no allocation in any `_process`), the note-lifecycle API is sound, and the typed/string setter split is a genuinely good piece of design for supporting both hot game code and tooling.

What would stop a real ship: (1) no runtime master/instrument volume (Tier 1's F-A05-8) compounded by the fact that even the mechanism that *does* carry it (`project_process`) is bypassed by Skald's own recommended integration pattern, so there is currently no path from "the sound designer set the mix in the editor" to "the game hears that mix" (F-B05-2); (2) the example you'd actually copy from is stale relative to the generator that made it, reintroducing a fixed audio glitch (F-B05-1); (3) zero documented or enforced thread-safety contract for the one thing every game needs to do continuously — tune parameters from gameplay code while audio renders on another thread (F-B05-3); and (4) a routine content edit (renaming an asset, tweaking an unrelated node) can silently break the game's build against the generated symbols with no warning (F-B05-4). None of these are large engineering lifts individually, but together they mean the boundary between "the editor" and "the game" — the entire reason Skald exists — is the least finished, least documented, and least defended part of the tool.
