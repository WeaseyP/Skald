# Skald 0.2 — Roadmap

Compiled 2026-08-01 from a 27-agent audit (259 findings across four tiers), reconciled against
`docs/CODEX-REMEDIATION-BRIEF.md`, `docs/proposals/bpm-ux.md`, `BUGS.md` and `CHANGELOG.md`.
The live bug frontier lives in `BUGS.md` (rewritten alongside this document); this file is the
plan. Every claim below carries a `file:line` citation or a finding ID; the full finding index
is the appendix.

---

## 1. Verdict

**Skald 0.2 is not releasable today, and the reason is not missing features.** The audit found a
tool whose individual nodes are well implemented, whose DSP emission is clean (a kitchen-sink
graph of every node type compiles with zero errors — F-B04 summary), whose golden/FFT test
harness is better than most projects this size have (F-C4-12), and whose manual is unusually
rigorous. What it also found is that **the artifact the user runs is not the artifact the tests
test**, and that controls, generated APIs, examples, previews and manual all make claims the
shipped code does not honour.

The single worst fact, which no tier-1 or tier-2 agent found because all 22 of them tested the
compiler built from source rather than the one the app spawns: **the codegen binary committed to
git and executed by the app (`skald-ui/skald_codegen.exe`, tracked via `.gitignore:7`) is dated
2026-07-24 — nine commits to `skald-backend/core/` (51 repository commits) behind HEAD** (F-C1-1,
F-C3-1, F-C4-1). It predates the `"<nodeId>::<param>"` set_param alias the live preview addresses
every knob by (`useWasmAudioEngine.ts:255-262`), so **in the committed tree, dragging any exposed
parameter during playback does nothing at all** — the worklet discards the failed `set_param`
(`skaldWasm.worklet.ts:114`) and the topology signature masks the value so no rebuild fires
(`projectSerializer.ts:236-248`) (F-C4-2). The same stale binary re-introduces the voice-steal
click that was fixed in source, and per C4's A/B runs it also predates the Reverb pre-delay and
Mixer exposed-level fixes — which is why every checked-in `generated_audio.odin` is stale
(F-B05-1) and why "the manual is pessimistically stale" turned out to be only partly true: for a
user of the committed app, several of those warnings are still operationally correct.

Compounding it, **the audited tree is not the committed tree** (§3.2): the fresh
`skald-backend/codegen.exe` every tier-3 agent used as empirical ground truth is untracked and
exists only on this machine, and so do the manual the audit measured the code against and two
source modules imported by shipped code. No second party can reproduce this audit, and no release
can be cut from this tree as it stands.

Beyond that headline: a master volume of 0 exports as full volume (F-A05-1); the generated API
advertises setters the DSP provably never reads (F-B02-1, verified in emitted code); the CLI path
that 100 of 101 shipped example files take silently discards their authored tempo, master volume
and every P-lock (F-C3-2, F-C2-7); regenerating the same file can reassign which instrument is
asset 0 (F-B04-1 — six distinct byte-outputs from fourteen runs of one shipped file); Load is a
one-click, unrecoverable destruction of the session, and one Ctrl+Z immediately after Load
destroys the just-opened project's sequencer data (F-C4-5, F-B06-2); and the recommended game
integration path drops both the authored mix and the only limiter in the system, so Skald's own
default patch hands a game samples peaking at 2.28–3.93 (F-C2-1, measured).

The three tier-3 assessments of scope agree more than they appear to. C2 costed the audio
composition fixes at roughly a week and is right — none of them is architectural. C3 said the
pipeline is not fit to ship and is also right — but its "seams" (binary provenance, one ingestion
path, determinism, a schema version) are small, ordered work, not a rewrite. C4's two-focused-weeks
estimate covers its trust/onboarding list; C5's four-wave plan covers everything. **Reconciled:
0.2 is roughly three to five focused weeks of well-ordered work — Wave A (gates, provenance,
determinism, cheap wins) then Wave B (the blockers) — and it should be framed internally as a
release about honesty, not capability** (C5's framing, adopted). Nothing on the blocker list is
hard; everything on it is the difference between a very good prototype and a tool someone can
trust with a day's work.

    (F-B09b-2), 4 specific claims struck inside otherwise-valid findings. 40 of the 54 tier-1/2
    highs survive at severity.** A corrected finding appears here only in its corrected form.
    **One C1 verdict was itself overturned by the adversarial pass (D2)** and must not be
    propagated: C1 endorsed F-B04-2's claim that the recursive subgraph parser
    (`json.odin:203-222`) is "dead code for the real product." It is not — those lines are the

  - **C2 (interactions)** measured gain/composition failures with a real harness and real numbers.
  - **C3 (architecture)** mapped the pipeline's seams (four representations of a patch, nothing

  - **C5 (scope)** produced the wave plan this roadmap uses as its skeleton.

## 3. The critical set

These are the nine tier-3 criticals plus what C1's verification elevated, consolidated where they
are one problem — plus two found *after* the audit by the adversarial pass (D2) and coordinator
verification (§3.2 tree state, §3.12 packaged installer), which no tier agent examined. Each item
names its impact, its fix, and its wave packet (§5).

### 3.1 Binary provenance — one problem, many symptoms *(critical · S · packet A2)*

`skald-ui/skald_codegen.exe` is a tracked build artifact (`.gitignore:2` ignores `*.exe`, `:7`
un-ignores this one) that the app spawns for both preview and Generate (`main.ts:70-73`,
`forge.config.ts:20`). It is nine backend-core commits stale. CI builds its own binary from
source and never looks at this one (`.github/workflows/ci.yml`), so the green badge certifies a
compiler users do not run. Consequences traced and verified:

- **Every exposed-parameter knob is a silent no-op during preview** in the committed tree — the
  core loop of the product, dead (F-C4-2; mechanism above). It resumes working after any
  unrelated rebuild, so it reads as intermittent — the worst failure shape for trust.
- The **voice-steal anti-click fix is un-shipped**: the stale binary emits the old unconditional
  hard reset (A/B diff, F-C3-1), which is exactly the defect found in all six checked-in
  `generated_audio.odin` copies (F-B05-1) — root cause, not coincidence. Regenerating the
  examples without fixing the binary reproduces the staleness.
- Per C4's A/B on the repo's own fixtures, the shipped binary also predates the Reverb pre-delay
  (P1) and Mixer exposed-level (P3) fixes — so those fixes are "written but not delivered."

**Fix:** stop tracking the binary; make `start`/`make` depend on `build:codegen` (rebuild is
sub-second, Odin is already vendored in `.tools/`); add a `-version` build stamp and a
renderer↔binary handshake that refuses to start the preview on mismatch; add a CI job that
rebuilds and fails on diff if the exe ever reappears in the index. Until this lands, nothing
anyone measures is what users run — it is Wave A, day one.

### 3.2 The audited tree is not the committed tree *(critical · S · packet A1)*

Found in the coordinator's final verification pass; it outranks most of what is in the tiers.
`git status` against the audited working tree shows **17 untracked paths and 10 modified files**,
including:

- `skald-backend/codegen.exe` (1,161,216 bytes) — the freshly built compiler that **C1, C2, C3
  and C4 all used as empirical ground truth** — is untracked and exists only on this machine.
  The only `.exe` git tracks is `skald-ui/skald_codegen.exe` (1,153,536 bytes, 2026-07-24): the
  stale one (§3.1).
- Two source modules **imported by shipped code** — `stepMetrics.ts` (imported by
  `SequencerToolbar.tsx`) and `useElementWidth.ts` — are untracked. A clean clone does not build
  the same product.
- The entire `docs/manual-source/` chapter set — **the specification this whole audit measured
  the code against** — is not under version control. Neither is `examples/snes-kit/` (9 patches)
  nor `docs/CODEX-REMEDIATION-BRIEF.md`, the previous plan of record.

Consequences, stated plainly: **no second party can reproduce this audit** (its empirical
baseline binary and its specification exist on one disk); **no release can be cut from this
tree**; and every conclusion in this document is one `git clean` away from being unverifiable.
A few untracked paths are expected — `docs/manual/`, `scripts/manual/`,
`src/main/dialogDefaults.ts` and its test were created by the coordinator during the audit —
the pre-existing ones are the problem.

**Fix (packet A1, day one, before anything else):** commit the manual sources, `snes-kit/`,
`stepMetrics.ts`, `useElementWidth.ts` and the brief; resolve the 10 modified files into
deliberate commits; add a CI step that runs `git status --porcelain` after a build and fails on
untracked files under `docs/`, `examples/` or `skald-ui/src/`.

> **Status 2026-08-01 — mostly done.** The tree is committed on `review-fixes` in eight commits
> (`3a4ab40`..`e941703`): the 22 manual chapters and `scripts/manual/`, `examples/snes-kit/`, the
> CODEX brief, both untracked source modules, the sequencer and Import-Patch work, and these three

### 3.3 The exposed-parameter path fails silently at every layer *(critical-adjacent · S · packet A6)*

Independent of the stale binary, the design that made it invisible must be fixed:
`canApplyParamLive` is a byte-length check only (`projectSerializer.ts:227-228`) while the
instant path adds three more conditions, and the worklet ignores `skald_set_param`'s return value
— the file's own comment states the invariant this violates (`projectSerializer.ts:230-235`)
(F-C1-3). One reachable instance already exists: **`syncRate` is exposable in one click**
(`NodeParameterControls.tsx:159/:172/:185` omit the `false` flag), which emits a dead ±1e6 setter
into the public API *and* makes the Sync Rate dropdown permanently inert in the preview (F-C1-2).
**Fix:** worklet posts an error on a dropped set-param and the UI surfaces it like `previewStale`;
`canApplyParamLive` takes the value; worklet name-buffer 64→128 (and fix
`WasmWorkletGuard.test.ts`, which locks the wrong number in green — F-B08-5).

### 3.4 Codegen non-determinism *(critical · S · packet A3)*

`build_project_from_graph` iterates `map[string]Node` unsorted (`json.odin:303`, `:331`) against
the codebase's own three written warnings (`graph_utils.odin:9-14`). Fourteen runs of the
unmodified `four-bar-song.skald.json` across two independently built binaries produced **six
distinct byte-outputs**, and the wasm shim's integer asset index permutes with them —
`skald_note_on(asset, …)` addresses a *different instrument* per regeneration (F-B04-1, verified
and extended by C1). **Fix:** `nodes_sorted_by_id` in both loops (one hour), plus a
double-run determinism gate in `run_golden.bat` so the *next* violation fails CI (F-C3-3). This
is a hard prerequisite for every refactor whose safety net is "regenerate and diff," and for any
golden gate over `examples/`.

### 3.5 Two readers of `.skald.json`; the one 100 of 101 examples take discards the session *(critical · S+M · packet A4)*

The CLI sniffs the format (`main.odin:51-75`); bare-graph files — the shape of every editor save
and 100/101 shipped examples — hardcode `bpm = 120`, `master_volume = 1.0`, `pattern_steps = 0`
(`json.odin:298-299`) and never read the `session` block the editor writes (`useFileIO.ts:76`).
Verified: a 140 BPM patch generates `p.bpm = 120` (F-C3-2). Separately, the Odin unmarshaller
matches `patch_overrides` and save files write `patchOverrides`, so **every P-lock in every
editor save is silently dropped on the CLI path** (F-C2-7, F-C1-5). `examples/AUDIT.md` certified
the corpus through exactly this lossy path. **Fix:** read `session` and accept the
`patchOverrides` alias on the graph path (the ~20-line stop-the-bleeding change), then collapse
to one constructor by making the graph path a normalizer into `build_project_from_raw`.

### 3.6 Master gain needs one decided design, not four patches *(critical · M · packet B1)*

Four confirmed defects share one cause — `master_volume` is a compile-time literal fused into the
limiter with no runtime setter (F-C1-8 consolidates F-A05-1, F-A05-8, F-B05-2, F-B08-1):

- `master_volume: 0` exports at **full volume** (`codegen.odin:2455-2456` treats `<= 0` as
  "absent"; `projectSerializer.ts:110` sends the raw slider value while `:199` floors instrument
  volume *with a comment explaining this exact hazard*).
- Preview plays `vol·tanh(x)`, export plays `tanh(vol·x)` — the export is **always louder and
  less saturated** than what was tuned by ear (C1's corrected statement; at vol 0.5 and peak 2.0:
  preview 0.482 vs export 0.762, +4 dB).
- The recommended per-asset integration path never calls `project_process`, so games get neither
  the authored mix nor the limiter; the shipped demo substitutes an unexplained `* 0.6`
  (`integration_demo/main.odin:211-212`).
- There is no runtime volume setter of any kind (`grep set_master_volume` → nothing).

**Fix (one shape closes all four):** `master_volume` becomes a real field with
`project_set_master_volume`; the limiter becomes a standalone `skald_soft_limit(l, r)` the
per-asset path can call; the dock slider drives the shim param instead of a post-worklet JS
`GainNode`. Roughly a day; it is the boundary the whole product exists to cross.

### 3.7 No gain structure anywhere on the path games use *(critical · M · packets B1/B7/B10)*

Measured on the per-asset path (F-C2-1): the manual's canonical default chain peaks at 0.53 (one
note), **1.61** (four), **2.28** (eight), **3.93** with default Distortion; the flagship song
runs 7.9 dB into the master `tanh` as its normal operating point. There is no meter, no clip
indicator, no dBFS readout anywhere in the editor (F-C2-12). **Fix:** the B1 gain/limiter split
above; a per-`_process` soft-limit option; a stereo peak-hold meter with clip LED tapped *before*
the JS master gain (~60 lines); a stated gain contract in Foundations. Deliberately **not**
fixed: auto-normalizing the voice sum (worse than clipping — C2's call, adopted).

### 3.8 Load and undo are not a safety net *(critical · M · packets B3/B4)*

Load replaces the canvas with no dirty check, no confirmation, no title-bar filename, no
autosave, and clears the only undo stack that could recover it (`useFileIO.ts:114-136`; no
`confirm(` anywhere in `skald-ui/src`). Worse — C1's verified one-keypress path: Load clears only
the *graph* stack while `loadTracks` **pushes** the pre-load tracks onto the sequencer stack
(`useSequencerState.ts:169-172`), so a single Ctrl+Z after Load swaps in the previous project's
tracks and the registry prunes them as orphans — **every note in the just-opened project gone,
unrecoverably** (F-B06-2 as strengthened by C1). Undo itself fails seven distinct ways (two
stacks popped by one keystroke, drag snapshots one tick late, palette drop / Import / Export-Step
untracked, transport untracked, wall-clock coalescing — F-C4-6 consolidating eight findings).
**Fix:** one history stack of `{nodes, edges, tracks, session}` snapshots behind a single
`pushHistory`; the four missing call sites; snapshot on first drag tick; dirty flag + confirm +
window title + 30 s autosave/recovery + atomic save.

### 3.9 The first hour *(critical · M · packet B6)*

26 of 101 shipped examples have no Instrument node and produce a red *Preview failed* banner on
Play — including the two files the manual's spine chapters open with; the Load dialog opens on a
tree that ships `archive/PulsarBeam.json` (hard-fails codegen, verified) and a folder named
`to implement` (F-C4-3, F-B06-5). The README's only two links 404; the manual — the project's
best asset — is untracked in git, unpackaged, and unreachable from the app (F-C4-4, F-C1-6).
**Fix:** auto-wrap loose graphs on load (the backend already does this for the CLI —
`json.odin:309-326`); exclude `archive/`/`to implement/` from packaging; curate `start-here/`;
fix the links; commit and package the manual; add a Help menu; ship a default first-run patch.

### 3.10 The handoff to a game is the least finished part of the tool *(critical · M · packets B1/B12)*

No thread-safety contract anywhere (setters are unguarded field writes; the manual contains zero
occurrences of "thread" — F-B05-3); no provenance stamp in generated output and blind overwrite
(F-B05-7); symbols rename under cosmetic edits and un-exposing node B renames node A's setter
(F-B05-4, F-C3-10); no chapter documents the generated API at all — 21 chapters on the authoring
surface, zero on the deliverable (F-B05-8). **Fix for 0.2:** one sentence of thread contract
emitted into the header ("all `_set_*` calls on the thread that calls `_process`"); header lists
each asset's exposed params (data already computed at `codegen.odin:1691-1703`); AUTO-GENERATED
banner + build stamp + input hash; write the integration chapter (Wave D). Stable `exportId` is
Wave C (needs the schema version).

### 3.11 Process: findings don't get fixed because they are prose *(critical · M · §8)*

C5's process finding, adopted with C1's numeric correction. See §8 — the four CI gates and the
Wave-A-must-be-green rule are release blockers in their own right.

### 3.12 The shipped installer cannot preview audio for anyone *(critical · S · packet A13)*

Found by D2 in the final pass; **zero of the 27 audit agents examined the packaged artifact**, so
this sits outside the 259 and was never severity-rated by the tiers. Verified directly:

- `forge.config.ts:20` — `extraResource: ['./skald_codegen.exe', '../examples']`. **No Odin
  toolchain is bundled.** Preview compiles Odin at runtime, so a packaged install cannot preview.
- `main.ts:178` — `findOdin` probes exactly `SKALD_ODIN`, `odin`, `C:\Odin\odin.exe`. The repo
  **vendors a working toolchain** at `.tools/odin-dev-2025-02/odin-windows-amd64-dev-2025-02/odin.exe`
  and the resolver never looks there.
- `scripts/setup-dev.ps1:78` — `$env:SKALD_ODIN = $odinExe.FullName` is **process-scoped**. It is
  not persisted to the User or Machine environment, so it evaporates when the setup shell closes,
  which is the same shell the script tells you to close.

Net effect: a user who installs v0.1.0, and a developer who follows the documented setup and then
opens a new terminal, both get an editor whose central promise — hear it before you ship it — is
silently unavailable. The failure is a missing compiler, reported (if at all) as a build error.

**Fix (S):** add `.tools/**/odin.exe` to `findOdin`'s candidate list ahead of `C:\Odin\odin.exe`;
persist `SKALD_ODIN` at User scope in `setup-dev.ps1`; and either bundle the toolchain via
`extraResource` or fail loudly at first launch with an actionable message naming the vendored path.

**▲ Ordering hazard — this gates a fix three separate findings recommend.** F-C1-1, F-C3-1 and the
Wave A provenance packet all propose *deleting the tracked `skald_codegen.exe` and building it on
`prestart`*. That is correct, and it is dangerous if landed first: today a stale compiler means
"exposed-parameter knobs silently do nothing in preview"; with no resolvable Odin and no checked-in
binary it becomes **"the app does not start"** for the documented setup path. **A13 lands before
A2's untracking step.** See §4.8.

## 4. Ordering constraints (the dependency spine)

C5's DAG, corrected by C1 and C3. These are rules, not suggestions; each was violated by at
least one prior remediation round.

1. **Wave A must be fully green before any Wave B packet is assigned.** The CODEX brief already
   put cheap architectural work first and it still did not happen; ordering alone is
   insufficient — completion is the gate (F-C5-9).
2. **Nothing that regenerates-and-diffs generated code starts before determinism (A3) lands.**
   That includes the `codegen.odin` split and any golden gate over `examples/`.
3. ▲ **The examples-in-CI gate**: land it in Wave A as an *exit-code + `odin check`* gate — but
   sequence the one-hour determinism sort first, and **spec it per F-C3-11, not per F-B11-1**:
   the obvious CLI loop exercises `build_project_from_graph` — the wrong path for 100 of 101
   files — and would certify output silently retimed to 120 BPM with all P-locks dropped. The
   corrected gate runs each file through the real `parseSaveFile` → migrations →
   `buildProjectData` → codegen → `odin check -no-entry-point`, asserts the emitted `p.bpm` and
   tanh coefficient match the file's `session`, and keeps a small separate CLI-path gate for the
   fallback parser. **No diff/golden gate over examples until A3 + A11.**
   *(Resolution of the C5-vs-C1/C3 disagreement: C5's "smoke gate is independent of determinism"
   is true for exit codes but its spec tested the wrong ingestion path and certified less than it
   appeared; C1/C3's corrections win on spec, C5 wins on timing because the determinism fix is
   one hour, not a blocking workstream.)*
4. **No schema-touching change before the version field + migration registry (C1).** That gates:
   multiplicative VCA gain, explicit assetType, exportId, Wavetable backfills, keyTrack-shaped
   anything, and auto-wrap-on-*save* (auto-wrap on load/Play without saving is allowed earlier).
5. **Do not split `codegen.odin` before A3 + A11** (byte-identical corpus diff is the proof).
   Do not re-pin manual citations before the split — that would re-pin 828 citations twice.
6. **Do not wire `renderBpmSyncToggle`** (the dead expose affordance, F-A03-4) before the
   exposure-honesty packet (B2) — wiring it first converts a latent bug into a reachable one
   (F-B02-3).
7. **Do not rewrite manual chapters before code freeze** (Wave D), with the one exception of the
   gated false-pessimism sweep (A10).
8. ▲ **Fix Odin toolchain resolution (A13) before untracking the codegen binary (A2).** Three
   findings independently recommend deleting the tracked `skald_codegen.exe` and building it on
   `prestart`. Correct, and unsafe in the wrong order: with no bundled Odin, no `.tools/` lookup in
   `findOdin`, and no checked-in binary, the documented setup path goes from "preview silently does
   nothing" to "the app does not start." See §3.12.

thing, maintained separately, with nothing reconciling them — and it has already fired once, on
`docs/manual-source/70-space-funk-build.md` ("Building *Space Funk* From Nothing", 48 KB), which was
written and then left out of a build unnoticed.

## 8. Process — why findings historically don't get fixed

The evidence (F-C5-9, F-B09a-4, C1's re-verification): the prior health review's **discrete bug
list — all 30 items — is durably fixed with zero regressions**, while its architecture and
hygiene findings written as prose in reports overwhelmingly persist into a tree whose backend has
since tripled in size. (C1's sampled re-verification of those prose findings: roughly 60%
verified-live, 25% vacuous or unfalsifiable, 15% wrong or since-fixed. The "111 of 119" aggregate
is refuted; the pattern is not.) Meanwhile the CODEX brief is ~1.5 of 5 waves done — W1 and half
of W3 landed while W0's one-line warm-up, all of W2, and W3's B6/B7 stayed open. The same
BPM-sync defect was found in three successive rounds, one layer up each time. `sax3.json`
survived two rounds untouched.

**Severity has demonstrably not predicted what gets fixed; checkability has.** Everything that
got fixed fits in one file, has a pass/fail check, and was written as a packet with an ID.
Everything that didn't lacks at least one of those. It follows that producing finding #200 is
worth approximately nothing and closing #1 is worth a lot. Hence:

1. **CI gates, not tickets.** The four recurring classes become red builds: examples corpus
   (A5), range parity (A8), generated-example freshness (A2), citation drift (A9). A finding is
   a ticket nobody does; a failing CI step is a thing that must be done.
2. **Wave A must complete before Wave B assignment.** Ordering alone already failed once;
   completion is the gate.
3. **Track packet state (`assigned / landed / verified`), not finding severity.** Review the
   unassigned list before the unfixed list.
4. **Moratorium on new audits** until the Wave A + Wave B packet list is executed and verified.
   This review added 199 tier-1/2 findings on top of a still-live backlog; the marginal value of
   another pass is ~zero.
5. **Split `codegen.odin` in Wave A (A12) or explicitly accept sequential execution.** The file
   is the global lock that made the last plan serial, and serial execution is why it is 1.5/5
   complete. This is the throughput argument the monolith finding always lacked.
6. Lift the CODEX brief's golden-file discipline ("acceptance must pass; read the golden diff;
   only then update, in the same commit") and stop conditions verbatim — they are the best
   process text the project has.
