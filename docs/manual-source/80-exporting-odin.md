# Exporting Odin and wiring it into a game

> The whole of Skald exists to produce one text file. This chapter is about that file: what is in it, what you are allowed to call and from where, and what happens to your game's build the next time the sound designer presses the button.

## Who this chapter is for

Two people, reading it from opposite ends.

If you are the **game programmer**, someone has handed you a `.odin` file and told you it is the audio. You have never opened Skald and you do not need to. Everything you must know — the procedures to call, the order to call them in, the thread you may call them from, and what breaks when the file is regenerated — is in this chapter and in the header comment at the top of the file itself.

If you are the **sound designer**, this is the chapter you send them. It is also the chapter that tells you which of your editor decisions are visible to the game (an **exposed** parameter, an **Export ID**, an asset's Type) and which are baked into the generated source and therefore only changeable by regenerating.

Nearly every other chapter in this manual tells you to "expose" something without ever showing you where an exposed parameter goes. It goes here.

## What you get

One file. One Odin package. No dependency on Skald, no runtime library, no data files: the generated source imports only `core:math` and `core:math/rand`, both from Odin's own standard library (`skald-backend/core/codegen_project.odin::generate_project_code`). Drop the file into your project, `import` it, and it compiles.

The file has three parts, in this order:

1. **The package line and the header comment.** The header is not decoration; it is the API reference, generated from the same analysis as the code below it, and it is the one artefact an integrator will actually read.
2. **Shared helpers** — a small xorshift PRNG for Noise nodes, the `ADSR_Stage` enum, the wavetable shapers, `skald_soft_limit`, the `Note_Event` and `Skald_Param_Info` structs, and (only when some asset has a Delay or Reverb) `skald_feedback_tail_seconds`. These are emitted once for the whole file.
3. **One section per asset.** For an asset called `Sfx` you get `Sfx_Voice_State`, `Sfx_Processor`, and then every procedure whose name starts `Sfx_`. Assets do not share state and do not call into each other.

At the very bottom there is a `project_init` / `project_process` / `project_destroy` wrapper. **Ignore it.** It exists for Skald's own test harness, it allocates with `new`, and the header says so in as many words. Game code drives the per-asset procedures directly.

### Choosing the package name and the output path

In the editor, the sidebar's **Generation** section has a **Package Name** text field (placeholder `generated_audio`) and a **Select Output File** button, then the primary button — **Download Code** (`skald-ui/src/components/Sidebar.tsx::Sidebar`). The package name defaults to `generated_audio` and is saved with the project, so it survives a reload (`skald-ui/src/hooks/nodeEditor/useSessionSettings.ts::DEFAULT_SESSION`).

The button is named the way it is because it no longer generates anything new: the live preview has been compiling and running this exact generated code on every edit since the WASM preview landed. Download Code only writes the `.odin` out for you.

From a shell or a build script, the same job is one command. The generator reads a project from `-in:` or, with no `-in:`, from standard input:

```
skald-backend/codegen.exe -in:my-patch.skald.json -out:src/audio/generated_audio.odin -package:generated_audio
```

`-name:`, `-package:`, `-in:`, `-out:` and `-wasm-shim:` are the flags; `-version` and `-check` are covered under "Preflight". With no `-out:` the generator writes `generated_audio.odin` into the current directory (`skald-backend/main.odin`). Never pass `-wasm-shim:` for a game build — that is the editor's file, discussed below.

### The header, from a real export

Everything below is an excerpt from the header of the integration demo's `generated_audio.odin`, generated from `examples/integration_demo/_demo_project.json`:

```odin
package generated_audio

// =====================================================================
// Generated by Skald.
// AUTO-GENERATED — DO NOT EDIT. Every hand edit here is lost on the next
// Generate; change the .skald.json in the editor and regenerate instead.
//   generator: skald_codegen fnv1a64:ce6d95bda37f0dc1
//   input:     fnv1a64:7d741c5a059f1f27
//
// SFX assets: Sfx
// Music Layer assets: Layer
//
// Game integration: import this package and use the per-asset APIs.
//   SFX:         <Foo>_init, <Foo>_trigger, <Foo>_process, <Foo>_is_playing
//   Music Layer: <Bar>_init, <Bar>_start, <Bar>_stop, <Bar>_process,
//                <Bar>_set_loop
// ...
// THREADING: every call on one asset — _init, _note_on, _note_off, _trigger,
// _start, _stop, _set_*, _set_param, _process, _is_playing — must come from
// the thread that calls that asset's _process. ...
// ...
//   Sfx
//     Sfx_set_cutoff   min 20  max 20000  default 800  unit Hz   (node 2, param cutoff)
//   Layer: (no exposed parameters)
// =====================================================================
```

Three things in there are load-bearing and are each pinned by a test, so you can rely on them being present in any file this generator produces: the `AUTO-GENERATED` banner with its two digests (`skald-backend/tests/unit/provenance_test.odin::test_header_carries_banner_stamp_and_input_digest`), the threading rule (`::test_header_states_the_thread_rule`), and the per-asset list of exposed parameters with their concrete setter names, ranges, defaults and units (`::test_header_lists_each_assets_exposed_params_and_both_setter_styles`). That last list is emitted from the very same plan the setters and the `_PARAMS` table come from (`skald-backend/core/codegen_project.odin::emit_exposed_param_contract`), so the header cannot advertise a setter the body does not have.

### The second shape you may see, and must not ship

Skald emits **two** files from one analysis. The game-facing package is one. The other is a `@(export) skald_*` WebAssembly shim used only by the editor's own preview — it holds each processor in a file-private global, renders in 128-sample blocks, and addresses assets by integer index (`skald-backend/core/codegen_project.odin::generate_wasm_shim_code`). Its own header says "Not part of the game-facing API; do not ship this file." If you have been handed a file whose procedures are called `skald_init` and `skald_trigger(asset: i32, …)`, you have the wrong file; ask for the one with `<Asset>_` prefixes.

## Bouncing and stems

Not every game wants generated source. A jam build, a trailer, a mobile title with no room for a synthesis runtime, or a composer who wants the loop in their DAW — all of them want audio, not Odin. Skald renders it from the same place the preview plays from: a full mix, or one file per instrument.

**Bounce to WAV…** sits under **Download Code** in the sidebar's Generation section, with a **Bars** field and an **Include tail** tick (`skald-ui/src/components/Sidebar.tsx::Sidebar`). Press it and you get a 24-bit stereo `.wav` at 48 kHz (`skald-ui/src/hooks/nodeEditor/useOfflineBounce.ts::BOUNCE_SAMPLE_RATE`) — on the desktop app through a save dialog, in the browser as a download.

### It is the same audio, not a second opinion

The bounce is not a re-implementation of the mix. It builds the WebAssembly module from the identical project description the preview builds from and then calls `skald_process` in a loop, reading the same two output buffers the AudioWorklet reads (`skald-ui/src/audio/offlineRender.ts::renderOffline`). Everything on the master bus — the sum of every asset, the master fader, the DC blocker, the soft limiter, in that order — happens *inside* `skald_process` (`skald-backend/core/codegen_project.odin::generate_wasm_shim_code`), so the bounce gets all of it by construction rather than by re-deriving it. A fixture drives one set of wasm exports through the real worklet source and through the bounce and requires the two buffers to be sample-for-sample equal (`skald-ui/src/tests/audio/OfflineRender.test.ts::renderOfflineChunked`).

It is also faster than realtime, and that is not a trick either. The generated module has no wall clock: `skald_init(sample_rate)` seeds the float the step counter divides by, and time advances only by the frames you ask for. A sixteen-bar render costs whatever your CPU takes, and produces the sample values realtime playback would have produced.

### Length, and the tail

**Bars** is whole bars at the project tempo, sixteen sequencer steps to the bar, and it opens on however many whole bars your pattern occupies (`skald-ui/src/audio/offlineRender.ts::barsForPatternSteps`). The range is 1 to 64. Looping is forced on for the bar count regardless of the transport's Loop button — you asked for eight bars of a four-bar pattern, so you get the pattern twice, not four bars and four bars of silence.

**Include tail** keeps rendering after the last bar. The sequencer is stopped, and the render continues while anything is still audible: voices in their release stage, a Delay still echoing, a Reverb still decaying — the same `_is_playing` that tells a game when it may free an asset (`skald-backend/core/codegen_processor.odin::generate_processor_code`). A patch that never goes quiet — a self-oscillating filter, a Reverb at full feedback — is cut off at thirty seconds of tail rather than rendering forever (`skald-ui/src/audio/offlineRender.ts::MAX_TAIL_SECONDS`).

### What the file is

A canonical 44-byte RIFF/WAVE header, PCM format tag, two channels, 24 bits per sample, little-endian (`skald-ui/src/audio/wavEncoder.ts::encodeWav24`) — the same chunk layout the acceptance harness's own writer uses (`skald-backend/acceptance/wav.odin::write_wav16`), widened from 16 bits. Nothing is added on the way out: no dither, no normalisation, no extra gain. A sample outside ±1 is clamped rather than allowed to wrap into a full-scale click, and a NaN or infinity becomes silence — the same thing the DC blocker and limiter already do with one on the live bus.

The bounce writes atomically, for the reason Save does: the new file lands beside the target and is renamed over it, so a failed write cannot destroy the bounce you made yesterday (`skald-ui/src/main/atomicSave.ts::atomicWriteFileSync`).

### Stems

**Export Stems…** sits beside it and writes one `.wav` per Instrument plus `master.wav` into a folder you choose (`skald-ui/src/hooks/nodeEditor/useOfflineBounce.ts::exportStems`). Same bar count, same tail setting, same 24-bit format. Two Instruments that share a name get distinct file names rather than one silently overwriting the other, and an Instrument called "master" does not collide with the mix (`skald-ui/src/hooks/nodeEditor/useOfflineBounce.ts::stemFileNames`).

**Mute and solo do not apply to a stem export, deliberately.** They are baked at generation time — a muted asset's `_process` is not even called from the mix (`skald-backend/core/codegen_project.odin::generate_wasm_shim_code`) — so honouring them would hand you a folder with silent holes in it wherever you had muted something while working. The stem build clears them, as a serialiser option and nothing more: your tracks are not modified, the mute buttons do not move, and nothing lands in the undo history (`skald-ui/src/utils/projectSerializer.ts::buildProjectData`).

**A stem is the instrument as it sounds in the mix, not as it sounds alone.** One module is built and rendered N+1 times; each stem silences every *other* instrument at runtime with `skald_set_volume` and leaves its own alone, so it keeps the level you set on that Instrument. It also passes through the master DC blocker and soft limiter, because those live inside `skald_process` and there is no way to reach a per-asset output without leaving `skald_process` — and that is the answer you want anyway: lay the stems back together in a DAW at unity and you get the master bounce, near enough that the difference is the limiter responding to a different sum. If you need an instrument at its raw pre-master level, solo it and use **Bounce to WAV…** instead.

In the browser build there is no folder picker and no zip: the stems download one after another.

### If a bounce fails

Every failure in the chain — no Instrument on the canvas, a generator or compiler error, a permission error on the write — is reported in the same banner Save and Download Code use (`skald-ui/src/hooks/nodeEditor/useOfflineBounce.ts::useOfflineBounce`). A bounce that fails silently behind a spinner would be worse here than anywhere else in the editor, because the user has already spent the wait.

## What an "asset" is

**One Instrument node in the editor becomes one asset in the generated file.** Nothing outside an Instrument is exported at all — a loose chain of nodes on the canvas produces silence, and a project with no Instrument at all is a hard error rather than an empty file (`skald-backend/main.odin`). One asset per distinct sound your game triggers: a footstep, a laser, a bass layer, a pad layer are four assets, not one.

Two kinds:

- **One-shot SFX.** Your game fires it: `<Asset>_trigger`, or `_note_on` / `_note_off` if you want to hold notes. Its sequencer track, if it has one, is not emitted — the asset's `_process_sequence` is generated as an empty procedure.
- **Music Layer.** The asset carries its own sequencer pattern and plays it itself. `<Asset>_start` starts the pattern from step 0, `<Asset>_stop` halts it, `<Asset>_set_loop(p, false)` makes it play once and stop. The pattern is stepped from inside `<Asset>_process`, so you drive it exactly the same way you drive an SFX.

Which one you get is the Instrument card's **Type** setting, read straight from the save (`skald-backend/core/codegen_analysis.odin::detect_asset_type`). Only a file that never chose — Type left on *Auto* — falls back to the old inference: "does an unmuted, non-empty sequencer track point at this Instrument at Generate time" (`::active_sequencer_tracks`). That inference is why the Type field exists. Deleting the last note from a track used to silently turn a music layer into an SFX and change the API the game had been calling; now the classification is a setting, and the editor backfills it once for older files.

### The Export ID is the API's name

Every procedure in an asset's section is prefixed with the Instrument's **Export ID**: `Sfx_init`, `Sfx_trigger`, `Sfx_set_cutoff`. The card shows the field, shows the resulting `<ExportID>_trigger`, and its placeholder shows what the prefix would be if you leave it blank (`skald-ui/src/components/InstrumentNode.tsx::InstrumentNode`).

**Set it once, and renaming the Instrument afterwards never renames a symbol.** That is the entire purpose of the field: before it existed, the prefix came from the display name, so a sound designer tidying "Sfx" into "Player SFX" broke the game's build with no warning. An Export ID the author set wins; only when the field is empty is the prefix derived from the display name, exactly as older files did, so no existing export moved (`skald-backend/core/codegen_analysis.odin::instrument_export_prefix`, with the fallback in `::clean_instrument_name`; pinned by `skald-backend/tests/unit/asset_identity_test.odin::test_export_id_names_the_asset_not_the_display_name`).

The prefix is sanitised into a legal Odin identifier: every byte outside `[A-Za-z0-9_]` becomes `_`, and a leading digit gets an `n` in front (`skald-backend/core/param_utils.odin::sanitize_identifier`). So the shipped example instrument "808 Glide Sub" exports as `n808_Glide_Sub_init`, `n808_Glide_Sub_process`, and so on. An Export ID that sanitises to nothing usable — `---`, or a name with no Latin letters or digits at all — is treated as absent rather than emitting `____trigger` (`::has_usable_identifier_chars`).

**Two assets that would export under the same prefix stop the build**, naming both, whenever at least one of them pinned it (`skald-backend/core/codegen_analysis.odin::find_export_prefix_conflict`):

```
Error: instruments "Bass" and "Lead" would both export as "Keys". Give one of
them a different Export ID (the display name can stay as it is).
```

Two instruments whose *display names* collide and which pinned nothing keep the old silent `Keys` / `Keys_2` suffixing, so pre-existing files still generate what they always did (`skald-backend/core/codegen_project.odin::resolve_unique_names`). Pin your Export IDs and you never meet that behaviour.

### Which Instrument settings the game can see

Most of the Instrument's own controls are **structural**: they decide the shape of the emitted code, not a value it reads.

| Instrument setting | Where it lands | Runtime-settable? |
|---|---|---|
| `voiceCount` | the size of `voices: [N]<Asset>_Voice_State`, and the bound of every voice loop | no |
| `unison` | the size of each oscillator's `osc_<id>_phase: [N]f32` | no |
| `detune`, `glide` | literals inside the emitted DSP | no |
| `volume` | a real `p.volume` field, applied to both channels at the end of `_process` | **yes** — `<Asset>_set_volume`, clamped 0–1 |
| Export ID, Type | the symbol prefix and which lifecycle procedures matter | no |

There is no runtime way to change how many voices an asset has, because the voice count is an array size. If a game needs a chord bigger than the asset can play, that is a decision made in the editor and regenerated.

## The lifecycle

### `_init` — once, before anything else, and it is a full reset

```odin
Sfx_init :: proc(p: ^Sfx_Processor, sr: f32)
```

**You own the storage.** Declare the processor wherever you like — a field on your own struct, as the demo does (`examples/integration_demo/main.odin::App_State`), a global, or heap memory you allocated yourself. Nothing in the per-asset API allocates.

`sr` is your output device's sample rate in Hz, and the asset is tuned to it from that moment on: filter coefficients, envelope timings, delay-line reads and the sequencer's step length all divide by it. Pass the real device rate, not a guess.

`_init` clears everything — every voice, the transport counters, the PRNG seed, the bus-effect state and the delay ring buffers — and then writes each exposed parameter's editor value into its field. So calling it again is a clean restart, which is how you re-use one processor for a new level rather than allocating a second. It is also the reason **calling `_process` without ever calling `_init` produces garbage**: `sample_rate` is zero, and the oscillator's `freq / sample_rate` is an infinity that propagates into the output on the first sample. There is no assertion; the code does not check.

### Playing notes

```odin
Sfx_trigger  :: proc(p: ^Sfx_Processor, note: u8 = 60, velocity: f32 = 1.0, duration: f32 = 0.0)
Sfx_note_on  :: proc(p: ^Sfx_Processor, note: u8, velocity: f32, duration: f32)
Sfx_note_off :: proc(p: ^Sfx_Processor, note: u8)
```

`_trigger` is the fire-and-forget one, and every argument has a default, so `Sfx_trigger(&sfx)` is a legal middle-C hit at full velocity. With `duration <= 0` it computes a natural one-shot: the envelope is held through attack plus decay and then released. A patch with no envelope at all is given one second.

`_note_on` / `_note_off` are for held notes: pass `duration: 0` to `_note_on` and the note sustains until you call `_note_off` with the same note number. `velocity` is 0–1, **not** MIDI 0–127.

Both clamp, and both clamp *silently* — `note` to 0…127, `velocity` to 0…1. The header explains why: these are called at audio rate, where a diagnostic is not affordable. If you need to know your values were wrong, check them yourself. The clamp is applied on both sides on purpose: `note` is the key `_note_off` matches voices on, so clamping only the way in would leave `note_off(200)` unable to release the voice `note_on(200)` parked at 127, and that voice would stay active forever.

A note arriving when every voice is busy **steals** one: first the oldest voice whose envelopes are all in release or idle, and only failing that the oldest voice outright. The stolen voice's envelope level is handed to the new note's attack ramp rather than being snapped to zero, and its oscillator phase and filter memory are deliberately left intact, because zeroing them mid-waveform was an audible click on every steal.

### `_process` — the buffer contract

```odin
Sfx_process :: proc(p: ^Sfx_Processor) -> (f32, f32)
```

**One call, one stereo frame.** Left and right, in that order, as two `f32` return values. There is no block-oriented entry point in the game-facing API and no buffer for you to fill; the loop, the block size and the interleaving are all yours. If your device wants interleaved `f32` stereo, you write `out[i] = l; out[i+1] = r`.

The contract in full:

- **Sample rate** is whatever you passed to `_init`. `_process` never asks again.
- **Channels** are always two. Even a wholly mono patch returns the same value twice — a Panner is the only thing that makes them differ.
- **Block size** is one frame, always. Call it once per frame for as many frames as your device asked for.
- **Nobody allocates.** There is no `new`, `make`, `append` or `delete` anywhere inside a per-asset procedure (the only `new` in the whole file is in the test-harness `project_init`). It is safe in a real-time callback in the sense that matters most: it will not take a lock or hit the allocator.
- **Music Layers step their own sequencer** from the top of `_process`, so the pattern advances exactly in step with the audio clock and cannot drift against it.

If your game plays several assets at once, you call each asset's `_process` once per frame and sum the results yourself:

```odin
// excerpt — examples/integration_demo/main.odin, producer_thread
sfx_l, sfx_r     := ga.Sfx_process(&app.sfx)
layer_l, layer_r := ga.Layer_process(&app.layer)
l := (sfx_l + layer_l) * 0.6
r := (sfx_r + layer_r) * 0.6
```

Do not skip an asset's `_process` because it is silent. A Music Layer that is not called does not advance its pattern, and an asset in the middle of a reverb tail that is not called does not finish decaying.

### Assets that process *your* audio

An Instrument containing an **Input** node is an effect, not a source: a reverb bus your game routes other sounds through. Feed it one stereo frame, then pull one out.

```odin
Verb_feed_input(&verb, l, r)
out_l, out_r := Verb_process(&verb)
```

`_feed_input` is emitted for every asset, but it only does anything when the patch actually reads it; the header gains an extra paragraph about effect assets when the project contains an Input node at all.

### `_is_playing` — and exactly when it goes false

```odin
Sfx_is_playing :: proc(p: ^Sfx_Processor) -> bool
```

This is how you know a one-shot has finished and its slot can be re-used. It returns true if **any** of three things is true:

1. the asset's sequencer transport is running (`p.playing`, set by `_start`) — so a Music Layer is "playing" from `_start` until `_stop`, or until a non-looping pattern reaches its end;
2. any voice is still active;
3. **the effect tail has not run out.**

That third clause is the one that bites people. A voice becomes inactive when all of its envelopes reach Idle — but a Delay or Reverb sitting after the voices is still audibly ringing at that moment, and an asset that reported `false` there let games free the slot mid-echo. So on the falling edge — the first sample at which no voice is alive and the transport is stopped — the asset arms a countdown from its **live** parameter values and reports true until it expires:

```odin
// excerpt — generated from skald-backend/tests/fixtures/delay_tail_live.json
Asset_bus_tail_seconds :: proc(p: ^Asset_Processor) -> f32 {
	total: f32 = 0.0
	mix_3: f32 = (f32(0.500000000));
	if mix_3 > 0.0 {
		period_3: f32 = (p.delayTime);
		fdbk_3: f32 = (p.feedback);
		total += skald_feedback_tail_seconds(period_3, fdbk_3)
	}
	return total
}
```

`skald_feedback_tail_seconds` is the time for a feedback line to fall 60 dB, computed once per note-off rather than once per sample, which is what keeps the logarithm off the audio path (`skald-backend/core/codegen_project.odin::emit_feedback_tail_proc`). Only Delay and Reverb nodes that actually have a path to an Output are counted (`skald-backend/core/codegen_analysis.odin::compute_bus_tail_seconds`). The `<Asset>_BUS_TAIL_SECONDS` constant next to it is the *worst case* if every tail parameter sat at its range maximum; nothing reads it, and it is there as a documented upper bound. Do not use it as a timeout — on real content it can be two orders of magnitude larger than the true tail.

**A voice with no ADSR at all** does not vanish on the sample its duration expires — that was a hard cut mid-waveform and an audible click. It lingers for `NOADSR_FADE_SECONDS`, five milliseconds, under a linear fade to zero, applied both to what it adds to the output and to what it feeds into bus effects (`skald-backend/core/codegen_processor.odin::NOADSR_FADE_SECONDS`, `skald-backend/core/codegen_nodes.odin::generate_graph_output_adds`).

One honest caveat about that path. A no-ADSR voice is deactivated by `duration`, and only by `duration`: the emitted line is `if voice.duration > 0.0 && voice.age >= voice.duration + f32(0.005000000) do voice.active = false` — `NOADSR_FADE_SECONDS` is a compile-time constant of the generator, so it is always written out as the literal, never a name. `_trigger` never produces a zero duration (it substitutes one second), but if you call `_note_on(p, note, vel, 0.0)` yourself on a patch with no envelope, that voice never becomes inactive and `_is_playing` never returns false. Either give such a patch an envelope in the editor, or always pass an explicit duration.

### What the game must call, every block

For each asset your game currently has loaded:

1. Fire whatever the gameplay decided this block — `_trigger`, `_note_on`, `_note_off`, `_start`, `_stop`.
2. Apply whatever parameter changes the gameplay decided — `_set_<param>`.
3. Call `_process` once per frame for the whole block, summing into your own mix buffer.
4. Occasionally, not per sample, check `_is_playing` to recycle finished one-shots.

Steps 1 and 2 must happen before the frames they are meant to affect — the demo's producer fires its timeline events immediately before rendering each frame for exactly this reason (`examples/integration_demo/main.odin::handle_mode_events`).

## Parameters at runtime

An **exposed** parameter is the editor's promise that the game can change this number while the sound is playing. An unexposed one is a literal baked into the DSP; changing it means regenerating and rebuilding.

Exposure gets you four things, all named after the asset:

**A real field on the processor struct**, initialised in `_init` to the value you left in the editor.

**A typed setter**, which clamps to the parameter's authored range before writing:

```odin
// excerpt — examples/integration_demo generated_audio.odin
Sfx_set_cutoff :: proc(p: ^Sfx_Processor, value: f32) {
	v := value
	if v < 20.000000000 do v = 20.000000000
	if v > 20000.000000000 do v = 20000.000000000
	p.cutoff = v
}
```

An out-of-range value is not an error and is not reported: it is silently clamped to the nearest end of the range, and the parameter keeps working. The range comes from `schema/nodes.json`, the one authored copy of every parameter's min, max, default and unit, so a setter's bounds are the same bounds the editor's slider had.

**A row in `<Asset>_PARAMS`**, which is a plain slice your tooling can iterate — a debug overlay, a mixer UI, a save system that wants to persist tweaks — without knowing anything about the patch:

```odin
Skald_Param_Info :: struct { name: string, min: f32, max: f32, default: f32, unit: string }

Sfx_PARAMS := []Skald_Param_Info{
	{"cutoff", 20.000000000, 20000.000000000, 800.000000000, "Hz"},
}
```

**A string-keyed pair**, `<Asset>_set_param` and `<Asset>_get_param`. Both return a `bool` that is `false` for a name the asset does not have, and both accept two spellings of every parameter:

```odin
Sfx_set_param :: proc(p: ^Sfx_Processor, name: string, value: f32) -> bool {
	switch name {
	case "cutoff", "2::cutoff":
		Sfx_set_cutoff(p, value)
		return true
	}
	return false
}
```

### Which setter to use, and why the `::` alias exists

Use the **typed setter** in hot gameplay code. It is a clamp and a store, and the compiler resolves it.

Use the **string setter** when the name is data — a config file, a script, a designer-facing tool, a debug console.

The second spelling, `"<node_id>::<param>"`, is the editor's key, and it is also the **stable** one. The typed setter's field name is `cutoff` only while one node in the asset exposes `cutoff`. If a second node exposes the same parameter, both gain a label prefix — `Squelch_LP_cutoff`, `Tail_Filter_cutoff` — and if that second exposure later goes away, the survivor's name reverts. So an edit to node B can rename node A's setter, even though nothing about node A changed (`skald-backend/core/codegen_analysis.odin::build_instrument_plan`). The node id in the `::` key never moves. The generated header states this contract in the file itself; the short version is:

> Game code that must survive edits should key on `<Asset>_set_param(p, "<nodeId>::<param>", v)`.

If you have a handful of parameters and you regenerate rarely, the typed setters are fine and clearer. If you have dozens, or your gameplay code and the patch are maintained by different people, the alias is the one that keeps compiling.

### No dead setters are minted

A setter you can call that does nothing is worse than no setter. Skald therefore refuses to mint one, by two mechanisms.

First, a table of which (node type, parameter) pairs the generated DSP actually reads as a runtime field (`skald-backend/core/codegen_analysis.odin::param_is_reachable`). An Oscillator's `frequency` is dead unless `fixedPitch` is on, because otherwise the pitch comes from the note; every MIDI Input parameter is dead; a `syncRate` is never live. Exposing one of those produces a warning naming the reason and no setter (`::warn_dead_exposed_params`, with the message text in `::param_dead_reason`).

Second, a safety net under the table: after an asset's processor is emitted, the generator scans the emitted **text** for a read of `p.<field>` for every exposed parameter. A field that is only ever written — by `_init`, by its own setter, by a P-lock — is dead by definition, whatever the table said. The asset is regenerated without it, so neither the setters nor the header can advertise it (`skald-backend/core/codegen_analysis.odin::exposed_field_is_read`, `skald-backend/core/codegen_analysis.odin::unread_exposed_fields`, `skald-backend/core/codegen_analysis.odin::omit_resolutions`; pinned by `skald-backend/tests/unit/exposure_scan_test.odin::test_unread_string_exposure_is_pruned_from_body_and_header`).

The practical consequence for you as an integrator: **if `<Asset>_PARAMS` lists it, the DSP reads it.** There is no third category of "present but inert".

### P-locks, and who wins

A sequencer step can carry per-step parameter overrides — **P-locks**. In the generated code a P-lock is a call to the asset's own string setter, emitted into the sequencer step it belongs to:

```odin
// excerpt — generated from skald-backend/tests/fixtures/plock_step.json
	case 8:
		Asset_set_param(p, "cutoff", 8000.000000000)
		Asset_note_on(p, 48, 1.000000000, f32(2.000000000) * (60.0 / p.bpm / 4.0))
```

So the precedence is simply *last writer wins*, and there is no restore. While a Music Layer's pattern is running, every P-locked step overwrites whatever your game last set for that parameter, and the P-locked value then **persists** until the next P-lock on that parameter or your next setter call. There is no shadow copy of the game's value and nothing puts it back at the end of the step.

If your gameplay needs continuous authority over a parameter — a cutoff following the player's depth underwater, say — either write it every block (so you win on every sample except the exact step boundaries), or do not P-lock that parameter in the pattern. Mixing the two on one parameter produces exactly the stutter you would predict.

Two related facts worth knowing. A P-lock target is also enough to *create* an exposed parameter: a parameter nobody clicked "expose" on still gets a field, a setter and a `_PARAMS` row if a step locks it, because the sequencer needs a setter to call (`skald-backend/core/codegen_analysis.odin::effective_exposed_params`). And a P-lock aimed at an unreachable parameter, or at a node that has since been renamed or deleted, is a hard error with the list of valid targets, not a silent no-op (`::collect_plock_targets`).

## Volume and clipping

Each asset's `_process` ends with its own volume and its own soft limiter:

```odin
	return skald_soft_limit(output_left * p.volume, output_right * p.volume)
```

`p.volume` is the Instrument's Volume control, and it has a runtime setter — `<Asset>_set_volume(p, v)`, clamped 0–1. `skald_soft_limit` is a plain `tanh` on each channel, whose ceiling really is 1.0:

```odin
skald_soft_limit :: proc(l: f32, r: f32) -> (f32, f32) {
	lf, rf := l, r
	if math.is_nan(lf) || math.is_inf(lf) || math.is_nan(rf) || math.is_inf(rf) {
		lf, rf = 0.0, 0.0
		skald_master_flush_count += 1
	}
	return math.tanh(lf), math.tanh(rf)
}
```

It is transparent below about 0.3 and saturates smoothly instead of clipping as an asset gets hot (`skald-backend/core/codegen_project.odin::emit_soft_limit_proc`). Two consequences:

**Each asset is individually bounded to ±1**, so no single asset can hand your device an out-of-range sample through gain alone. That matters because Skald does not divide by the voice count — eight loud voices really are eight times as loud as one, and the limiter is what catches it.

**Your sum of N assets is not bounded.** Three assets each returning 0.9 give you 2.7. This is your final mix stage and Skald does not write it for you, but it does give you the same limiter to call: `skald_soft_limit` is a free function in the generated package, emitted into every file. So the honest shape of a game's mix is `skald_soft_limit(sum_l * your_gain, sum_r * your_gain)`. The demo instead multiplies its sum by a bare `0.6` (`examples/integration_demo/main.odin::producer_thread`) — enough for two assets, and not a formula to copy.

An asset can opt out of its own limiter, in which case `_process` returns the raw product and says so in a comment. There is no editor control for this; it is the Instrument's `limit` parameter, settable only by hand-editing the save or in a project-shaped JSON, and absent means limited (`skald-backend/core/codegen_processor.odin::generate_processor_code`).

**Roadmap 9.9 (audio-safety guardrails) changed one thing for the game-facing API specifically, and it is unconditional — `limit: false` does not opt out of it.** Immediately before that `return` line, `_process` now checks its own `output_left`/`output_right` for NaN or Inf (an unstable filter, a runaway feedback network, a divide-by-zero in a hand-authored graph) and flushes them to silence, counting the flush in a new per-asset field: `p.nonfinite_count` (`skald-backend/core/codegen_processor.odin::generate_processor_code`). Before this, a NaN output propagated through `math.tanh` as NaN — silently poisoning anything summed with it — and an Inf output came out of `tanh` as a false, perfectly in-range `±1.0` tone, indistinguishable from a real loud sample. There is no setter to read `p.nonfinite_count` back from your own game code today (the editor's preview reads it through the separate wasm-shim exports below); treat its existence as a guarantee that a broken patch goes silent instead of glitching, not as a diagnostic you can currently query at runtime.

The **DC blocker** roadmap 9.9 also asks for lives on the master bus (`project_process` / the preview shim's `skald_process`), not on the per-asset path above: a one-pole filter like it rings for a couple of milliseconds on a sudden note onset, which would have broken this manual's own pinned `panner_center_unity`/`panner_mono_sum` exact-gain fixtures had it sat inside `_process`. Since `project_process` is the wrapper this chapter already tells you to ignore, **the DC blocker never reaches your game** — if a patch has a genuine DC offset problem (the asymmetric Distortion shape is the one node that can introduce one, `docs/manual-source/85-deliberate-exclusions.md`'s `KI-041`), your own final mix is still the only place it gets removed, exactly as before this packet (`skald-backend/core/codegen_project.odin::emit_dc_block_proc`).

The project's **master volume** slider is a different thing again, and on the per-asset path it does not reach you: it is applied inside the `project_process` wrapper that game code is told not to use, and (as `skald_set_master_volume`) inside the preview shim. If the sound designer's master fader is part of the intended mix, ask them for the number and fold it into your own final gain — or, better, treat their per-asset Volume settings as the mix and your final gain as a master you control. One trap to know about: a project saved with `masterVolume` at exactly 0 exports **silent**, and the generator prints a loud warning saying so, because an authored 0 means the fader was pulled down; an *absent* key still means unity (`skald-backend/core/json.odin::resolved_master_volume`, `::warn_authored_master_silence`, pinned by `skald-backend/tests/unit/master_volume_test.odin::resolved_master_volume_authored_zero_is_silence`).

## The threading contract

This is the one section to read twice, because the generated code cannot enforce it.

> Every call on one asset — `_init`, `_note_on`, `_note_off`, `_trigger`, `_start`, `_stop`, `_set_*`, `_set_param`, `_process`, `_is_playing` — must come from the thread that calls that asset's `_process`.

The setters are **plain field writes with no synchronisation**. `Sfx_set_cutoff` is a clamp and a store; `Sfx_process` reads `p.cutoff` directly on the same sample. There is no atomic, no mutex, no double buffer, and no pending-value queue anywhere in the generated code. So a setter called from your gameplay thread while the audio thread is inside `_process` is a **data race** — undefined behaviour, not merely a parameter that arrives a frame late.

What that means in practice, since most games do not render audio on the gameplay thread: **queue the values yourself.** Your gameplay code writes the desired cutoff into a structure it owns; the audio thread drains that structure at the top of its block and calls `Sfx_set_cutoff`. A single-producer/single-consumer ring, or a small array of atomics with a dirty flag, is enough. The demo sidesteps the question entirely by calling both the setters and `_process` from the same producer thread, with the device callback doing nothing but drain a ring buffer of already-rendered samples (`examples/integration_demo/main.odin::audio_callback`, `::producer_thread`) — a shape worth copying if you have no other constraints.

Separate assets are separate state. Two assets driven from two different threads are fine, as long as each asset is only ever touched by one of them.

## Regenerating

The sound designer will change the patch. Here is what your code survives and what it does not.

**Survives a regeneration:**

- The asset prefix, as long as its Export ID is pinned. Renaming the Instrument does not rename `Sfx_trigger`.
- Every `"<nodeId>::<param>"` key. Node ids do not change.
- The asset's *order* in the file, which is sorted by sanitised node id — a total, stable order that does not depend on Odin's map iteration (`skald-backend/core/graph_utils.odin::nodes_sorted_by_id`). Nothing in the game-facing API is addressed by index, so this matters mainly to the preview shim, but it also means the diff of two regenerations is readable.
- The general shape of every procedure. `_init`/`_trigger`/`_process`/`_is_playing` are always there.

**Does not survive:**

- A typed setter's field name, if another node in the asset starts or stops exposing the same parameter (see the `::` alias above).
- An asset's prefix, if its Export ID was never pinned and someone renames the Instrument.
- Any parameter that stops being exposed: its field, setter and `_PARAMS` row all vanish and your call site stops compiling. That is the good failure — loud, at build time.
- Anything you edited by hand in the file. The banner is not a suggestion: the generator writes the target unconditionally, with no diff and no confirmation.

### Telling whether the `.odin` in your game is current

Two digests in the header answer this (`skald-backend/core/provenance.odin::emit_provenance_banner`).

`generator:` identifies the compiler that produced the file. It is not a version number a human maintains — it is an FNV-1a digest over the bytes of every backend source file, embedded at compile time (`skald-backend/main.odin::CODEGEN_SOURCES`, `::source_digest`). Run `codegen.exe -version` and compare its `source-digest:` line to your header's `generator:` line. Equal means the file was made by a generator built from the same sources; different means one of them moved. `-version` also prints a per-file digest, so a mismatch can name the file that changed rather than just asserting staleness. The editor makes the same comparison before every Download Code and refuses to run a mismatched binary (`skald-ui/src/main/codegenStamp.ts::parseStamp`).

`input:` is an FNV-1a digest of the input JSON, with carriage returns skipped so the same committed file digests identically on Windows and Unix checkouts (`skald-backend/core/provenance.odin::input_digest`). Re-run the generator over the `.skald.json` you believe produced the file; if the `input:` line comes out the same, it did.

If you want the strongest form of the check, run the generator again into a scratch path and diff. A generation is deterministic for a given input and generator, so a clean diff is proof.

### The save-format version guard

Skald's save files carry a schema version, and a file from a **newer** Skald than your generator is refused whole rather than half-read:

```
Error: this file was saved by a newer Skald (save version 9; this generator
reads up to 4). Update Skald, or re-save the file from a matching editor.
```

The editor and the generator mirror one number — `skald-ui/src/utils/saveMigrations.ts::CURRENT_SAVE_VERSION` and `skald-backend/core/types.odin::SAVE_FORMAT_VERSION` — and the editor migrates older files forward on load (`skald-backend/core/json.odin::build_project_from_json`, pinned by `skald-backend/tests/unit/save_version_test.odin::test_save_version_newer_is_refused_with_a_message`). An absent version is 0 and accepted, so nothing that predates the field broke.

One detail if you script the generator: the guard applies to **graph-shaped** input — the `.skald.json` the editor writes, with a top-level `nodes` array. A project-shaped export, with a top-level `project` object (like `examples/integration_demo/_demo_project.json`), carries no version field and is not version-checked.

## Walkthrough: building and running the integration demo

`examples/integration_demo/` is a complete, working game-side integration: two assets, a real audio device via miniaudio, a producer thread and a ring buffer, a scripted timeline, and a runtime parameter sweep. About five minutes.

You need Odin on your `PATH`. From the repository root:

**1. Build the generator.** Both `.exe` files are gitignored, so a fresh checkout has neither and the demo's script will not find one.

```
cd skald-backend
odin build main.odin -file -out:codegen.exe
```

That is the same command the golden and acceptance harnesses use, and `codegen.exe` is the name `build_and_run.bat` looks for.

**2. Check the demo project before generating anything.** `-check` runs the whole pipeline — parse, every preflight rule, both emissions, the output-target guard — and writes nothing:

```
.\codegen.exe -in:..\examples\integration_demo\_demo_project.json -check
```

Expected:

```
Check OK: 2 instrument(s)
```

**3. Build and run the demo.** The script regenerates the `generated_audio` package from `_demo_project.json`, compiles, and runs:

```
cd ..\examples\integration_demo
.\build_and_run.bat
```

Expect the regeneration line, then `Codegen OK: 2 instrument(s) -> ...`, then a device line and the timeline, on a clock driven by the sample counter rather than the wall clock:

```
Audio device: <your device> @ 48000 Hz, mode=Full_Demo
[t=0.500s] Sfx_trigger #1
[t=1.500s] Sfx_trigger #2
[t=2.000s] Layer_start
[t=4.000s] Sfx_trigger + cutoff sweep
[t=6.000s] Layer_stop
[t=8.000s] shutdown
Full demo timeline complete.
```

You should hear two filtered saw one-shots, then a kick on every beat, then a third one-shot whose filter opens from 200 Hz to 4000 Hz over 200 ms as `Sfx_set_cutoff` is called per frame (`examples/integration_demo/main.odin::demo_timeline`, `::check_timeline`).

**4. Run it without an audio device.** For CI, or on a machine with no output:

```
.\integration_demo.exe -mode:silent-test
```

Expected, with exit code 0:

```
silent-test PASS (48000 frames clean, mode=Silent_Test)
```

That mode renders one second in memory and checks every sample for NaN and infinity (`examples/integration_demo/main.odin::run_silent_test`). It is a good smoke test to steal for your own build: nothing in the generated `_process` sanitises its own output, so a patch driven into instability reaches your device unless you check.

The other modes — `-mode:sfx-once`, `-mode:sfx-loop`, `-mode:layer` — are listed in `examples/integration_demo/README.md` and are the smallest versions of each API shape.

**5. Read the generated file.** Open `examples/integration_demo/generated_audio/generated_audio.odin`. The script has just rewritten it from the project next to it, so the header's `input:` digest and your generator's `-version` will agree — the exact check described above, done for you.

## Preflight: what the generator refuses

Skald would rather stop the build than hand you an asset that compiles and sounds wrong. Every hard error below exits **1** and prints one message naming the offending nodes and the fix; a successful run exits **0** and prints `Codegen OK: N instrument(s) -> <path>`. Warnings go to stderr and do not change the exit code.

| Refused | Message shape |
|---|---|
| An Instrument inside an Instrument | *instrument "Outer" contains another Instrument ("Inner", node id 2) … use Explode Instrument …* (`skald-backend/core/graph_validate.odin::validate_no_nested_instruments`) |
| Two nodes with the same id | *instrument "Asset" has two nodes with the same id "1" …* (`skald-backend/core/graph_validate.odin::validate_unique_node_ids`) |
| Two ids that sanitise to one identifier | *node ids "osc-1" and "osc_1" … become the same identifier "osc_1" …* (`skald-backend/core/graph_validate.odin::find_duplicate_node_id`) |
| A project with no Instrument | *input contains no instruments. Wrap nodes in an Instrument …* (`skald-backend/main.odin`) |
| Two assets exporting under one prefix | *instruments "Bass" and "Lead" would both export as "Keys" …* (`skald-backend/core/codegen_analysis.odin::find_export_prefix_conflict`) |
| A wire to a port that does not exist | named, rather than dropped (`skald-backend/core/graph_validate.odin::validate_connections`) |
| One modulator feeding both a per-voice and a post-effect node | *A modulator runs once per voice or once per sample, never both … Duplicate the LFO …* (`skald-backend/core/codegen_analysis.odin::find_voice_source_into_bus_modulator`) |
| A P-lock on a missing or inert parameter | the message lists every valid target (`skald-backend/core/codegen_analysis.odin::collect_plock_targets`) |
| A node type with no generator | refuses and exits, rather than writing a file with a hole in it |
| A save from a newer Skald | the version message above |
| An output path owned by another Odin package | see below |

The last one is two guards, not one, and the second deserves its own note because it will happen to you the first time you point `-out:` at a source directory. The first guard is the exact-path case: if the output file already exists and declares a *different* `package` — a hand-written file, most often the test harness — the generator refuses to overwrite it rather than silently replacing hand-written code. The second guard is the sibling-directory case: Odin allows one package per directory, so writing `package generated_audio` into a folder that already contains a different package would break that folder's build even though the target file itself doesn't exist yet. The generator refuses, and names the file it found:

```
Error: Refusing to write into <dir>: it contains demo_generated_audio.odin
('package generated_audio'), and Odin allows only one package per directory —
adding 'package skald_bass' there would break the build. Pick a directory of
its own, such as skald-backend/tester/generated_audio/generated_audio.odin.
```

Give each generated package its own directory (`skald-backend/core/target_guard.odin::codegen_target_conflict`, mirrored on the editor side by `skald-ui/src/main/codegenGuards.ts::assertCodegenTargetSafe` and pinned by `skald-backend/tests/unit/target_guard_test.odin::test_overwrite_foreign_package_is_refused_naming_both`). `-out:nul` is exempt: it is the documented way to run the generator for its diagnostics alone.

Warnings you should read rather than ignore: an exposed parameter the DSP never reads, an authored master volume of 0, a modulation source whose peak will hit the exponential pitch clamp (`skald-backend/core/codegen_analysis.odin::warn_exponent_port_overdrive`), a node with no path to an Output, and a Panner whose pan cannot reach the output. None of them stops the build. All of them describe an asset that will not sound the way it was authored.

If you wire the generator into CI, `-check` is the cheap gate: it exercises every rule above, generates both shapes, and writes nothing, so a bad patch fails your pipeline instead of your game.

## Deliberate limits

Some things the generated code does not do are not gaps — they are decisions, made once and written down. The audio is mono internally with a terminal Panner; there is no runtime tempo control, because the BPM is baked into the sequencer's step arithmetic at `_init` and no `set_bpm` exists; the voice count is an array size and therefore a build-time choice; and there is no offline render, no stem export and no scale quantisation *in the generated package* — the editor bounces and exports stems itself (see "Bouncing and stems" above), but nothing in the `.odin` you ship does. Read "What Skald deliberately does not do" for the full list and the reasoning behind each; this chapter deliberately does not restate it.

## Terms introduced

| Term | Meaning |
|---|---|
| **Asset** | One exported Instrument, with its own processor struct and its own `<Asset>_`-prefixed public API. Either an SFX or a Music Layer. |
| **Export ID** | The Instrument setting that names the asset's API. Pinning it means renaming the Instrument never renames a generated symbol. |
| **Asset prefix** | The sanitised Export ID that every one of an asset's procedures carries. A leading digit gains an `n`; anything outside `[A-Za-z0-9_]` becomes `_`. |
| **SFX asset** | A one-shot the game fires with `_trigger` / `_note_on`. Its sequencer track is not emitted. |
| **Music Layer asset** | An asset that carries its own sequencer pattern, driven by `_start` / `_stop` / `_set_loop` and stepped from inside `_process`. |
| **Exposed parameter** | A parameter promoted to a live, named, range-clamped field on the generated processor, with a typed setter, a `_PARAMS` row and a string-keyed setter. |
| **Typed setter** | `<Asset>_set_<field>(p, value)`. Fast and compiler-checked; its field name can change when another node's exposures change. |
| **String setter** | `<Asset>_set_param(p, name, value) -> bool`. Slower, data-driven, returns `false` for an unknown name. |
| **`::` alias** | The `"<nodeId>::<param>"` key accepted by the string setters. The stable name: node ids never change. |
| **`_PARAMS` table** | A slice of `{name, min, max, default, unit}` describing everything an asset exposes, for tooling to enumerate at runtime. |
| **P-lock** | A per-step parameter override in the sequencer. Emitted as a call to the asset's own string setter, so it overwrites the game's value and the new value persists. |
| **Bus tail** | The audible ring of a Delay or Reverb after the last voice has stopped. Counted down from live parameter values and reported by `_is_playing`. |
| **Soft limiter** | `skald_soft_limit`, a plain per-channel `tanh` with a true ceiling of 1.0. Applied per asset inside `_process`, and available for your own final mix. Flushes a NaN/Inf input to silence and counts it, unconditionally — `limit: false` does not opt out of this half. |
| **Non-finite flush count** | `p.nonfinite_count` on each asset's own processor struct — how many times that asset's `_process` has had to silence a NaN/Inf output. No per-asset getter ships to game code today; the editor's preview reads the equivalent through the wasm shim's `skald_get_nonfinite_count`/`skald_get_asset_nonfinite_count`. |
| **Provenance stamp** | The `generator:` and `input:` digests in the header. Content-derived, so they cannot be forgotten, and they answer "is this file current". |
| **Save-format version** | The number the editor stamps into every save. A file from a newer Skald is refused whole rather than half-read. |
| **Preview shim** | The second file emitted from the same analysis, `@(export) skald_*`, used only by the editor's WASM preview. Not part of the game-facing API; do not ship it. |

Known issues affecting export are tracked in KNOWN-ISSUES.md under **Export API**.
