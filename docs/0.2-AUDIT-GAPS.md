# D2 — Adversarial final check on the Skald 0.2 audit

Read: all 10 Tier 1 files, all 12 Tier 2 files, all 5 Tier 3 files (199 + 60 findings). Deliberately
did **not** read D1's roadmap. Everything below was re-derived from the repo. I ran the UI test
suite and the repo's prebuilt binaries read-only; I compiled nothing.

**Headline:** the audit is good and C1's calibration is mostly right, but three things are true that
nothing in the 27 files says. (1) **The audited tree is not the committed tree** — four source
modules imported by shipped code are untracked, ten files are modified, the entire manual and the
`snes-kit` corpus are untracked, and the "repo's prebuilt" `skald-backend/codegen.exe` that four
Tier 3 agents used as ground truth **is not in the repo at all**. (2) **The shipped v0.1.0 installer
cannot preview audio for any user** — it bundles no Odin compiler, `findOdin` cannot see the
vendored one, and nothing tells the user. The core loop is dead in the *released* product, not just
the committed tree. (3) **C1 is wrong once, and it is the dangerous kind of wrong**: it endorses
F-B04-2's claim that `json.odin:203-222` is dead code. C3 caught it; if D1 follows C1, someone
deletes the only code path that parses instrument subgraphs.

## Gaps worth adding to 0.2

**G1 — The packaged app cannot preview, and neither can a developer in a fresh shell. (S)**
`forge.config.ts:20` bundles no Odin. `main.ts:178`'s candidate list omits the vendored
`.tools/odin-dev-2025-02/…/odin.exe` that `setup-dev.ps1:67` downloads. `setup-dev.ps1:78-79` sets
`SKALD_ODIN` for the current session, then prints "Run: cd skald-ui; npm start" (`:88`). README's
Install section never mentions Odin. Fix: add the `.tools` path to the candidate list, persist
`SKALD_ODIN` at user scope, and state the prerequisite in the README. **This must land before any
"delete the tracked exe and build it on `prestart`" change** — see D5.

**G2 — Confine `invoke-codegen`'s output path. (S)**
`main.ts:95-105` writes renderer-supplied bytes to a renderer-chosen absolute path with no
normalization and no extension check; `main.ts:109-119` then passes the same string as `-out:` and
`skald-backend/main.odin:96` writes it blindly. `assertCodegenTargetSafe` (`codegenGuards.ts:83-86`)
only compares `package` declarations and returns early when the target does not exist — i.e. exactly
the drop-a-new-file case. No shell is involved (`spawn` with an args array everywhere, no
`shell:true`), so this is a write primitive, not command injection. Fix: keep a main-side set of
paths returned by `select-output-path` and require membership; add
`setWindowOpenHandler(() => ({action:'deny'}))` and a `will-navigate` guard.

**G3 — Sanitize `exposedParameters` names. (S)**
`codegen.odin:1250` is `field_name := p_name` — verbatim from the project file
(`projectSerializer.ts:45`). It is then spliced into a struct field, an init line, a proc name, a
`_PARAMS` string literal, two `case "…"` literals, and a P-lock emission. `node_key_emittable`
(`:1006-1013`) validates the *node id* but not the param name, and `lookup_param_range` accepts any
unknown name. A newline or quote reliably produces uncompilable Odin while codegen still prints
"Codegen OK". One call: `sanitize_identifier(p_name)`. This is the same defect class as F-B04-5 and
should ship with it.

**G4 — Rename `snes-kit` before `examples/` ships. (S)**
I generated `examples/snes-kit/songs/space-funk.skald.json` with the repo's codegen: the output
contains **467 occurrences of "SNES"** and every public entry point is `SNES_Kick_init`,
`SNES_Snare_trigger`, `SNES_Slap_Bass_process`, … A Nintendo trademark propagates into the
downstream user's shipped game source. `examples/snes-kit/README.md:10-17` additionally names *The
Flintstones (SNES) — Unused Song 2 (Dean Evans / Ocean)*. `dialogDefaults.ts:30` hardcodes
`IMPORT_SUBDIR = 'snes-kit'`. The uncommitted `forge.config.ts:20` change adds `'../examples'` to
`extraResource`, so the *next* release installs all of this on users' machines; v0.1.0 does not
(verified: `skald-ui/out/Skald-win32-x64/resources/` holds only `app.asar` + the exe). Rename to
`16bit-kit` / `16-Bit Kick` etc. — one constant, one README, the JSON `name` fields, and chapter 70.

**G5 — Add a third-party NOTICE. (S)**
`skald_codegen.exe` is statically linked against Odin's `base:`/`core:` libraries, BSD-3-Clause
(clause 2 requires reproducing the notice in binary redistribution). No `NOTICE`,
`THIRD-PARTY-NOTICES` or `LICENSES` file exists anywhere in the repo or the packaged output.
Chromium/Electron is already covered by the auto-copied `LICENSES.chromium.html`. One page.

**G6 — Window-close guard + autosave. (M)**
`main.ts:22-30` registers no `'close'` handler; `main.ts:54-58` quits unconditionally; there is no
`beforeunload`, no dirty flag, no Ctrl+S binding (`app.tsx:203-268` binds Ctrl+Z/Y, Ctrl+C/V, `[`/`]`
and nothing else), and `main.ts:324` is a bare `writeFileSync` with no temp-and-rename. C4-5 covers
the Load path; **nobody covered the close button**, which is the more common way to lose a session.
Add: dirty flag → `close` prompt → 30 s autosave to `userData/recovery.json` → atomic save
(this last is F-B06-3, currently rated `medium` — see "Under-weighted").

**G7 — Single-instance lock. (S)**
`main.ts:243` uses one fixed `userData/wasm-preview/` for `generated_audio.odin`, `wasm_shim.odin`
and `skald.wasm`. `previewBuildChain` (`main.ts:229`) serializes builds *within one process*. There
is no `app.requestSingleInstanceLock()`. Two windows = two `odin build` runs writing the same three
files. Also: nothing is cleaned up on quit, and `main.ts:206`'s `child.kill()` terminates only the
direct child, so `wasm-ld.exe` survives on Windows.

**G8 — Strip the BOM on Load. (S)**
`main.ts:346` / `:375` read with `'utf-8'`; Node does not strip a BOM, so `JSON.parse` throws and the
user sees "not valid JSON". The Odin backend *does* skip `RUNE_BOM`, so a BOM'd file compiles via the
CLI but cannot be opened in the editor. Any file that passed through PowerShell 5.1
`Out-File -Encoding utf8` has one.

**G9 — Fix the leaked render loop. (S)**
`app.tsx:275-291` injects the live `AnalyserNode` into every Output node's `data` and never removes
it; `useWasmAudioEngine.ts:116-123` closes the context on Stop but the node data still holds the dead
analyser, so `AudioVisualizer`'s rAF loop (`AudioVisualizer.tsx:22,94`) keeps running at 60 fps
forever, per Output node, pinning the closed audio graph. Side effect: that dead object is
serialized into save files via `toObject()` (`useFileIO.ts:72-78`).

**G10 — Accessibility floor. (M)**
Not full WCAG — three things: give the palette items a real `onKeyDown` (they already claim
`role="button"`), add a visible `:focus-visible` style (`index.css` is 22 lines and several controls
set `outline:'none'`), and make arrow keys work on integer sliders (`CustomSlider.tsx:112-121`
quantizes a 0.1 step to zero movement on a 1–32 param). Everything else can wait.

**G11 — Code signing. (M, mostly procurement)**
Verified: `Skald-0.1.0 Setup.exe`, `skald_codegen.exe` and `skald-backend/codegen.exe` are all
`NotSigned`. No signing config in `forge.config.ts` or either workflow. A 140 MB unsigned installer
gets a SmartScreen wall. If a certificate is out of scope for 0.2, say so in the README rather than
leaving users to discover it.

**G12 — Audit chapter 70 and `snes-kit`. (M)**
`docs/manual-source/70-space-funk-build.md` is a full build-along with 45 `file:line` citations, and
the 16 patches it teaches are untracked. It codegens cleanly today (I ran it: `Codegen OK: 6
instrument(s)`), but it has had zero review. It is also the chapter most likely to be a new user's
first hour.

## Under-weighted

**F-B09b flash_3 #6 — "No IPC parameter validation." Rated `live` with no severity at all.**
This is G2, the only renderer→arbitrary-write primitive in the app. It sits in a triage table between
"sync `fs.readFileSync`" and "no CSP", and would drop out of any severity-sorted plan. **→ high.**

**F-B06-3 (atomic save) — `medium` → high.**
On its own, "a failed overwrite can corrupt the file" is a medium. Beside G6 (no autosave, no
backup, no dirty flag, no close prompt) and F-B06-2 (Load destroys the session), it is the last
remaining copy of the user's work. Four separate findings, one conclusion: **Skald has no mechanism
by which a user's work survives anything going wrong.** No single agent could see that, because the
pieces are in B06, B07, C4 and (for the close button) nowhere.

**F-B08-8 (`findOdin` never caches misses, uses blocking `spawnSync`) — `low` → medium.**
Rated low because "ENOENT fails immediately". True in isolation. Combined with G1 — which makes the
miss the *normal* case for a fresh shell and for every packaged install — the app now runs an
uncached, main-thread-blocking three-candidate probe on **every** Play, and one hung candidate
freezes all IPC for 10 s (`main.ts:181`).

**F-B01-2's addendum (sequencer history unbounded) — needs its own line.**
C1 added it as supporting evidence for the undo-desync finding. It is also a memory leak:
`useSequencerState.ts:14-17` pushes a full snapshot of the tracks array on every `toggleStep`, and
`StepGrid.tsx:154-159` fires that per cell entered during a paint-drag. Paired with G9, "memory
growth over a long session" is a real 0.2 item that no agent owned.

**F-B09b-1 (duplicate node id → connections point at the wrong node) — promote out of triage.**
C1 verified it live and said it "deserves promotion out of a triage document". It is still sitting in
09b's findings list, where a severity filter over the main finding set will never see it. The code's
own warning admits the defect (`json.odin:196-200`).

**F-A05-3 (no diagnostic for zero `GraphOutput`) — `medium`, and it is the other half of C4-3.**
26 of 101 examples produce a red banner on Play. The generic version of that failure — a patch that
builds clean and is silent — has no diagnostic at all. Fixing only the auto-wrap leaves the silent
case.

**F-B11-2 (six node types with zero fixture coverage) — correct, and its own strongest evidence.**
Noise, LFO, S&H, Mapper, MIDI Input, Distortion are exactly the six where Tier 1 found live bugs.
That is the single most predictive statement in the whole audit and it is rated alongside doc-bugs.

**F-C1-6 (manual untracked) — `medium` → 0.2 blocker, and understated.**
C1 listed `stepMetrics.ts` as the one untracked module imported by shipped code. There are **four**:
`stepMetrics.ts`, `useElementWidth.ts` (both imported by `PianoRoll.tsx`/`StepGrid.tsx`),
`src/main/dialogDefaults.ts` (imported by `main.ts`), `src/utils/importLayout.ts` (imported by
`useFileIO.ts`) — plus 3 untracked test files, and the whole `scripts/manual/` Node project with its
own lockfile. Committing the 10 modified files without the 4 new modules breaks the build.

## Dangerous recommendations

**D1 — Deleting `json.odin:203-222` (from F-B04-2, endorsed by C1).**
Would remove subgraph parsing for every instrument on both ingestion paths. See "Accuracy
corrections". **Instead:** keep the branch; add the preflight rejection for *nested* Instruments that
F-B04-2's second half actually recommends.

**D2 — C2's F-C2-1 recommendation #1: move the `tanh` limiter into every per-asset `_process` and
have `project_process` "stop needing its own and just sum".**
`project_process` currently does `mixed += l` per asset then `tanh(mixed * master_vol)`
(`codegen.odin:2468-2478`). If each asset returns a tanh-bounded ±1 and the wrapper only sums, an
N-asset project can reach ±N with **no limiter at all** — for `four-bar-song` that is ±5 into the
device. The WASM preview's `skald_process` mirrors `project_process`, so this breaks the *editor*
too. It also destroys the property `00-foundations.md:421` documents (master volume reduces
saturation), because saturation now happens before master volume. C2's own migration note — "it can
only ever make output quieter, never louder" — is true per-asset and false for the project path.
**Instead:** C1's F-C1-8(2) / C3's F-C3-7(3) — emit a standalone `skald_soft_limit(l, r)` that both
`project_process` and the per-asset integration path call. Same benefit, no regression. Note C1, C2
and C3 each propose a *different* master-gain architecture and none cites the others; pick one
before any of it is assigned.

**D3 — The Panner gain fix has two proposals pointing in opposite directions and no decision.**
F-A08-3 and F-B10-3 say attenuate the direct-to-Output path by 0.7071. C2's F-C2-2 says multiply the
Panner's pair by 1.4142 and explicitly rejects the other. C5 correctly identifies it as "a pan-law
decision that has never been made" but leaves it in 0.2 as "one line". Whichever agent implements it
first sets the law. Additionally, ×1.4142 raises peaks in a system C2 itself measures at 7.9 dB into
the master saturator, and its safety depends on D2's limiter — which is the flawed recommendation.
**Instead:** record the decision explicitly (only 1 of 80 `.skald.json` patches contains a Panner —
`examples/instruments/keys/glassy-fm-pluck.skald.json`, verified — so re-levelling 80 patches to
match 1 is clearly wrong; C2's direction is right, but sequence it after the limiter question is
settled).

**D4 — C2's F-C2-8: change P-lock stickiness for shipped patches, non-opt-in.**
It proposes emitting a restore of the authored value at step 0 and says "ship it as the fix, not as
an opt-in", changing the audio of four shipped patches. But stickiness is a *deliberate, commented*
design decision (`codegen.odin:2160-2165`: "they persist until the next override — Elektron-style").
Silently overriding a documented intent is the same failure mode the audit spends 199 findings
criticising. **Instead:** document the five precedence rules (which is C2's own first recommendation
and is unambiguously right), and treat the restore as a design proposal for 0.3.

**D5 — "Delete the tracked `skald_codegen.exe`; make `start`/`make` depend on `build:codegen`"
(F-C1-1, F-C3-1, F-C4-1 — all three, none sequenced against G1).**
The change is correct in principle. As specced it makes `npm start` require Odin on PATH — and

## Strategic note

**The 0.2 framing is wrong in one specific way: it treats the problem as a backlog when the evidence
says the problem is reproducibility and delivery.**

Three facts nobody assembled. (1) The tree cannot be released: 53 commits past `v0.1.0`, dirty, four
untracked source modules imported by shipped code, the whole manual and `snes-kit` untracked. (2) The
*already-released* v0.1.0 installer cannot preview audio for anybody, because it ships no Odin and
never says so. (3) The repo's own history is the strongest evidence in the audit: B09a and B09b show
111 architecture findings surviving three review rounds, the CODEX five-wave plan at ~1.5/5, and a
one-line Create Group fix scheduled first as a "no-risk warm-up" surviving two rounds unfixed. C5-11
counts four documents that already look like plans. **A fifth plan, containing 25–30 blockers across
five agents' lists, is the intervention with the worst track record in this repository.**

The three agents who costed it disagree by 3×: C2 says "a week", C4 says "two focused weeks", C3 says
"two to three focused weeks" *and* explicitly defers every feature. Their blocker lists overlap but
are not the same list. Union them honestly and it is 6–10 weeks of one person's time — which is not
a 0.2, it is a rewrite of the release.

**The cheaper move, and I think the right one: cut a 0.1.1 whose entire scope is "someone who is not
the author can install this and hear a sound."** Roughly a week:

1. Commit everything; prove a clean clone builds and tests green. Nothing else is verifiable first.
2. G1 — the packaged/fresh-shell Odin path.
3. F-C1-1/F-C3-1 — binary provenance, in that order (D5).
4. F-B04-1 — one-hour sorted-iteration fix; it is the cheapest permanent win anyone found.
5. The four CI gates from C5-F-C5-9 (examples corpus with the corrected glob, range parity, generated-example
   freshness, binary freshness). **Gates, not tickets** — the repo's history says checkability, not
   severity, predicts what gets fixed.
6. G4 + G5 — trademark rename and NOTICE, before `extraResource: ['../examples']` ever ships.

Then re-triage against a tree that can be reproduced and a product that runs. My expectation is that
a meaningful fraction of the 259 findings will look different from that vantage point — several
already do (F-A07-1 and F-A08-1 are the worked example: "the manual is stale" and "the fix was never
delivered" are the same evidence read from two different trees).

**The bigger move, if the appetite exists:** C4-14 is right that the pitch is too broad, and the
scope work in C5-F-C5-6 is the best single artifact in the audit. But neither is worth doing before
step 1. A positioning statement about a product that cannot be installed and run is a document about
an idea.
